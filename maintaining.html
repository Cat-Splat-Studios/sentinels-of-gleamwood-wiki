Maintaining the wiki

This wiki only works if it stays true. This page makes staying true mechanical: what to update when, how to re-shoot the screenshots, and how to add a page — no judgment calls required.

01The three laws of this wiki

Code is the only truth

If the wiki and the code disagree, the code wins and the wiki has a bug. Fix it in the same commit as the code change — a stale page is worse than no page.

Every page declares its sources

Each domain page ends with a “Keep this page honest” box listing the exact files it mirrors (the index mirrors no sources, so it has none). Touched one of those files? That page is now suspect. That box is the whole audit system.

Screenshots are regenerated, not edited

Every screenshot is captured from the live editor by a menu item. Nobody crops or annotates by hand — if a tool's UI changes, re-run the capture and the images are current again.

The gate is five checks, and it lives in §06. Validate Run Content clean · the PlayMode suite green via Tools/run-tests.sh · python Tools/check-wiki.py prints OK · DebugSettings.json restored after the run · the wiki edit in the same commit. It is at the bottom of this page because it is the last thing you do — not because it is the least important, so go and read it once now.

Modding & campaigns
Mod / locale loading — folders, precedence, or what a broken file doesdialogue.html §09 + the shipped README. The editor/build divergence is load-bearing: builds always load overrides, and the editor loads them whenever a campaign is active — every domain gates on ModSet.Active != null || SimulateKey, so the Simulate Mods toggles only force a domain on when no campaign is bound. A toggle sitting off therefore proves nothing; check what the slot is bound to before concluding your asset edit is what the game read.
Enemy modding — the override loader, the clone, or a new field on any state configenemies.html §10. A new public scalar field on a state config becomes moddable automatically (the loader reflects over public fields and the templates are generated) — so the risk is the opposite of usual: the surface grows without anyone documenting it. Adding a field type that is NOT a scalar needs the "what you can and cannot change" table updated, or the templates will quietly omit it with no explanation.
Weapon modding — WeaponOverrides / WeaponVariants, the clone, the loot/catalog injection, or a new field on a weapon or combo/dash configcombat.html §10. Same auto-moddable-scalar rule as enemies (public fields are reflected, templates generated) — plus weapons also parse Vector2 and StatusesToApply by name, so a NEW parseable type means updating both the "what you can change" table AND the WeaponOverrides.Parse allowlist. A new shipped status must be added to the StatusCatalog asset or a mod cannot name it.
The mod model itself — ModSet discovery, mod.ini keys, the vanilla/campaign split, or how a slot binds to a campaignmodding.html §01 (the folder table and "one campaign at a time") + TemplateBuildStepBase.WriteManifestTemplate, whose commented manifest ships in every build and is the first thing a modder reads. Those two must say the same thing. A slot's campaignId is save data — renaming a campaign folder orphans every save made with it, exactly like a nodeId.
The campaign tier — CampaignPlan, the [Plan]/[Node:]/[Biome:] grammar, or what refuses a webmodding.html §07's key table AND the template emitted by CampaignTemplateBuildStep.cs (it writes out the SHIPPED web, so it self-updates when the web changes — but not when a KEY changes). The key names are deliberately identical to ContentIniImporter's: add a key to one and you owe it to the other, or the copy-a-block-out-of-GameContent.ini promise quietly stops being true.
A new asset kind nameable from a campaign (a biome field pointing at some new SO)RunContentCatalog + its builder — a runtime build has no AssetDatabase, so an unlisted kind is unresolvable from text no matter how correct the parser is. Then the §07 key table. Rebuild with Gleamwood ▸ Dev ▸ Run ▸ Rebuild Content Catalog and commit the regenerated asset.
Player skinning — PlayerSkinOverrides, the PlayerAnimation.Awake hook, or the player's clip vocabulary (a clip added/removed/renamed, or a slot changed on Player.asset)modding.html §06. The skin template is GENERATED from Player.asset, so a new clip appears in it automatically — but if you rename a clip the FSM plays, existing skins that named the old one silently show shipped art for it. The clip-line grammar itself lives in ModClipSetBuilder.ParseClipLine, shared with the enemy graph reader: a new clip keyword there must be documented for both.
Mod art — the sheet reader, the pivot rule, or anything about how a mod's clips are builtUpdate enemies.html §12 — its key table, its refusal table, or both. Two invariants there are load-bearing and neither is obvious from the code: pivot is authored in PIXELS from the bottom (Unity's own default is the centre, which floats every modded creature) — and now optionally as an x,y pair for off-centre anchors like a split-body torso, parsed in EnemyGraphParser.TryPivotXY — and pixels-per-unit is read off the donor's art, never written (the project is standardized at 64 now, but reading it off the donor needs no modder input and keeps a mod at the donor's scale by construction even if a future asset diverges — and a written key could only ever be got wrong, silently resizing the character). If you add an option word to clip, it needs a row in §12's key table; if you add a refusal, it needs one in the refusal table with what would otherwise have happened. Changing the loop default means rewriting the warn box that explains the asymmetry, not just the word.
Graph authoring — a new state config type, a new transition condition, or a change to the [Graph:] grammarenemies.html §11. A new state config type becomes authorable automatically — the type list is derived by reflection over EnemyStateConfig subclasses, so only the printed list in §11 needs the new verb. A new condition does NOT: the allowlist in EnemyConditionCompiler is closed on purpose, so it needs a keyword there and a row in the conditions table. Anything newly refused needs a row in §11's refusal table with the reason — a refusal that does not say what would have happened is barely better than a crash. If you add a field that must never be settable from text, deny it in EnemyGraphParser too, or it becomes a way around every graph check.
Levels & rooms
Room standards, sockets, the reachability model, a validator checklevels.html + Documentation/ROOM_STANDARDS.md if the standard itself moved.
The reachability MODEL — RoomReachability's flood, metrics, or what RoomAudit refuseslevels.html §04 — its "movement model" table mirrors the flood one row per rule — AND ROOM_STANDARDS.md §3 (the trap-only rule) and §4 (change control). Three constants do not follow the asset and are transcribed in RoomReachability.cs: TerminalFallSpeed, BodyWidth, BodyHeight — they live on Player.prefab, so retuning the prefab makes the model wrong. Not silently any more: RoomReachabilityTests.TheTranscribedPrefabNumbers_StillMatchThePlayerPrefab loads the shipped prefab and fails on drift, naming the constant that moved — re-transcribe when it does. Adding a PlayerAbilities flag means new rows in §04 and a new offer in PlayerAbilityCatalog, or nothing can ever earn it.
The .room GLYPH VOCABULARY — a new character, or a change to what one meansUpdate levels.html §02 + ROOM_STANDARDS.md §3b, then fix the code in four places. A glyph owes four places, and skipping any one of them fails silently in a different direction: RoomText.Glyphs (which feeds every refusal message and every written file's header), RoomTextParser (read), RoomTextWriter (write), RoomBuilder (build). The writer is the one people forget, and the failure mode is the worst available: a room round-trips to some other glyph with the whole suite green, because a round-trip test only compares a drawing to itself. Pair any new glyph with a differential that builds the prefab and reads it back. Note also that a glyph carrying collision meaning needs a Unity layer, not a tilemap name — the two role maps Floors/Walls are decorative and shipped rooms already contradict them.
Thin platforms — the OneWay layer, the mover's second cast, or drop-throughlevels.html §02 + ROOM_STANDARDS.md §3/§3d. Two settings here are not preferences and each shipped broken once: the platform map's CompositeCollider2D must be GeometryType.Polygons (Outlines has no interior, so a player mid-pass-through lands on the collider's underside), and the Player prefab must actually carry oneWayMask (a newly-added serialized field is not written into an already-serialized asset, so it deserialises to 0 and every platform becomes air). Both are pinned by ShippedPlayerPlatformWiringTests — tests that read the shipped asset, because a hand-built rig proved the mechanism and shipped the bug twice. PlatformEffector2D cannot be used: the mover is kinematic and resolves collisions with raycasts, which do not consult effectors.
An InteractZone — a new interactable, or what one saysUpdate levels.html §02. Two things bite here. (1) The floating label is auto-provisioned, not wired per prefab, and it must stay that way: RoomBuilder builds a BiomeExit from the X glyph with AddComponent, so a campaign's text rooms have no inspector in which to attach a TextMesh — a label that only appears when someone remembered to drag one in is a label the modding tier can never have. An authored label still wins; auto-creation only fills an empty field. (2) LabelText() returning a string is not evidence the player sees it — that exact gap shipped: RunPlan.TitleFor resolved the destination, BiomeExit.Assign stored it, and RefreshLabel dropped it on if (label == null) return; because every rest-scene interactable had a TextMesh and no room-prefab exit did. Assert on the rendered TextMesh.text, not on the getter.
A layout GENERATOR — LatticeGenerator's tiers, the door discipline, or a new LayoutTopologylevels.html §07b (the tier table and the door discipline) + the genRules rows in §06 + modding.html §07's key table — a campaign INI is the only surface that can select a topology at all, so an undocumented key there is an unreachable feature. If a tier gains a required room shape, say which shipped lat-*.room supplies it, and re-check the sweep in LatticeGeneratorTests that reads those real drawings.
A spawn-table gate — a new axis beside minStage / minRoomDistancelevels.html §08 AND enemies.html §10's header-key table — EnemyVariants.IsHeaderKey is a closed allowlist, so unlike a state-config field this does NOT become moddable automatically. A new gate owes four places: the table, the allowlist, EnemyVariantTable, and EnemyGraphBuilder's known-key list. Miss one and the key reads as "unknown key — ignored".
What the layout plan EXPOSES — a new BiomeLayoutPlan query, or a consumer changing which one it readslevels.html §07 / §09. The rule that earned this row: a choice with two callers (the bypass door and the map that marks it) belongs ON the plan, once — they were separate copies and disagreed in every branched biome. Anything that picks a room for content should be a method there, not a call site.
The WEB itself — a [Node:] added, removed or repointed, or a new [Biome:] in the runFive hand-maintained copies describe the one real file, and every one of them drifts silently: levels.html §07's diagram, tuning.html's verbatim node block and its "what's in the file today" counts, extending.html's orientation line, and Documentation/ExampleMod/…/Campaign/RunWeb.ini (which claims in its own header to be the shipped web). Documentation/CampaignTemplate/RunWeb.ini is the exception — generated and gitignored, so re-run the template build step rather than editing it, and never treat it as a doc to fix by hand. The rule that earned this row: retired nodeIds survived in four of those five after a re-web. Grep the old ids before you call it done. Also state the blast radius out loud — RunWebFingerprint hashes the web's SHAPE, so any of these edits voids in-flight suspended runs while leaving saves and permanent meta intact.
The run web's SHAPE, in the shipped game — a node added/removed, an edge repointed, a biome swapped onto a nodeNothing to write, but know the consequence: RunWebFingerprint hashes exactly this, so every suspended run in every existing save becomes unresumable (the saves themselves survive). Biome tunables are outside the hash on purpose — retune those freely. The one exception is genRules.topology, which RunWebFingerprint folds in per node: swapping a biome's layout topology voids suspended runs exactly like repointing an edge, because the same seed under the other topology does not strand, it silently relocates the player into an entirely different level.
Progression & economy
What the player can DO — RunDirector.Abilities, a PlayerAbilities flag, or when the set is recomputedUpdate progression.html §04b's "Where the ability set comes from" table. The invariant is one line — abilities mirror the ACTIVE SLOT, frozen during a run at what the layout was generated from — and it has exactly one escape hatch: no slot bound ⇒ Owned(null) ⇒ All, which is the editor/sandbox case. Player input ORDERING — anything read in PlayerStateMachine.Update()The order of that method is a contract, not a style. base.Update() runs CheckTransitions() first, and a state's Enter() can consume shared input state — PlayerJumpState.Enter() zeroes LastJumpInputTime. So any check that must beat a transition has to sit above base.Update(); drop-through sat below it and was unreachable on a clean press, which read to the player as "requires mashing the button." The one-commit rule: the wiki edit rides in the same commit (or at worst the same PR) as the code change. Reviewers: a diff that touches a file named in a “Keep this page honest” box, without touching that page, is an incomplete diff.
Why no moving number is written into prose. The suite count used to be hardcoded in seven places, and the trap was documented on this very page BY NAME, listing every site to update — and all seven went stale anyway. That is the proof: a hand-synchronised copy of a moving number is unmaintainable no matter how well the checklist is written, so the fix is one authoritative site and a rule against copying it, not a better checklist. The former sites were index.html (the hero pill, the “Validated, loudly” card and the pipeline SVG's “N-test suite” label), quickstart.html (the §01 card and the §05 checklist), progression.html §08, and Documentation/GAME_TUNING_GUIDE.md's menu table. Apply the same reasoning to any other number that moves every arc.

03Re-shooting the screenshots (one menu click)

One menu item re-shoots every screenshot in the wiki from the live editor, so a tool's UI change is a re-run rather than an editing job. Nobody crops or annotates by hand.

  1. Be at the machine, with the editor in the FOREGROUND, focused and unobstructed. The capture does not ask Unity for a picture of itself — WikiScreenshotTool.Pump calls InternalEditorUtility.ReadScreenPixel at each window's screen rect, so it photographs whatever the OS is compositing over that rectangle. Anything on top of the editor, an alt-tab mid-run, or a screen lock is what lands in the PNG.
  2. Run Gleamwood ▸ Wiki ▸ Capture Tool Screenshots. It opens each tool, positions it, waits for the repaint, and writes every PNG into Documentation/Wiki/images/. Takes a few seconds; the Console logs each capture and ends with [WikiShots] all captures complete.
  3. Skim the PNGs (any image viewer) — open them, do not trust the file list. Commit them with your change. Every PNG the capture writes must be referenced by a page: an unreferenced one is either a missing figure or a shot to delete from CaptureAll(), and Tools/check-wiki.py cannot see it — it validates img→file, never file→img. Two are unreferenced today (workbench-melee-aerials.png, workbench-melee-ground.png — OUTSTANDING.md §1.4).
Never drive this over the Unity CLI, and never headlessly. unity cmd menu --path "Gleamwood/Wiki/Capture Tool Screenshots" is the invocation that works for every other menu item on this project, and it is the one that destroys the wiki: with no human at the machine the foreground window is a terminal, so all thirteen tracked PNGs are overwritten with a photograph of it. Nothing fails. The files keep the right names, the right dimensions and plausible sizes, the Console still logs [WikiShots] captured … for each and ends with [WikiShots] all captures complete, and the hashes are all distinct — only opening one shows what happened. Recover with git checkout -- Documentation/Wiki/images/. This is the one wiki job that cannot be automated; it needs a person with the editor in front of them.

Adding a new screenshot

Open Assets/_Game/Editor/WikiScreenshotTool.cs and add one line inside CaptureAll():

// a workbench page (asset path + optional sub-tab index):
WorkbenchShot("workbench-mything.png", "Assets/_Game/.../MyThing.asset", 1);

// a prefab-stage scene view with gizmos (prefab path + ortho zoom):
PrefabStageShot("tuner-mything.png", "Assets/.../MyThing.prefab", 2.5f);

A sub-tab index is that tab's position in its category's form.SubTabs(…) call, counting from 0. The lists are deliberately not restated here — read them off the SubTabs(…) call in Assets/_Game/Editor/Workbench/WorkbenchCategories.cs (the melee one and the enemy one), because a copy on this page goes stale the day someone inserts a tab and the failure is silent: the capture succeeds and photographs the wrong page under the right filename. Both lists are also mirrored as comments beside the shots in WikiScreenshotTool.cs; those are the ones to keep in step. Reference the new PNG from a page with the standard figure block:

</figure>

04Adding a page

Copy an existing page rather than starting one — the skeleton is fixed, and four mechanical steps are what make a new page reachable and auditable.

  1. Copy any domain page (this one is the canonical skeleton): same <head> with wiki.css, same nav.wiki block, header.page band, numbered <section>s, a “Keep this page honest” box, prev/next links, footer.
  2. Add the page's link to nav.wiki on every page (it's the same block everywhere — a find-and-replace across Documentation/Wiki/*.html).
  3. Add a card for it on index.html's page grid.
  4. Fill the honest box with the real file list the page describes. If you can't name the files, the page isn't ready.
Don't fork styling. All look-and-feel lives in wiki.css. If a page needs a new component, add it to the stylesheet so the next page gets it for free.

06Before you push

Five checks. This is the page's only gate — run it on every push that touches code or the wiki.

  • Gleamwood ▸ Validate Run Content — 0 errors.
  • Tools/run-tests.sh — green (Logs/playmode_test_results.txt), zero failed and zero inconclusive. What the script checks, and what it deliberately cannot. Three of Law 1's obligations are purely mechanical — a link resolves or it does not, an image exists or it does not, a §NN citation matches that section's real number or it does not — and until this script nothing checked them. It also pins the nav.wiki block identical across every page, which is the thing that breaks when a page is added by hand.

The section-label check is the one that earns its keep. Pages cite each other as <a href="levels.html#anatomy">levels.html §05</a> — an anchor and a human-readable number. Every link checker validates the anchor; nothing validates the number, which is a fact about somebody else's file and goes stale the moment a section is inserted anywhere. Every instance found so far had a correct anchor and a wrong number, so navigation worked perfectly and the citation lied. A §NN with no anchor is itself an error — there is nothing to compare the number against, so the check used to skip it in silence, and six citations (five of them on this page) sat in the green column claiming a coverage they did not have. Cite with an anchor, or do not cite a number.

It says nothing about whether the PROSE is true. That check is reading the code, and it is what the "Keep this page honest" boxes are for. A green run means nothing is structurally broken — not that the page is right.
