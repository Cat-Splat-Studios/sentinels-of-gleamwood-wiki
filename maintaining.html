Maintaining the wiki

This wiki only works if it stays true. This page makes staying true mechanical: what to update when, how to re-shoot the screenshots, and how to add a page — no judgment calls required.

01The three laws of this wiki

Code is the only truth

If the wiki and the code disagree, the code wins and the wiki has a bug. Fix it in the same commit as the code change — a stale page is worse than no page.

Every page declares its sources

Each domain page ends with a “Keep this page honest” box listing the exact files it mirrors (the index mirrors no sources, so it has none). Touched one of those files? That page is now suspect. That box is the whole audit system.

Screenshots are regenerated, not edited

Every screenshot is captured from the live editor by a menu item. Nobody crops or annotates by hand — if a tool's UI changes, re-run the capture and the images are current again.

Enemy modding — the override loader, the clone, or a new field on any state configenemies.html §10. A new public scalar field on a state config becomes moddable automatically (the loader reflects over public fields and the templates are generated) — so the risk is the opposite of usual: the surface grows without anyone documenting it. Adding a field type that is NOT a scalar needs the "what you can and cannot change" table updated, or the templates will quietly omit it with no explanation.
Weapon modding — WeaponOverrides / WeaponVariants, the clone, the loot/catalog injection, or a new field on a weapon or combo/dash configcombat.html §10. Same auto-moddable-scalar rule as enemies (public fields are reflected, templates generated) — plus weapons also parse Vector2 and StatusesToApply by name, so a NEW parseable type means updating both the "what you can change" table AND the WeaponOverrides.Parse allowlist. A new shipped status must be added to the StatusCatalog asset or a mod cannot name it.
The mod model itself — ModSet discovery, mod.ini keys, the vanilla/campaign split, or how a slot binds to a campaignmodding.html §01 (the folder table and "one campaign at a time") + TemplateBuildStepBase.WriteManifestTemplate, whose commented manifest ships in every build and is the first thing a modder reads. Those two must say the same thing. A slot's campaignId is save data — renaming a campaign folder orphans every save made with it, exactly like a nodeId.
The campaign tier — CampaignPlan, the [Plan]/[Node:]/[Biome:] grammar, or what refuses a webmodding.html §07's key table AND the template emitted by CampaignTemplateBuildStep.cs (it writes out the SHIPPED web, so it self-updates when the web changes — but not when a KEY changes). The key names are deliberately identical to ContentIniImporter's: add a key to one and you owe it to the other, or the copy-a-block-out-of-GameContent.ini promise quietly stops being true.
A new asset kind nameable from a campaign (a biome field pointing at some new SO)RunContentCatalog + its builder — a runtime build has no AssetDatabase, so an unlisted kind is unresolvable from text no matter how correct the parser is. Then the §07 key table. Rebuild with Gleamwood ▸ Dev ▸ Run ▸ Rebuild Content Catalog and commit the regenerated asset.
The run web's SHAPE, in the shipped game — a node added/removed, an edge repointed, a biome swapped onto a nodeNothing to write, but know the consequence: RunWebFingerprint hashes exactly this, so every suspended run in every existing save becomes unresumable (the saves themselves survive). Biome tunables are outside the hash on purpose — retune those freely.
Player skinning — PlayerSkinOverrides, the PlayerAnimation.Awake hook, or the player's clip vocabulary (a clip added/removed/renamed, or a slot changed on Player.asset)modding.html §06. The skin template is GENERATED from Player.asset, so a new clip appears in it automatically — but if you rename a clip the FSM plays, existing skins that named the old one silently show shipped art for it. The clip-line grammar itself lives in ModClipSetBuilder.ParseClipLine, shared with the enemy graph reader: a new clip keyword there must be documented for both.
Mod art — the sheet reader, the pivot rule, or anything about how a mod's clips are builtenemies.html §12. Two invariants there are load-bearing and neither is obvious from the code: pivot is authored in PIXELS from the bottom (Unity's own default is the centre, which floats every modded creature) — and now optionally as an x,y pair for off-centre anchors like a split-body torso, parsed in EnemyGraphParser.TryPivotXY — and pixels-per-unit is read off the donor's art, never written (enemies are 100, the player 64 — a key could only ever be got wrong, and wrong silently resizes the character). If you add an option word to clip, it needs a row in §12's key table; if you add a refusal, it needs one in the refusal table with what would otherwise have happened. Changing the loop default means rewriting the warn box that explains the asymmetry, not just the word.
Graph authoring — a new state config type, a new transition condition, or a change to the [Graph:] grammarenemies.html §11. A new state config type becomes authorable automatically — the type list is derived by reflection over EnemyStateConfig subclasses, so only the printed list in §11 needs the new verb. A new condition does NOT: the allowlist in EnemyConditionCompiler is closed on purpose, so it needs a keyword there and a row in the conditions table. Anything newly refused needs a row in §11's refusal table with the reason — a refusal that does not say what would have happened is barely better than a crash. If you add a field that must never be settable from text, deny it in EnemyGraphParser too, or it becomes a way around every graph check.

The one-commit rule: the wiki edit rides in the same commit (or at worst the same PR) as the code change. Reviewers: a diff that touches a file named in a “Keep this page honest” box, without touching that page, is an incomplete diff.

03Re-shooting the screenshots (one menu click)

  1. Make sure the Unity editor is visible on screen (the capture photographs real screen pixels — a minimized editor captures garbage).
  2. Run Gleamwood ▸ Wiki ▸ Capture Tool Screenshots. It opens each tool, positions it, waits for the repaint, and writes every PNG into Documentation/Wiki/images/. Takes a few seconds; the Console logs each capture and ends with [WikiShots] all captures complete.
  3. Skim the PNGs (any image viewer). Commit them with your change.

Adding a new screenshot

Open Assets/_Game/Editor/WikiScreenshotTool.cs and add one line inside CaptureAll():

// a workbench page (asset path + optional sub-tab index):
WorkbenchShot("workbench-mything.png", "Assets/_Game/.../MyThing.asset", 1);

// a prefab-stage scene view with gizmos (prefab path + ortho zoom):
PrefabStageShot("tuner-mything.png", "Assets/.../MyThing.prefab", 2.5f);

Sub-tab indices are the order of the tabs on that page, starting at 0 (so Melee: 0 Overview, 1 Swings, 2 Dash Attack; Enemies: 0 Overview, 1 Behavior, 2 Attacks, 3 Reactions, 4 Presentation). Reference the new PNG from a page with the standard figure block:

<figure class="shot">
  <img src="images/workbench-mything.png" alt="What it shows">
  <figcaption><b>Real capture.</b> One sentence saying what to look at.</figcaption>
</figure>

04Adding a page

  1. Copy any domain page (this one is the canonical skeleton): same <head> with wiki.css, same nav.wiki block, header.page band, numbered <section>s, a “Keep this page honest” box, prev/next links, footer.
  2. Add the page's link to nav.wiki on every page (it's the same block everywhere — a find-and-replace across Documentation/Wiki/*.html).
  3. Add a card for it on index.html's page grid.
  4. Fill the honest box with the real file list the page describes. If you can't name the files, the page isn't ready.
Don't fork styling. All look-and-feel lives in wiki.css. If a page needs a new component, add it to the stylesheet so the next page gets it for free.

06Before you push

  • Gleamwood ▸ Validate Run Content — 0 errors.
  • Gleamwood ▸ Run PlayMode Tests — green (Logs/playmode_test_results.txt).
  • Open the wiki page you touched in a browser once. Broken images and dead links are visible in five seconds.
  • The wiki edit is in the same commit as the change it documents (§2).
