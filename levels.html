Levels & Rooms

How a run gets built: room prefabs with sockets, a seeded generator that butts them edge-to-edge, side dungeons, bypass doors, and a validator + reachability audit that refuse to ship a level the player cannot cross. Author rooms against the real movement numbers and the tools do the rest.

01From prefab to run — the pipeline in one glance

Everything on this page is one chain. Know which link you're editing and you know which tool checks your work.

1 · Room prefabs

Tilemap-painted prefabs with a RoomTemplate on the root and door sockets on the edges. Live in Assets/_Game/Biomes/Emberfall/ as Room_Ember_*, plus the three Branching pieces in Assets/_Game/Biomes/Fan/ — Room_Fan_Base (FanBase), Room_Fan_Rise (FanStorey) and Room_Slip_Ember (Exit | SlipAway). Every shipped biome is Branching and pulls those in as Room_Fan_*, Room_Slip_Ember; without a FanBase in the pool the validator hard-errors, so they are not optional extras.

2 · Biome pools

A BiomeDefinition owns a room pool, gen rules, spawn table, music and boss. Authored via Gleamwood ▸ Content Workbench (Levels category) or the INI (§10).

3 · The run web

RunPlan.asset is a DAG of nodes — biomes, rests, forks, bypass edges. The generator assembles each biome from its pool, seeded, at scene load. Nothing is baked.

Two gates guard the chain: Gleamwood ▸ Audit Room Reachability proves every room is crossable, and Gleamwood ▸ Validate Run Content proves the whole web is playable. The validator also runs as a build preprocessor — broken run content throws BuildFailedException and the build refuses to compile.

02Room anatomy

A room prefab is: a root GameObject carrying RoomTemplate, a child Grid with up to three role tilemaps — Floors (walkable tops) and Walls (walls, ceilings, cover) on layer Level, plus the optional Platforms map on layer OneWay — each with a TilemapCollider2D. Grid cells are 1×1 unit, origin at the bottom-left cell corner. Source: Assets/_Game/Systems/Run/ProcGen/RoomTemplate.cs and Documentation/ROOM_STANDARDS.md.

Thin platforms: the layer is the seam, not the map name. Floors vs Walls is a role split, and shipped rooms already contradict it — Room_Ember_BigArena puts one continuous ledge run on both — so it cannot carry collision meaning. The Unity layer can, because it is the one thing both readers see: the mover's oneWayMask raycast and RoomReachability.CollectGeometry. A cell on OneWay blocks a downward crossing of its top edge by feet that started at or above that edge — you land on it, you jump up through it from below, and down + jump drops you through. In a .room drawing it is the - glyph — the full character vocabulary lives in Documentation/ROOM_STANDARDS.md §3b, and RoomText.Glyphs is what every refusal message prints.

Two settings here are not preferences, and each shipped broken once. The platform map's CompositeCollider2D must be GeometryType.Polygons: the pass-through test is inside-ness, and the default Outlines builds edges with no interior, so a player mid-pass-through finds the bottom edge instead and lands on the collider's underside — hanging below the bar the art draws. And the Player prefab must actually carry a non-empty oneWayMask; a newly-added serialized field is not written into an already-serialized asset, so it deserialises to 0 and every platform silently becomes air. ShippedPlayerPlatformWiringTests pins both by reading the shipped assets — a hand-built rig proved the mechanism and shipped the bug twice. PlatformEffector2D cannot be used: the mover is kinematic and resolves collisions with Physics2D.Raycast, and raycasts do not consult effectors — while enemies are solver-driven, so an effector would be one-way for enemies and solid for the player.

Sockets

A RoomSocket is just side (Left=0, Right=1, Up=2, Down=3) + cell (int). Apertures are 3 cells and authored open — no tiles in the doorway. The generator butts rooms edge-to-edge and aligns L↔R apertures on the same floor row; there is no carving. s.cell + 3 must stay inside the room bounds or the validator errors. Every socket must also be cappable: a straight 3-cell opening in a flat wall/floor/ceiling run, so the biome's socketCap prefab can seal it when unused.

Up sockets are a promise. A Down socket is always traversable (you fall through it). An Up socket only counts as an exit if the room internally terraces up to it in ≤2 u steps — that is the author's responsibility, and the reachability audit (§4) is what catches you when you break it.

Markers and fixtures inside a room

  • EnemySpawnMarker — on floor cells with ≥3 u clearance; red wire-sphere gizmo. Fields: overrideTable (e.g. a guaranteed elite), deferToSequence, isBossPoint (§8).
  • EntryPoint — a named child in Entry rooms (and stand-in / rest layouts); the player teleports here.
  • BiomeExit — the exit fixture in Exit rooms.
  • BossGate / BossDoor — arena and corridor components (covered with the boss beat on Enemies & Bosses).
  • Hazard (Pit) — an explicit trigger volume spanning a gap floor, ≥2 u below the lip. There is no fall damage; a pit only kills because you put this volume there.
The debug pool is not run content. Anything under a path containing /Debug/ is skipped by the reachability audit (if (path.Contains("/Debug/")) continue;), and the validator only walks content reachable from the RunPlan — so Assets/_Game/Biomes/Debug/ (Biome_DebugPool.asset, SpawnTable_Debug.asset, Room_Debug*) never gates builds. Nothing in code references Biome_DebugPool.asset; it's a manual sandbox. Experiment there freely.

The recipe

  1. Duplicate an existing Room_Ember_* prefab in Assets/_Game/Biomes/Emberfall/ (or a Room_Fan_* / Room_Slip_Ember one in Assets/_Game/Biomes/Fan/ if you are adding a fan storey or a slip-away) — or build fresh: root GameObject + RoomTemplate, child Grid with Floors + Walls tilemaps, each with a TilemapCollider2D, and each on layer Level (a Platforms map goes on OneWay — §02). A tilemap made through Unity's menus lands on Default, and the layer is the only thing the mover's collisionMask reads, so the room is air to the player — while both gates still pass it: the audit files every non-OneWay collidable map as solid whatever its layer, and the validator's layer pass only checks the platform layer. Duplicating inherits the right layers; building fresh does not.
  2. Paint greybox-first with Assets/_Game/Biomes/Greybox/Tile_GreyFloor / Tile_GreyWall (full-cell ColliderType.Grid — the collider is exactly what you see). Painted content must begin at cell (0,0) and the tilemap grid must not be offset from the room root — both are validator errors. Art tilesets come later on a separate collider-less layer over the same greybox collision; never collide on art sprite shapes.
  3. The footprint calculates itself from the paint; sizeInCells self-stamps in OnValidate. Nothing to type.
  4. Add sockets on the RoomTemplate: side + cell (L/R cell = floor row of the 3-tall aperture; U/D cell = leftmost column of the 3-wide one). Leave the doorway open — no tiles. Check the cyan gizmo lines up with the hole, and keep cell + 3 inside bounds.
  5. Tag it. Entry ⇒ R socket + EntryPoint child. Exit ⇒ L socket + BiomeExit. Boss ⇒ L+R + BossGate + exactly one isBossPoint marker. BossCorridor ⇒ L+R. Branch pieces follow the grammar in §7: riser = Down+Up, corner = Down+Right, terminal = Left only — tag terminals Treasure (payout) or Secret (bypass-door home).
  6. Place EnemySpawnMarkers on floor cells with ≥3 u clearance.
  7. Join the pool. Normally the room name already matches the biome's INI glob (roomPool = Room_Ember_*) — just re-run Gleamwood ▸ Import Content INI. Explicit pools (pyre-crown) need the name added by hand.
  8. Prove it: Gleamwood ▸ Audit Room Reachability, then Gleamwood ▸ Validate Run Content. Both clean or the room isn't done.
The fix-tile rule: "When placing fix tiles: never within 2 columns above a platform edge that must stay mountable — the tile blocks the jump arc."

04The reachability guarantee

A room is judged by simulating the real controller over your tiles. It refuses one thing only: a trap. If you can arrive through a door and reach no other door — with every ability unlocked — that is a dead run and the room is thrown out. Everything else is reported, not refused.

A door you cannot reach is not a bug — it is the point. Gating is per CONNECTION (RoomTemplate.RequiredForPath(from, to)), not per room. A room's ground-floor corridor can be a stroll while its ceiling door needs a wall jump; only the ENTRY-TO-EXIT journey the layout actually routes has to be walkable with the abilities the run currently holds. The door above you that you cannot take yet is what an earned ability is for. Judging the whole room instead once deleted the pool's only junction and left the player in an empty scene.

Where it lives

FileRole
Systems/Run/Rooms/RoomReachability.csThe movement model and the flood. Runtime assembly, because a campaign's .room drawings must be proved walkable on a player's machine, where no AssetDatabase exists.
Systems/Run/Rooms/RoomAudit.csTHE verdict — one implementation, three callers: RoomBuilder (campaign text rooms, at load), RunContentValidator (editor + build gate), and the menu. Two opinions about "is this room broken" is how a room once became shippable at runtime and unshippable at build time.

The movement model

The flood's state is (x, row, vertical velocity, dash cooldown) — not a cell. Three earlier versions tracked position alone and every one was wrong, because arriving somewhere at terminal fall speed and arriving there standing still lead to different places.

RuleWhat the model does
NumbersRead from PlayerSettings.asset at audit time, never from the C# field initialisers — the tuned asset and the defaults disagree on values that decide rooms (DashCooldown 0.2 vs 1.0, DashDuration 0.4 vs 0.2).
SolidEvery cell with a tile on any child Tilemap carrying a TilemapCollider2D — the union, so a seam between a Floors map and a Walls map is still solid.
The bodyThe real collider box, 0.565 × 1.328, swept over every cell column and row it straddles. Narrower than a cell, so it can span two columns — which is what catches a corner tile the head hits.
The latticeRows are integer sub-cells (cellQ = 2 for the shipped tuning, so half-cells). One step is the time to cross one cell at MoveSpeed. Per step the body moves vy − 1 rows and velocity loses 2 — exact integers for any tuning, so the model never drifts on floating point.
JumpA launch velocity, not a fixed rise. Both a held launch and a tapped launch are tried, so a full jump that would not fit under a ceiling does not block the move. Horizontal freedom is ±1 cell per step with free mid-air reversal — what bounds the reach is time in the air, not a lateral constant.
FallingAccelerates until terminal speed, which slows the fall and therefore makes a long drop carry further horizontally. Swept, so it cannot tunnel through a corner.
Wall jump (ability)Any airborne position whose feet touch solid on either side is a launch pad, repeatably against the same face — nothing tracks a wall identity or a count. So one wall is a ladder and a shaft is climbable without terracing.
Dash (ability)Air-capable, cancels gravity outright, and chains — which is exactly why the cooldown is carried in the state. Without modelling it, dashes would chain every step and a gap of any width would read as crossable.
ClearanceThe player is 2 cells tall, so a 1-cell gap is still a wall — and now it is reported by coordinate rather than left for you to find.

Running the audit — and reading what it says

  1. Run Gleamwood ▸ Audit Room Reachability. It sweeps shipped prefabs under Assets/_Game/Biomes (skipping /Debug/) and every campaign .room text drawing — each installed Mods/<id>/Campaign/Rooms/ plus Documentation/ExampleMod. Before this, an author drawing a room got no editor feedback at all.
  2. It closes with N room(s) checked — E refused, W that read wrong, N door(s) behind an ability. Errors are clickable: the context object is the prefab.
What it saysWhat it means
refused (error)A trap: "entering by Left@1 leaves the player with no way out". Judged with every ability unlocked, so it means the geometry is broken rather than merely locked. This is the only thing that fails a build.
reads wrong (warning)"N stretch(es) of floor with only 1 cell of headroom: (3,8)-(3,8)…". Legal, but the art draws a passage where the geometry has a wall. Raise the platform above it by one, or fill the gap in so it reads as solid.
behind an ability (note)"Left@1 -> Up@2 needs wall jump". Working as intended — the room is still offered; the layout just will not route the main path through that door until the player can take it.
"Reads wrong" is three different sweeps, and each gets its own sentence. RoomAudit splits the flood's warnings by kind — on SealedPrefix and LipMarker — and emits one message per kind, worded with the fix that actually applies to it: a headroom stretch ("raise the platform above them by one"), an overhang lip ("raising a platform does NOT fix this — clear the cell ABOVE the opening"), or floor no door can reach ("this is not a headroom problem"). Labelling all three as headroom is what it used to do, and it sent an author with a sealed chamber hunting for a headroom problem that was not there. The three sweeps are:
  • ReportLowClearance — "(3,8)-(5,8)": a run of floor the 2-cell-tall body cannot walk along. Grouped into runs, so one low ledge is one message rather than one per column.
  • ReportOverhangLips — "(14,5) heading right — (15,5) is open but (15,6) is not": somewhere you can walk to and try, where the head ends inside a shelf and you stop dead in front of a whole cell of visible air. Reported from the cell you are STANDING on and the direction you tried, because the blocked cell on its own is not findable.
  • ReportSealedAir — "sealed floor no door reaches: (7,2), (8,2)…": standable cells no socket's flood ever reaches. A secret behind a wall is deliberate, which is why this warns; what it catches is the other kind — a room whose author believes they drew a route.
In all three the blocking test reads solid only — a platform overhead is not a ceiling, because you can rise through it. So converting an overhang into a one-way platform makes its warning disappear as the fix lands, rather than needing to be suppressed. (One-way cells still count as something to stand ON.)
You rarely run this alone. Gleamwood ▸ Validate Run Content runs the same auditor over every pooled room, and the build gate turns its errors into a failed build. The standalone menu item is for iterating on one room fast — and it is the only one that also reads your .room drawings.

06BiomeDefinition — the biome's knobs

One asset per biome under Assets/_Game/Biomes/ (create: Gleamwood/Biome Definition, or let the INI create it for you — §10). Edit it in the Workbench's Levels category, which also checks the run plan references it.

Read the topology row first — it decides which generator builds the level, and the field's default is not what ships. LayoutTopology has three members: Chain (the left-to-right spine with dead-end spurs, §7), Lattice (a rolled grid of columns and bands that can carry LOOPS, §7b) and Branching (a trunk, a vertical fan column, and one path per storey, §7c). Chain is the enum's zero, so a biome asset with no key deserialises to it — but every one of the ten shipped biome assets sets topology: 2, which is Branching. What each member promises is documented on LayoutTopology in BiomeDefinition.cs.

The generator walks DOWN this list until one fits your rooms, so asking for more than your pool can build costs a log line, never the level.
genRules.branches · pathRoomsMin / pathRoomsMax · bandHeight4 · 4 / 6 · 20Branching only. How many paths the level offers including the boss road (1 is legal and means a forced-boss level with no way to skip the fight); how many rooms ONE path owns east of the fan column, inclusive — the boss path spends part of that budget on its corridor and arena; and how tall one path's band is in cells. bandHeight must exceed the tallest room in the pool or nothing can be placed, and the slack above the tallest room is exactly how much vertical jog a path is allowed. These defaults were measured, not chosen — the sweep that picked them is written out beside the fields in BiomeDefinition.cs. Depth, salt, and why merges never get easier

  • DepthOf(nodeId) = the longest path from entry (relaxation, guard NodeCount+1). Depth drives stat scaling and spawn-table minStage gating — "a lane merge never makes the game EASIER". Bypass edges count for depth too.
  • NodeSalt = FNV-1a StableHash(nodeId) — two same-biome nodes generate different layouts. string.GetHashCode is explicitly not used; saves depend on stability.
  • The generator itself is pure and deterministic: Generate(runSeed, stageIndex, biome) with System.Random(HashSeed(seed, stageIndex)) — same inputs, identical plan, forever. Suspend/resume re-generates instead of serializing layouts.

How the chain is assembled

The rest of this section describes the Chain generator specifically. No shipped biome asks for it today — every one of them sets Branching (§7c) — but it is the oldest of the three, the one with committed determinism goldens, and the vocabulary the other two are described in contrast to.

Entry at origin → middles → BossCorridor (only when an arena is also in the pool — "a corridor without an arena is never placed") → Boss arena → Exit. Each link picks the previous room's R socket and the next room's L socket (random among same-side sockets) and offsets so the floor rows align — rooms butt edge-to-edge, no carving. With probability verticalJogChance the generator prefers a middle whose L-socket row differs from the previous R row. When a boss is present and calmRoomBeforeBoss is on, the room directly before the first boss piece is the calm room (never the entry) — its spawn markers are deactivated at assembly.

Branch pieces come from untagged pool rooms (Entry/Exit/Boss/BossCorridor are excluded). Every placement is overlap-tested against everything already placed; a branch commits whole or is discarded whole — "fail-soft: fewer branches, never corruption". Branches append after the chain so chain indices (calm/boss/exit) never move. A pool without corners or terminals is quietly linear. Every unconsumed socket becomes a cap — including U/D sockets that never grew a branch. Branch links (fork ↔ riser ↔ corner) are the only vertical room connections; the main chain itself never links vertically.

Junctions, bypass doors, and the coward's road

  • Placement preference ("the slip-away is earned"), and it lives on the plan rather than at the call site: a Secret-tagged pocket → any pocket → the calm room → the room deepest from the entry. Only when even that finds nothing does it error — "the layout offers nowhere to put it — no pocket, no calm room, and nothing reachable that is not a way out." The door spawns at room center X on the anchor socket's floor row, labeled Slip away → {title} (no rest, no spoils).
    A pocket is a room of degree ≤ 1 that is not the entry and not a way out — derived from the layout's edges, never from "the rooms a branch appended". That is what makes the rule work on a lattice ring and a Branching fan as well as on a chain spur: nothing populates the chain's branch list on those paths, so every ring used to reach the old error instead of a door. One implementation, two callers — the host that spawns the door and the minimap that marks it (§9) — because they had already drifted apart.
  • Rules: BypassTo is legal only mid-biome and only to the current node's bypassNextId. Carried health is captured as-is — "no heal, no forge; the price of not fighting" — and you go straight to the next biome: "no rest on the coward's road".
  • At the rest: a single next means a plain walk-over RestExit. A fork means RestHost hides the RestExit and assigns one pooled PathDoor per next id, labeled "→ {biome displayName}"; interacting calls AdvanceTo(nodeId), validated against the current node's exits. Too few doors: loud error + fail-open (the RestExit stays on and the run continues down exit 0). Extra doors deactivate.
  • Saves: the run is saved at the entry of every room (SuspendAtRoomEntry, both hosts; the RestSite re-saves after the heal). The save carries seed, nodeId, path, atRest, health, stats, weapons. Resume re-enters the room from scratch; pre-M5 saves invalidate by design — wipe, never migrate.
  • Treasure: each Treasure-tagged pocket gets the biome's branchTreasure at room center, floor row + 0.6. On a layout with a cycle and no pocket at all, the room deepest from the entry gets it instead — and that fallback is deliberately withheld from trees. On a tree, no pocket means the level grew no side content, and the deepest non-exit room of a chain is its boss corridor: the one room every run is forced through, so "somewhere out of the way" would invert into "on the critical path". Measured on the shipped pools, 58–83% of seeds across the five biomes that existed when the sweep was run have no pocket, and every one of them resolved to Room_Ember_BossCorridor. Ten ship now (§7) and the sweep has not been re-run. The figure is very likely still the right shape — nine of the ten run-content biomes carry an identical 22-prefab roomPool, and only pyre-crown's differs, so there is little new geometry for the pocket rate to have moved on — but treat the range as historical rather than current until somebody re-measures it over the ten. A ring has no dead ends by construction, so having none says nothing about whether the level deserves a reward — and paying nothing there is exactly how every ring generated so far paid out nothing at all, silently.
The bypass triangle: a node with bypassNextId needs (1) its id resolvable, (2) the biome's calmRoomBeforeBoss ON — otherwise "the junction door has no room to live in" — and (3) a BypassDoor prefab in Resources. The validator enforces all three; the audit (§4) keeps the pockets it prefers actually reachable.

07bThe lattice — levels that loop

Everything above builds a chain: a spine left to right, with spurs that go up, turn once and dead-end. Set genRules.topology = Lattice and a second generator takes over — one that lays rooms on a rolled grid of columns and bands, and can close a loop.

Why a grid, and not "let branches try to rejoin"

In the chain, a room's position is solved from its parent's socket — so where a room ends up depends on the path taken to reach it. That makes a tree free and a cycle nearly impossible: two paths into the same room have to agree by luck, and with arbitrary room sizes they essentially never do. Fix the grid first and the dependence disappears. A room's position becomes a function of its slot, both paths compute the same coordinates, and every cycle closes by construction — no search, no backtracking, no retries.

The door discipline, and it is not a preference. A lattice room puts its Left/Right doors on row 1 and its Up/Down doors on column 2. Row 1 because a door on row 0 has no floor under it (the text parser refuses it outright), so row 1 is the only row every band height can offer. Column 2 because it is the smallest offset that still leaves a wall cell either side of a 3-cell opening in the narrowest room the grammar allows. Matching cells are what let any two rooms mate — which is the whole mechanism by which a cycle closes for free. A pool that violates it is refused with a message naming the row and the column.

The three tiers

Where the loop pays out

A closed ring has no dead ends — every room has two ways out — so nothing on it reads as "somewhere you went out of your way to find". That is why a Stack matters beyond its shape: the top of its shaft is the first pocket a looping level has. Treasure and the slip-away door both read the layout's graph now (BiomeLayoutPlan.TreasureRooms / BypassRoom), preferring a real pocket and falling back to the room deepest from the entry only when the layout genuinely has none.

Turning it on

The shape is a text-only key — but both text surfaces read it. topology and latticeTier are parsed by CampaignPlan's [Biome:] block (a Mods/<id>/Campaign/ file) and by Gleamwood ▸ Import Content INI — ContentIniImporter.ApplyBiome has a case for each, and a value that is not a member of the enum is an error that names the members. topology is now the first row of that form too, since it decides which of the other dials do anything; latticeTier appears alongside it once the topology IS Lattice. Both were text-only until 2026-08-12. Know also what the shipped game asks for: every one of the ten run-content biome assets serializes topology: 2 — that is Branching (§6), not Lattice — and only the sandbox Debug/Biome_DebugPool.asset is outside that, carrying no topology key at all and so deserialising to Chain. So nothing the base game runs builds a lattice today, and the worked example below is the only place one is written down.

A complete, commented worked example ships in Documentation/ExampleMod/Mods/example/Campaign/RunWeb.ini — uncomment the block. The ten lat-*.room drawings beside it are the alphabet: lat-junction (the spine room an arc leaves from), lat-arc-start / lat-arc-end (its two ends), lat-crossroads (the through-room) and lat-pocket (a dead end to hide a reward in), plus straights and tagged ends. Read lat-junction.room to see per-connection gating in one file: you can walk it left to right with nothing, and its ceiling door needs a wall jump.

07cBranching — the shape the game actually builds

This is the topology every shipped biome asks for — all ten Biome_*.asset files serialize topology: 2. §7's chain and §7b's lattice are both real generators with real tests; neither is what a run walks through today.

A trunk runs east from the entry. A vertical fan column stands at its end, one storey per band. One eastbound path leaves each storey. Path 0 continues the trunk's own band and carries the boss corridor, the arena and the biome's Exit room; paths 1..n−1 end in SlipAway rooms, which are ways out too. Every path ends in a room you can leave by, which is the whole design in one sentence — the route choice moved inside the level, instead of living only at the rest's path doors.

Overlap is PREVENTED, not detected — and that is why this generator exists at all. The chain grows a side branch by placing rooms and testing each against everything already down, discarding the whole branch on the first overlap. That is the right trade when a branch is optional treasure: fewer branches, never corruption. It becomes the wrong trade the moment a branch is the only way to reach one of the node's destinations — a discarded branch is then a destination the player can never get to, and nothing downstream can tell it went missing.

So paths do not compete for space. Path k owns y ∈ [k·H, (k+1)·H) and nothing else may enter it, which makes overlap impossible by construction rather than caught afterwards. The cost is paid in vertical drama: a band H tall holds a room h tall anywhere in [floor, floor + (H − h)], so the slack above the tallest room in the pool is exactly how much jog a path is allowed — bandHeight 20 against a 16-tall pool leaves one 4-cell step.
The band is a filter on the DRAW, never a retry. Ask whether a band admits a room before choosing it, not after placing it. A generator that places and then rejects consumes RNG on the rejected attempt — and a fixed seed has to keep producing the identical layout forever, because suspended runs are re-generated from (seed, nodeSalt) rather than serialized. A shifted draw moves a player who is standing in the old level.

What your pool must supply

The alphabet is the tightest constraint on this topology, so the buckets deliberately overlap: a room with Left, Right and Up is both a middle and a fan base, and forcing it to choose would shrink an already thin pool. (The chain's partition is an exclusive else if ladder; this one is not.)

The budget, and why the tail is decided first

  • genRules.minRooms / maxRooms size the trunk — at least one room between the entry and the column, and the last of them is drawn under an extra filter so the column's base can actually stand on band 0's floor. A trunk that cannot satisfy it is a loud failure rather than a column floating half a band up.
  • genRules.branches is clamped to what the pool can carry. Asking for more costs a log line, never the level.
  • pathRoomsMin / pathRoomsMax are what one path owns east of the column, inclusive — and the boss road spends part of that allowance on its corridor and its arena, so its walkable middles are what is left rather than the whole budget.
  • The whole path is declared before the first room is placed. Every step then refuses any placement from which the rest of the list could not be laid down — which is the difference between a filter that is locally correct and one that is actually a guarantee. Deciding the tail as you arrive at it is how the boss road walks into a corner with 12 cells of headroom and an arena still to place.
  • A socket is marked used at the moment something connects to it, never on intent. So a path that stops early leaves its last door unspent, CollectCaps seals it, and a broken level is still a level you cannot fall out of. Marking on intent is how you get a hole in a wall.
It shares no code path with the chain — its own pool partition, its own placement loop, and that is the point rather than duplication. Suspended runs are re-generated instead of serialized, so any edit to a generator can move a player who is standing in the old level; the cheapest way to guarantee a new generator cannot do that is to leave the existing one's bytes literally untouched rather than carefully preserved. BiomeGeneratorTests' committed goldens are what would catch it if that ever stopped being true.

Where the payout lands is not this generator's decision: treasure and the slip-away door both ask BiomeLayoutPlan for a pocket, exactly as a chain or a lattice does (§7). A fan level's pockets fall out of its edges like anyone else's.

09bThe room decides the zoom

A room's shape is a camera instruction. The host hands CameraFollow the world rects of every stitched room (SetRoomRects, read off each RoomTemplate), and the camera eases its orthographic size out to fit the height of the room the player is standing in. Walk into a drop shaft or a climb and the view opens up to show what is below and above — with no geometry probing at all. Scenes with no room rects (Hub, Rest) simply stay at base zoom.

They are on the CameraFollow component (Assets/_Game/Systems/Mechanics/CameraFollow.cs) under Room Zoom, and live on the F1 panel's Camera tab in play mode.

The PixelPerfectCamera is switched OFF while zoomed away from base — it owns the orthographic size whenever it is enabled, so the two cannot both be right. It is re-enabled the moment the camera returns to base zoom. If you are chasing a pixel-snapping artefact that only appears in tall rooms, this is why.
Bounds are inset live, never at load. SetBounds takes the layout's outer rect and the camera insets it by its current half-view every frame. The previous design baked the inset once at load from the serialized ortho size — which the PixelPerfectCamera then changed at runtime, over-insetting by several units and cutting the edges off the level. When the rect is smaller than the view on an axis, the camera locks to its centre there.

Two other guarantees the room author can rely on: a keep-in-frame leash clamps the player to within halfView − keepInFrameMargin of the frame centre, so no fall outruns the camera however deep the shaft; and a teleport safety net snaps rather than pans when the target moves more than a screen in one frame (pit respawn, room entry).

  • Safety net: an unresolvable asset name is an ERROR and the field is left untouched — "a typo in the INI must never silently wipe existing wiring". - is the explicit "clear this reference". Unknown sections/keys warn; last write wins within a section; ; starts a comment; bools accept true/1/yes and false/0/no.
  • roomPool values are comma lists of exact prefab names and/or trailing-* prefix globs over RoomTemplate prefabs, resolved into a name-sorted set. An entry matching no prefab is an error.
  • Shipped tunables: deliberately not listed here — every biome's numbers are its own [Biome:…] block a screen further down the same file, and a copy on this page is a copy that goes stale the next time one is retuned. What is worth knowing is the file's shape: every biome the run visits sets topology = Branching with its own path budget, and every one of them globs the same pool except pyre-crown, which spells its list out in order to swap in Room_Crown_BossArena ("the one with the dormant fire columns").
Re-glob with care: pool ORDER feeds the seeded generator, so re-globbing roomPool can change layouts for old seeds; resumed runs re-generate from the current pool (acceptable per M2 — but know that it happens).
