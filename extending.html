Extending the Game

The seam catalog: every place the codebase accepts new mechanics and content without touching core code — each attribute, registry, discovery hook and load contract, one worked example that ships a mechanic in a single file, and the recipes for adding seams that don't exist yet.

01How this game grows — attributes declare, editors discover

The extensibility thesis is one sentence: you declare, the editors discover. New content types tag themselves with an attribute; the Content Workbench, the F1 panel, and the validated dropdowns find them by reflection and grow their own UI. You never register anything by hand and you never edit the tools.

Declare

Put [WorkbenchCategory] on a class, [WorkbenchField] on a field, [Tunable] on a number. Attributes are markers — zero runtime cost.

Discover

TypeCache and reflection sweeps find your declarations. Only three consumer surfaces exist — the Workbench, TunableTabs, and the two dropdown drawers — and only they ever need edits, and only for genuinely new kinds of seams.

Validate

Every content contract that would fail silently at runtime — magic state names, catalog registration, reachability — has a validator check that runs from the menu, after every INI import, and as a build gate.

Behavior of the generic form (WorkbenchGenericForm.Draw) switches on whether you curated:

  • Any field tagged → curated mode: only attributed fields draw (reflection over public and non-public instance fields), grouped by section. Untagged fields hide — that's your "internal scratch fields stay invisible" lever.
  • No fields tagged → every serialized field draws, with a footer tip suggesting you add [WorkbenchField].
  • AudioClip fields always render as a sound row with a preview Play button, both modes.
  • Property drawers on your fields — [AnimatorStateRef], [EnemyStateNameRef] — apply automatically, because the form goes through EditorGUILayout.PropertyField.

[Tunable] — F1 debug panel by declaration

  • Ctor: TunableAttribute(string tab, float min = 0f, float max = 1f), on a field or a property (give a property a clamping setter — the slider cannot then push it out of range). A new tab name creates the tab on demand; Section, Label, Tooltip, OnChanged and Save are the named extras.
  • Types: bool → toggle, float/int → slider. Anything else logs unsupported type and draws nothing.
  • A gameplay value declares Save = false. Save = true writes the number into the tracked DebugSettings.json, which the panel re-applies at boot over whatever the serialized asset holds — so retuning the asset appears to do nothing, for a reason three directories away. TunableParityTests pins it.
  • The declaration boundary: PlayerDebugUI.ConfigureTabs() builds Movement / Jump / Dash / Wall Slide / Hitboxes / Impact 100% from declarations; Camera, Troubleshoot, Run Cheats and Debug Info stay hand-built, because they bind scene components and read-only lambdas that no declaration can express (the last two behind #if UNITY_EDITOR || DEVELOPMENT_BUILD).

Every control on the panel, the save-key grammar, which host supplies which Impact row, and the session clone an F1 edit lands on are on Tuning & INI §02 through §05.

[AnimatorStateRef] / [EnemyStateNameRef] — string fields that can't drift

AnimatorStateRefAttribute(int layer = 0, string emptyLabel = "default"); [EnemyStateNameRef] takes no arguments. Both fields stay plain strings at runtime, so they cost nothing outside the editor — and any string field you add gets the same treatment by tagging it, which is this page's whole point.

The drawers are documented once, on Workbench §11: the clip-set-first rig resolution (the AnimatorController is a legacy fallback, not the primary source), the red [MISSING] flag, the [T] raw-text toggle, the create flow that no shipped field reaches, and the full inventory of tagged fields for both attributes.

03Discovery machinery & load contracts

Two mechanisms carry everything above: TypeCache finds your code — four sites, and none of them has a registration call to add yourself to — and Resources.Load finds your assets by name, on keys that are shipped API.

04Registries & data tables — where content gets wired in

A new asset that isn't in a registry doesn't exist as far as a run is concerned. These are the tables that make content reachable. (The fifth registry, TunableRegistry, is the F1 panel's runtime opt-in list — Register(this) in Awake/OnEnable, Unregister on teardown; it is not a data table, and its contract is in §02.)

WeaponCatalog — Assets/_Game/Systems/Run/Weapons/WeaponCatalog.cs

FieldMeaning
defaultMelee / defaultRangedThe starting loadout; implicitly resolvable even if omitted from weapons
weaponsWeaponDefinition[] — every findable weapon must be here
defaultTrackThe shared UpgradeTrack (forge stat curve)

ResolveShipped(string weaponId) matches by asset name (def.name == weaponId) across weapons plus the two defaults. That makes weapon filenames save data: stable once shipped — renaming breaks player saves, and the validator guards the list. Resolve() is the same lookup that then falls through to a [NewWeapon:] mod weapon, so a save holding one resolves on resume instead of silently reverting to the default; the two are kept apart so a mod variant's basedOn (which must name a shipped donor) can never recurse into the mod registry.

LootTable — Assets/_Game/Systems/Run/Weapons/LootTable.cs

Entries are { WeaponDefinition weapon; float weight = 1 }. Roll(rng, exclude) is weighted and exclusion-aware; a null result = an empty pedestal. Convention: keep a table single-type — one melee pool, one bow pool. The validator hard-errors any loot entry the catalog can't resolve ("picks would not survive suspend/resume").

Two things the roll does beyond weighting, and both are in Qualifies/ModEntries rather than anywhere else:

  • The meta-unlock gate lives here, at OFFER time. An entry only qualifies if RunDirector.IsWeaponUnlocked(e.weapon). A locked weapon stays in the table — gating in WeaponCatalog.Resolve instead would mean a saved run already holding that weapon failed to restore it.
  • [NewWeapon:] mod weapons join the same weighted roll, type-matched against the pool's own type (read off its first shipped entry) so a bow pool never starts offering blades, and gated by the same unlock check. When nobody mods weapons the whole cost is one WeaponVariants.Count == 0 test.

DynamicCondition — the no-code transition seam

One asset (Assets ▸ Create ▸ StateMachine ▸ Dynamic Condition) gates a transition on any context value: set PropertyName (a property on the Context type), a DynamicOperator (Equal, NotEqual, Greater, Less, GreaterOrEqual, LessOrEqual, IsTrue, IsFalse), and a FloatValue or BoolValue. It compiles to a cached expression-tree predicate at runtime; a compile failure logs an error and the condition returns always-false.

Gotcha: PropertyName must be a property on the context type, not a field. A field name compiles to nothing and the transition just never fires.

Executions & statuses — the combat gate seam

ExecutionDefinition (menu Combat/Execution Definition) gates finishers on RequiredDamageType, MustBeAirborne/MustBeGrounded, and RequiredStatus + MinStatusCount + ConsumeStatusOnTrigger. The status pipeline: WeaponDefinition.StatusesToApply puts a CombatStatusDefinition (StatusName, DecayTime = 5, MaxStacks = 10) on the target on hit, and that stack count then does three things: it gates executions, it ticks DamagePerTick damage every TickInterval seconds, and it removes SlowAmount of movement speed — the last two since 2026-08-18, both multiplied by the count, both on enemies and the player alike. And a stack gates an FSM edge through the status condition (status Ignite >= 2), so "enrage while burning" is now authorable in the Workbench and in a mod’s [Graph:] text alike. The note on MaxStacks that has always said "+ transitions" is finally true. ExecutionDefinition.CheckConditions and StatusCondition.Check are the two readers of CombatStatusManager.GetStatusCount in the game: StatusCondition is one of the eleven enemy transition conditions under Enemies/Code/Definitions/Transitions/Conditions/, and EnemyConditionCompiler's [Graph:] allowlist carries a status head, so both "execute when the target has 3 Ignite" and "change state when the target has 3 Ignite" are pure assets — no code. The one route still closed is a DynamicCondition: EnemyContext exposes no status count it could bind (its CombatStatus property is the manager object, not a number). What a player can SEE of a status is still a name and a count — OUTSTANDING "A status effect is unreadable".

06Worked example — ship a mechanic in one file

This is the canonical pattern. The HazardDefinition class is illustrative, but the exact pattern ships today on CombatStatusDefinition (Assets/_Game/Combat/Code/CombatStatusDefinition.cs) — that's the Statuses tab below, drawn entirely from these attributes with no editor code.

// One file, anywhere under Assets/_Game/. No other edits — no tool code, no registration.
[WorkbenchCategory("Hazards", Accent = "#4dd2ff")]

public class HazardDefinition : ScriptableObject

    [WorkbenchField("Feel", Tooltip = "Seconds between pulses", Note = "0 = single burst")]

}

07The validator & the INI importer — reference for the edit points

These two files are the pipeline: the importer turns text into assets, the validator refuses assets that would fail silently at runtime. They are a pair on purpose — the importer re-runs the validator at the end of every import, and the validator is also a build gate, so a rule added in one place fires from the menu, from an import, and from a build with no extra wiring. What follows is the reference for where you edit each of them.

Room traversal: one auditor, one verdict — and it is deliberately not "every door must reach every door". The verdict is RoomAudit.Audit (Assets/_Game/Systems/Run/Rooms/RoomAudit.cs), running over the flood in RoomReachability.Analyze (…/Rooms/RoomReachability.cs). Both live in the runtime assembly, because a campaign's text rooms have to be proved walkable on a player's machine where no AssetDatabase exists; only the sweep and the Gleamwood ▸ Audit Room Reachability menu stayed in Assets/_Game/Editor/RoomReachability.cs. Three callers share it: RoomBuilder (campaign rooms, at load), this validator (shipped prefabs, in the editor and at build), and that menu.

It errors only on a stranded socket — a door you can arrive through and then leave by no other, judged with every ability unlocked. That is a dead run. It warns on stretches of floor with only 1 cell of headroom (the player is 2 cells tall, so those read as passages and are walls). It notes, without refusing, which door pairs need which ability.

Why it stopped erroring on unreachable pairs: once gating moved to per-connection, a door the player cannot reach became a progression marker rather than a fault — "come back when you can climb". The runtime happily shipped such rooms while the editor validator still errored on them, and because Validate() feeds a build preprocessor that turns any error into a BuildFailedException, a deliberately marker-doored room was legal to play and impossible to build. Two opinions in the worst possible place. Movement metrics are read from the shipped controller (Metrics.FromPlayer() loads PlayerSettings), never from constants in the auditor.
The magic state-name registry. "dead" (auto-set by EnemyDeathConfig), "juggled" (EnemyJuggledConfig, used when CanBeJuggled), "hitstun" (EnemyHitConfig) — plus the "idle"/"chase"/"summon" next-state conventions. These names fail silently at runtime; the validator is where they get caught. Executions jump to GetState("dead") directly — a new enemy without it is unkillable.

The Workbench mirrors a few of these live as [ok]/[!!] badges — weapon-in-catalog, weapon-in-loot-table, enemy-in-a-spawn-table, biome-referenced-by-run-plan — all via an AssetDatabase.GetDependencies reverse lookup.

08FX & music seams

Both seams are "drop an asset in": every FX wiring point is a plain GameObject field and every music slot is an AudioClip field, and an empty one is silence rather than an error. Neither needs code.

Durability is a loop guard with a name, not a balance knob. An authoritative arrow has to remember who it has already struck or it re-hits the same enemy on every step of its sweep — and once that set exists, "how big may it get" is the same question as "how many can this pierce". 1 reproduces a clean single hit; 0 defers to the state config's SingleTargetHit, which is what every shipped bow does. Flight is bounded by LaneDistance regardless, so even an unbounded value terminates.
Audio rides the FX prefab. FX_HitSpark and FX_ArrowHit carry their own AudioSources — swap the clip on the prefab and everything referencing it follows. To make a new impact FX: build a prefab (particle + AudioSource), run Gleamwood ▸ Audio ▸ Create + Route Game Audio Mixer (idempotent — it sweeps every prefab AudioSource onto the SFX bus), then drop it into any field above via the Workbench.

Music — slots, per-biome, per-boss

MusicDirector auto-boots ([RuntimeInitializeOnLoadMethod], DontDestroyOnLoad) and crossfades between two sources on the Music bus. Every seam is "drop a clip in" — an AudioClip field on MusicSet.asset, on a BiomeDefinition or on a BossDefinition — and an empty slot is silence rather than an error. The fade lengths, the name-substring scene routing and the hazard in renaming a host scene are all on Audio, which owns them.

09Meta-recipes — adding a NEW seam

Verified end-to-end. Recipes 1–3 are declaration-only; 4–6 are the only places you edit tool code, and each is a single file.

Recipe 1 — new content type with full workbench support

§06's one file is this recipe — [CreateAssetMenu] + [WorkbenchCategory] + [WorkbenchField], with the rail tab, asset list, banner, save model, AudioClip preview rows and drawer support all following, and its escalation list covering F1 sliders, scene-free loading and INI authoring. Two things it does not cover. NewAssetFolder = "Assets/…/YourThings" on the same attribute is the whole opt-in for a New button on the tab, routed through WorkbenchAssetFactory.Create, which seeds id/displayName from the name you type and uniquifies the filename (§02). And an asset that must be registered somewhere before it does anything ships an IWorkbenchAssetCreatedHandler beside it (§03).

Recipe 2 — new Workbench tab

For a simple type, Recipe 1 is the whole recipe (see CombatStatusDefinition — one attribute, real). For a rich tab that needs sub-tabs, registration checks or cross-asset forms, implement IWorkbenchCategory and compose the page from WorkbenchForm primitives (form.Section, form.SubTabs, form.SoundRow, form.Registration…). The seven built-in tabs in Assets/_Game/Editor/Workbench/WorkbenchCategories.cs are the worked examples — the DialogueCategory is a good one to copy, editing three levels of nested arrays (beat → encounter → line).

Never edit ContentWorkbench.cs for a new type. The window is a shell that discovers categories — it has no per-type code. A new tab is a new [WorkbenchCategory] class or a new IWorkbenchCategory implementation; the window finds it automatically.

Recipe 3 — new F1 tunable tab

Name a new tab string in any [Tunable("MyMechanic", min, max)] — tabs create on demand. If the object isn't already passed to DebugUI.AddTabsFrom, also call TunableRegistry.Register(this) before the panel configures (Awake/OnEnable).

Recipe 4 — new validator check

  1. Open Assets/_Game/Editor/RunContentValidator.cs and add a static next to its siblings: 
    static void ValidateHazard(HazardDefinition h,
    System.Action<string, Object> error, System.Action<string, Object> warn)
{
    if (h.Damage <= 0) warn(h.name + ": damage 0 - hazard never hurts.", h);
}
  2. Call it from Validate() — or from ValidateBiome if your asset is reachable through a biome.
  3. There is no step 3. It now runs from Gleamwood ▸ Validate Run Content, after every INI import, and as the build gate — no extra wiring.

Recipe 5 — new INI key or section

  1. New key on an existing section: add a case "myKey": to the relevant Apply* switch in Assets/_Game/Editor/ContentIniImporter.cs, using the existing helpers — ParseInt/ParseFloat/ParseBool for values, AssignRef for asset references (it errors and leaves the field untouched on a typo). The default branch already warns on unknown keys, so old INI files stay compatible.
  2. New section type: add a section.name.StartsWith("MyThing:") branch in Import() pass 1 plus an ApplyMyThing(IniSection) method — copy the ApplyRest shape: FindAssetByName<T>, per-key switch, EditorUtility.SetDirty.
  3. Should the asset auto-create on import? Copy the ApplyBiome/ApplyBoss create path: ScriptableObject.CreateInstance + AssetDatabase.CreateAsset into your content folder.
  4. Extend the validator to cover it (recipe 4) — the importer already re-validates after every import, so your check fires immediately.
  5. Document the key on Tuning & INI's key table. The table is the contract.

Recipe 6 — new FX seam

  1. Build the prefab: particle + AudioSource, saved next to its siblings in Assets/_Game/Combat/FX/.
  2. Run Gleamwood ▸ Audio ▸ Create + Route Game Audio Mixer — the idempotent sweep routes your prefab's AudioSource onto the SFX bus.
  3. Existing hook? Drop it into any §08 field via the Workbench. New hook? Add a plain public GameObject MyEffect; field to the config and Instantiate it at the impact point in the state — copy the PlayerMeleeAttackState call site.

Recipe 7 — new enemy state verb

A new EnemyStateConfig subclass with CreateState() — the existing toolbox is Idle, Chase, FloatChase, AttackPhase, ProjectileAttack, Summon, Relocate, HazardPhase, GroundHazard, Hit, Juggled, Death, plus ExecutionPayoff. You inherit EnterSound from the base class for free; put [EnemyStateNameRef] on any next-state string and [AnimatorStateRef] behavior comes via AnimatorStateName. The Cat Splat State Machine ▸ Tools ▸ State Machine Creator can code-gen the boilerplate (with a self-registering menu path) — it writes the two .cs files and stops, creating no asset, so the config itself is made afterwards in the Workbench's + Create State, which is what sets StateName, adds the sub-asset and registers it in the definition. That is also the one place IStateMachineAssetPostProcessor implementations fire (§03). Details on Framework and Enemies & Bosses.

Recipe 8 — new spawn / loot content

Enemy: prefab into an EnemySpawnTable entry — root needs EnemyStateMachine + EnemyKillReporter, and the definition needs the "dead" and "hitstun" states. Weapon: into WeaponCatalog.weapons AND a LootTable. The Workbench Overview tab shows [ok]/[!!] registration badges for both, and the validator hard-errors loot-table weapons the catalog can't resolve.

10The safety rules — what keeps seams from becoming wounds

Six rules, stamped in code comments and enforced by tests and the validator. The first three are the ones that eat save files and playtests when broken.

Never mutate shared SOs at runtime

A mutated SO silently persists in-editor. Scale and modify context-side: EnemyStateMachine.ApplyStatScale scales the instance's context health, never the shared EnemyDefinition; RoomTemplate caches are [NonSerialized]; the F1 panel edits a clone of PlayerSettings — keepers must be transcribed into the asset. EnemySpawnerTests asserts the definition stays untouched.

Ids are save data — never rename shipped ones

BiomeNode.nodeId, BiomeDefinition.biomeId, DialogueSet.dialogueId, and weapon asset filenames (the catalog resolves by def.name). All carry "NEVER rename once players have saves" tooltips; the INI repeats it.

Stamp values on assets, not compiled defaults

The game reads assets only — C# field initializers are just fresh-asset defaults. The INI import writes into the SOs (SetDirty + SaveAssets); the same logic is why DebugUI save keys get a ...V2 bump when a default changes.

The INI is one-way

Editor-only import, never read at runtime. AssignRef errors and leaves the field untouched on a typo — the INI can never silently wipe wiring — and unknown keys warn, so old files survive schema growth.

Fail loud, or get validated

Magic state names and animator state names are silent no-ops in game — hence the dropdown drawers, the red [MISSING] flags, and the validator. An unreachable socket silently deletes the branch behind it — hence reachability analysis. The build gate refuses broken content.

Attributes declare, editors discover

Extending the workbench, F1 panel, or dropdowns is declaration-only. Only three consumer surfaces exist — ContentWorkbench, TunableTabs, the two drawers — and they only change for genuinely new kinds of seams.
