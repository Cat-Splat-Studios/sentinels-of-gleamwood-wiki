Modding Gleamwood

No Unity, no compiler, no account — a plain text file dropped next to the game. This page is the five-minute version; the three domain pages are the deep dives. Everything here is a player-facing feature that ships in the build.

01What you can change

A mod is a campaign: one folder under Mods/, beside the game's executable, with a mod.ini naming it. You pick a campaign when you start a new save, and that save is bound to it — exactly one campaign is ever active, so a campaign can never reach a vanilla save or anybody else's. Everything is applied to a private copy each run, so your files never touch the game's own — delete the folder and that save reports the campaign as missing rather than quietly becoming something else.

Mods/
  my-campaign/          <-- the folder name IS the campaign id
    mod.ini            <-- without this the folder is ignored entirely
    Enemies/  Weapons/  Dialogue/  Player/  Progression/
    Campaign/          <-- the run's shape
      Rooms/           <-- and your own rooms, drawn as text

This is what makes a campaign a campaign rather than a pile of retunes.§07 below
Where this is going: a campaign is a whole game. The destination is maker mode — Gleamwood becomes a 2D roguelite maker and ships as its own first campaign. Every seam on this page is judged against one question: if a campaign supplied all of it, would anything of ours still be load-bearing? That is why "can I change this?" keeps being answered with a text file rather than a plugin API, and why the folders above cover the run's shape, its creatures, its weapons, its voice, its look and its economy. Where the answer is still no, this page says so out loud rather than letting the maker-mode line read as delivered — see §08, where the moveset and the traversal abilities can be retuned but not extended, and §07, where a campaign can now declare a biome, a boss, a spawn table and its own music (all 2026-08-20) — and, since 2026-08-22, its own sound effects and menu blips too. The order in which those cells close is written down: Documentation/DESIGNER-HANDOFF-PLAN.md sequences vocabulary parity (its H5) and then maker mode with Steam Workshop (its H8), each item cited to the OUTSTANDING.md row that tracks it.

You never start from a blank page. Every build ships a complete campaign you can copy: Mods/_Templates/example-campaign/, holding a mod.ini plus one file per shipped enemy, weapon and conversation — with the real current values, correctly spelled, every line commented out. Copy that folder up into Mods/, rename it, delete the ; in front of one line, change the number. That is the whole workflow. (It sits inert where it ships — the game only looks one level under Mods/ for a mod.ini, so the template never shows up as a playable campaign.)

02Your first mod, in five minutes

Make the starting sword hit like a truck. Nothing to install.

  1. Find the game folder. The one with sentinels-of-gleamwood.exe in it — that name is pinned, because Steam's launch option points at a fixed path and a versioned executable would break it on every upload. Next to it is a Mods/ folder holding _Templates/example-campaign/. On a Steam Deck the same Windows player runs under Proton, and the folder is the same place seen from Desktop Mode: the game's install directory under ~/.steam/steam/steamapps/common/ (ModSet.ModsRoot is "the parent of Application.dataPath", wherever that lands). Nothing about a mod is Windows-only — the loader reads plain files — only the paths in this page are.
  2. Copy the example campaign. Copy Mods/_Templates/example-campaign/ up one level into Mods/ and rename it to my-campaign. Open its mod.ini and change name to whatever you want to see on the menu. Everything else is comments, so on its own it changes nothing.
  3. Uncomment one line. Open your copy's Weapons/DefaultSword.ini and find ; BaseDamage = 10. Delete the ; and the space, and change the number: 
    ; before
; BaseDamage = 1
; after
BaseDamage = 25
  4. Run the game. Start a new save and pick your campaign — the name you set in mod.ini — when it asks which campaign to play. A slot is bound to its campaign at the moment it is created and never again, so loading an existing save will not see your file at all. Then start a run and swing. The sword now deals 25.
  5. Check it loaded. Open the player log (see §04) and find the GLEAMWOOD WEAPON MOD REPORT block — it says what loaded and, if you fat-fingered something, exactly which line and why. The blocks print when the campaign ACTIVATES — the moment you pick it on the new save, not while the game boots — so look for them after slot selection (§04 has the details). The loader's own lines are there too — [Weapons] 1 weapon override(s) loaded from … and a [Weapons] warning per line it could not read — and the sword hitting for 25 is the proof.
Made a typo? A misspelled field or a value that is not a number is written to the log and then ignored — the weapon keeps its shipped value. One bad line can never break the game, and the report names it.

03Adding something new, not just retuning

The same files can DECLARE new content, built from an existing thing so it always works. A new weapon is the same type as its donor (a bow stays a bow); a new enemy borrows a shipped creature's animations, so it can never get stuck on a move that was never drawn.

; my-campaign/Weapons/frostbite.ini  — a new bow that sets things alight
[NewWeapon:Frostbite]
basedOn         = DefaultBow
; how often a pedestal offers it
weight          = 1
WeaponName      = Frostbite
BaseDamage      = 14
; a status, named
StatusesToApply = Ignite
; optional, from Weapons/sprites/
icon            = frostbite.png

; my-campaign/Enemies/glass_hound.ini  — a fast, fragile hound
[NewEnemy:GlassHound]
basedOn   = CinderHoundDef
MaxHealth = 3
tint      = #88ddff
weight    = 2

[NewEnemy:GlassHound.state:chase]
SpeedMultiplier = 1.8
Notes go on their own line — never after a value. In Weapons/, Enemies/, Player/ and Progression/ a ; only opens a comment at the start of a line. Written after a value it stays part of that value, which then fails to read and silently leaves the shipped number in place — the line looks perfectly reasonable and does nothing. (mod.ini and Campaign/ use a different reader that does strip a trailing ;, which is exactly how the habit gets picked up — see §07, where it is legal.) The rule is deliberate: a value may legitimately open with #, like tint = #88ddff. When a value will not read, the log now names this as the likely cause.
A declared enemy can go further than a variant. The [Graph:] tier lets an enemy declare its own states, transitions and attack chains in text — a genuinely new behaviour, still safe because it plays from a clip set that reports an unknown animation loudly instead of freezing. Weapons have no state machine, so they stop at "new weapon". Both deep dives cover the full grammar: Enemies §11, Combat §10.

04Did it work? Read the report

Every time a campaign ACTIVATES — you pick it on a new save, or resume a save bound to it — the game writes a short block per domain to its log; vanilla writes none, since there is then nothing to report. It is the fastest answer to "is my campaign loading". Wired since 2026-08-19 — see the note under the sample for where the blocks fire from.

======== GLEAMWOOD WEAPON MOD REPORT ========
folder : ...\Gleamwood\Mods\ashfall\Weapons
enabled: True   (build — always on)
retuned weapons : 1   [Weapon:...]
declared weapons: 1   [NewWeapon:...]
    OK  Frostbite            ranged, 14 dmg, icon, weight 1
RESULT: OK — 1 declared, 1 retuned.
=============================================
The three report blocks print when a campaign ACTIVATES, not at boot. GLEAMWOOD MOD REPORT, WEAPON MOD REPORT and PLAYER SKIN REPORT are each emitted by a LogIfModded() whose first line is if (ModSet.Active == null) return;, so they say nothing until a campaign is playing. They fire from CampaignSession.Activate, which is what the title's save-slot screen and a resumed save both go through — so you see them when you pick the campaign, not while the game is starting. A fourth line comes first: [Campaign] 'yourid' web accepted: N nodes, which is the one fact that says the campaign is playable (every other tier can be empty and the run still works; a refused web cannot). Vanilla prints none of it, so an unmodded player never sees a mod block.

They were unreachable between 2026-07-26 and 2026-08-19: the only call sites were in GameBootstrap.InitCore at BeforeSceneLoad, which runs after ResetStatics has cleared the active campaign and before anything can set one — so a pack that loaded cleanly and a pack whose every file was skipped produced identical output: none. The tests that touched the report called Build() directly and so never saw it, which is why ModReportReachabilityTests now goes through Activate instead.

Find the log at %USERPROFILE%\AppData\LocalLow\Cat Splat Studios\sentinels-of-gleamwood\Player.log (Windows). That second folder is the product name, not the title on the window — lowercase and hyphenated, exactly as it is spelled here. A line that starts FAILED or a message under -- N message(s) -- tells you the file, the line and what was expected.

Steam Deck / Proton. The Deck runs this same Windows player through Proton, so %USERPROFILE% lives inside the game's Proton prefix. In the standard Proton layout the log is at ~/.steam/steam/steamapps/compatdata/2953370/pfx/drive_c/users/steamuser/AppData/LocalLow/Cat Splat Studios/sentinels-of-gleamwood/Player.log (2953370 is the game's Steam app id; the prefix path is Steam's convention, so a non-default library folder moves the front of it), and Mods/ is beside the executable under steamapps/common/ as in §02. Both are reachable from Desktop Mode with a file manager.
Only object numbers, words and switches are text-moddable. You cannot name a projectile or an animation in a text file — there is no way to point at one — so those fields are not offered in the templates at all. Sounds left that list on 2026-08-22: a .wav in Campaign/Sfx/ is addressable by filename on any exposed sound field (§07). Artwork is the exception with its own route: enemies can bring a sprite sheet their animations are cut from (Enemies §12), and a new weapon can carry an icon.

05A worked example to copy

The repo ships a small, friendly pack you can read end to end and drop in as-is.

The editor and a build load mods differently

This is worth knowing before you trust a test: a build always loads mods; the editor loads them whenever a campaign is active, and the Simulate Mods toggles only force a domain on when no campaign is bound. Picking a campaign is already an explicit choice, so it needs no second opt-in — and without that, the editor would silently disagree with a build, the slot naming a campaign while the game played vanilla. The build branch is the one players hit, and it is the one a test pack exists to exercise.

06Reskin the player

A player skin changes the look of the game's moves. Select an owned-layer package or supply plain sprite clips; neither replaces the player state machine or combat rules. Movement tuning is a separate campaign tier, described in the tuning guide.

Layered appearance

; my-campaign/Player/emberknight.ini
[PlayerSkin]
; relative to this campaign's Player/ folder
layered = art/player.heroart

This loads my-campaign/Player/art/player.heroart at runtime through the same LayeredSpritePackageLoader used by Unity's importer. The gleamwood.layered-sprite.v1 package names its PNG relative to the manifest's folder and supplies canvas, pivot, pixels-per-unit, layer order, clocks, sequences and equipment variants. Both paths must stay inside their declaring folders. Import metadata and Unity .meta files are unnecessary in a campaign. A layered-only skin keeps the shipped gameplay clip set; drawing cadence and phase mappings belong to the package. See the artist guide for the shared viewer and drawing contract.

For simultaneous carried equipment, optional variantChannels entries name an id and a source of melee or ranged. A layer and its sequences use that same variantChannel; their variant values match the equipped weapon's layered appearance variant. Empty channels retain the original active-action selection. Each sequence may draw only its own channel's slots, so a sword swap cannot replace a bow or body layer. At most eight named channels are allowed. A multi-axis recipe can retain ordinary carry drawings through ascending, unique inheritOrdinarySlots; those slots use their own clocks and channels and cannot also be owned by the recipe's tables. All other omitted slots clear. The shipped player supplies both equipment inputs; individual packages must author the carry drawings and empty/unsupported variants explicitly.

A multi-axis recipe may also supply variantRequests, for example [{"channel":"melee","variants":["heavy"]},{"channel":"ranged","variants":["crossbow",""]}]. Channel IDs must be declared in variantChannels. All requested channels must match; any listed variant within one channel is sufficient. Matching ignores case. An explicit empty string matches an empty equipment slot; missing caller equipment does not establish that slot. Omit the field or supply an empty array for an unconditioned recipe; explicit null is invalid package syntax. Conditions are limited to eight unique channels and 1–128 unique variant names per channel. Existing selection order is preserved: the first matching exact active-action variant wins, otherwise the first matching common recipe. Put more specific conditions before their fallback at the same variant level. This selects compatible artwork for the supplied equipment; it does not enforce gameplay loadout restrictions.

Optional phaseMap arrays belong to sequences[], multiAxisRecipes[].axes[] or an axis's modes[]. Supply 2–32 [input, source] pairs from [0,0] to [1,1], with finite values within 0–1, strictly increasing input and nondecreasing source. Omitted, null or empty arrays keep native sampling. A selected mode owns its map and timing; an empty mode map does not inherit the axis map. With useElapsedSeconds, the supplied phase is first multiplied by clockDuration / selectedDuration, then mapped. The resulting source phase is multiplied by the selected duration before frame selection and clamping or loop wrapping. Without a map, elapsed sampling uses supplied phase × clock duration directly.

Equal source values create a hold: [[0,0],[0.7,1],[1,1]] reaches a nonlooping drawing's last pose at 70% and holds it. Input beyond the map end stays at source phase 1. A looping drawing wraps that endpoint to its first pose and holds there; it does not repeat the map. These mappings select drawings and attachment offsets without adding gameplay delays. An attachment axis following inherited body poses must use the body's matching native timing and phase map.

Optional smoothedClocks publish a normalized pose input through a named clock and clip. Each supplies an initialValue, defaultTarget, riseSeconds, settleSeconds and ordered targets. The first target whose clip/phase requests match selects its value. The player retains the input and smoothing velocity across clip and drawing-event changes; pause holds both, and a different appearance starts from its own initial value. Values stay within 0–1 and response times within 0.001–60 seconds. Smoothed clocks cannot share an autonomous/event output slot or depend on another smoothed output. These are pose parameters; an autonomous clock supplies elapsed cape phase separately. Packages must supply compatible drawings for the selected input ranges.

Optional motionClocks expose measured movement to drawing tables. Each record names a unique auxiliary clock (2–7), a clip, the supported source absoluteHorizontalVelocity, and finite increasing inputMin/inputMax bounds in world units per second. The player publishes Clamp01((measuredSpeed − inputMin) / (inputMax − inputMin)) with duration one. It reads actual horizontal velocity, including momentum after movement input is released. Missing context or nonfinite movement deactivates the input. These slots cannot overlap autonomous, smoothed or event outputs. An axis can use phaseMap to select bracing or starting drawings at authored speed thresholds without changing movement physics. Omission leaves older packages unchanged; the existing Art Viewer exposes the input for manual pose scrubbing.

The player's public CanComposePresentationClock, SetPresentationClock and ClearPresentationClock APIs let a gameplay caller publish a separate drawing input on a free auxiliary slot (2–7). The slot cannot belong to an autonomous, smoothed, motion or event output. A compatible recipe must explicitly request both the base mechanic and the caller's clock; a base-only recipe does not opt in. The caller supplies clip, normalized progress and duration, then clears the input when its context ends. Player reset, disable and appearance changes also clear it. This API does not add a package callerClocks field or play/retime a gameplay track: existing recipe requests and axes consume the input. The applied AirBow recipes use clock 6 for Jump/JumpApex/FallLoop while the base track aims, guarded to SteelStraight with Bow_Willow and level aim. They reuse the existing release event through FallLoop/Land; other equipment and aim contexts keep their established drawing paths.

Melee entry context. An opted-in melee recipe can request its base clip on clock 0 and MeleeEntry on clock 7. The latter has an empty phase, duration one and normalized value 0 for an opener or 1 for a chain/cancel. A nonlooping two-frame axis with fps: 2, duration: 1 and useElapsedSeconds: false selects between those entries. Authors decide which entry drawings fit their equipment. The state records the cause before playing each swing, holds it through recovery, and clears its owned input on the next swing or state exit. A shared recovery can use the base clock alone. Equipment conditions participate in the opt-in check, and authored clocks or event outputs retain ownership of slot 7. This drawing input does not change combo or cancel eligibility.

Melee recovery timing. The resolved swing config can supply a positive RecoveryTime; zero inherits the weapon's default. The state snapshots that duration after resolving the move and run modifiers, then uses the same value for the recovery exit and clock 0's normalized recovery progress. The clock's duration still reports the gameplay sprite track's length, so a recovery drawing should sample normalized progress with useElapsedSeconds: false. See the swing fields and Recovery Override in the Workbench.

An autonomousClocks record can also supply optional advanceRequests. Empty or omitted requests retain continuous advancement. Otherwise all requests must match before elapsed time advances; while unmatched, the clock continues publishing its exact held time. This lets a run clock retain the outgoing stride throughout braking while a separate cape clock keeps moving. Requests may reference distinct gameplay clocks 0/1 only; auxiliary dependencies and event bindings that overwrite a gate input are refused. A newly assigned appearance starts its own clock history. The importer, package builder and registered-drawing round-trip preserve both fields.

A table's optional attachment accepts either the original single axis or multidimensional axes with matching shape. Its integer offsets use row-major order, with the last axis varying fastest. This lets movement and upper-body pose position one shared cloth image without copying it for each body pose. Attachment offsets and image-table entries share the 262,144-entry budget. Validation checks every reachable canvas placement, including independent attachment dimensions, and rejects clipped placements.

The first *.ini file in ordinal filename order containing [PlayerSkin] wins, including a layered-only declaration. Later files do not fill in a partial skin. You may add the plain sprite/clip declarations below to the same skin as its explicit legacy fallback. The loader validates the package and that fallback before applying either: an invalid package, refused image, bad frame or invalid fallback syntax leaves the entire shipped appearance in place. Without plain declarations, fallback uses the shipped clips. With no layered key, a plain skin selects the legacy sprite drawing backend throughout.

Loaded resources are shared across player recreation within the campaign. The entry/title reset releases only its owned package and generated art; it does not destroy shipped assets or another package. Changing files or the editor simulation toggle does not hot-swap a live player's appearance. The retained prefab shader is used in builds, and the package's file, image and table budgets are enforced before a refused skin can replace the player.

Plain sprite clips and fallback

; my-campaign/Player/emberknight.ini
[PlayerSkin]
; your sheet in Player/sprites/, cols x rows
sprite = emberknight.png 12x8
; feet 2px above a cell's bottom
pivot  = 2
; keep the shipped art for clips you don't redraw
clips  = extend

clip Idle      = 0-18  fps 25
; the legs, during the split run
clip Run       = 24-35 fps 18 slot Legs
; the torso: THE SAME FRAMES as the legs clip above
clip Upper_Run = 24-35 fps 18 slot UpperBody
Plain sprite clips use slot. Their legacy split rig draws running legs and torso on two separate renderers, so some clips carry slot Legs or slot UpperBody. Keep those exactly as the template lists them, or a frame shows on the wrong half of the body. Everything without a slot is the whole body on the main renderer. The layered backend instead selects its owned drawing layers through the package's tables and registration data.
The paired clips must be given the SAME FRAMES. Three pairs exist — Run+Upper_Run, RunBowCharge+Upper_RunBowCharge, RunBowShoot+Upper_RunBowShoot. They are not two animations. They are one drawing, cut across the waist by a shader, so the legs can keep their own timing while the arms do something else — that is what lets the player run and aim at once. Point a pair at two different drawings and your character visibly comes apart at the belt: on the shipped archer, one drawing joins to within 2.7px and two drawings never got below 11px, whatever we tried. Note the example above gives both clips frames 24-35.
Pivot: one number, and both halves share it. pivot = 2 means "my character's feet sit 2px above the bottom of a frame". Because the halves are one drawing, they anchor identically — there is nothing to line up by hand, and you should not give a torso clip its own pivot. (An x,y form exists and still applies to enemy art, §12, where a sheet's centre is not its anchor. It used to be needed here too, back when the torso was separately drawn art painted over the legs; a hand-tuned anchor is exactly what the shader cut removed.)

You never start from a blank page here either: a build ships Mods/_Templates/example-campaign/Player/PlayerSkin.ini listing every clip the player has, body and torso, each with its slot and the right frame rate, every line commented out. It is regenerated from the shipped animation set on every build — so it grows when the player does, and the count in it is never something this page has to keep up with. Regenerate it by hand any time with Gleamwood ▸ Dev ▸ Player ▸ Generate Skin Template. With clips = extend you can reskin just the idle and run and leave the rest shipped.

Refused / notedBecause
a plain clip name the player doesn't haveBuilt but reported as a name the player never asks for, with a nearest-name hint. The rest of the skin remains usable; use the template's exact names.

Editor and build diverge like the rest (§05). The GLEAMWOOD PLAYER SKIN REPORT block says what loaded, and it prints from CampaignSession.Activate alongside the other two (§04). This tier flushes twice over: the block itself writes every message raised at load, and _reporting latches at the end of LogIfModded so everything after it — the whole clip-set build, which happens in PlayerAnimation.Awake — reports itself as it is raised rather than joining a list nobody reads again. So a refused skin does say why, in a build's log. The weapon and enemy loaders flush from Load(), so their [Weapons] / [Enemies] lines arrive the same way.

07Re-web the run

Everything above changes what is in the game. This changes the shape of a run: which biomes, in what order, where it branches and where it ends. Files go in Campaign/ inside your campaign folder, and the key names are the same ones the game's own content file uses — a block copied out of GameContent.ini means the same thing here.

; my-campaign/Campaign/web.ini
[Plan]
entry       = ash-start      ; where every run begins

[Node:ash-start]
biome = emberfall            ; a biome ID (not an asset name)
rest  = Rest_EmberTrail      ; the rest after it — the path doors live there

Trailing comments are fine here. Notice the ; where every run begins notes sitting after values above — legal in Campaign/ and in mod.ini, because these files share the reader the game's own GameContent.ini uses, and it strips a mid-line ;. That reader is the exception: in Weapons/, Enemies/, Player/ and Progression/ the same habit silently voids the value (§03). If you only remember one rule, put every note on its own line and it is always correct.

What you can name

A campaign can declare a biome of its own. [NewBiome:ashfields] with a basedOn naming a shipped biome makes an eleventh place: it starts as a copy — room pool, tiles, socket cap, spawn table and all, which is what makes one line playable — and every other [Biome:] key narrows it from there. Its name is then a normal id, so [Node:] biome = ashfields routes the web through it.

A boss works the same way. [NewBoss:AshTyrant] with a basedOn naming a shipped boss gives you its prefab, adds table and reward, and any of displayName, entranceDelay, bossPrefab, addsTable, rewardPrefab and musicTrack change it from there. Point a biome at it with boss = AshTyrant.

A campaign can bring its own music. Drop .wav files into Campaign/Music/ and name one by its filename (without the extension) in any musicTrack line — a biome's or a boss's. Your folder is checked before the shipped library, so a file named after one of ours replaces it for your campaign. .wav only: Unity cannot decode ogg or mp3 from bytes while the game is running, so those are skipped with a line in the report rather than silently. There is a 16MB-per-file cap. Sound effects work the same way — drop .wav files into Campaign/Sfx/ and name one on any sound field a mod tier exposes: a weapon’s AttackSound, an enemy state’s EnterSound. A separate folder from the music on purpose, so a swing cannot accidentally resolve a theme. There is no shipped fallback here, unlike musicTrack: our own combat clips are referenced by asset rather than by name, so there is no name to fall back to — you bring the sound or you keep ours. The menu blips work too: name a file after the shipped one — ui_move, ui_submit, ui_cancel, ui_tab, ui_tick, ui_success, ui_refuse — and it replaces that blip for your campaign.

There is no [Boss:] retune, and you do not need one: declare a boss basedOn the shipped one, change the line you care about, and point your biome at yours. That is the retune, said in one extra line, and it cannot accidentally change a fight in a biome you never mentioned. dialogue, outroSpeaker and outroText are refused here by name — a boss's conversation belongs to the Dialogue tier (Mods/<id>/Dialogue/), which clones the set it changes; setting them from the campaign would edit the shipped dialogue for vanilla too.

Four things are refused, each with the reason in the message: an id a shipped biome already uses (it would shadow it, and every message naming a biome becomes ambiguous — use [Biome:] to retune instead), a missing basedOn, the same id declared twice, and a basedOn naming another DECLARED biome — chaining would make the order of your sections matter, and "it worked until I moved the block" is a bad afternoon.

Everything else still resolves against the shipped game's content, plus any room this campaign drew itself (see below). You can recombine any of it; apart from rooms and biomes, you cannot invent new assets from a text file. Said precisely, because a maker will ask: CampaignPlan dispatches nine section shapes — [Plan], [Node:], [NewBiome:], [Biome:], [NewBoss:], [SpawnTable:], [NewRest:], [Rest:] and [Player.state:] — and anything else is reported as an unknown section and skipped. What a campaign file still cannot reach: a rest ROOM — layoutPrefab is refused by name in both rest blocks, because the room grammar has no vocabulary for a RestSite, ForgeSite, RunModifierSite, PathDoor or RestExit — and four reserved .room glyphs (B, h, w, d) that have no fixture in the project to place. Tracked in Documentation/OUTSTANDING.md, the rows "Four room glyphs are reserved with no fixture to place" and "The between-biome beat".

One thing a rest block still cannot do, said out loud — and one that changed. A campaign is no longer stuck with one kind of rest: [NewRest:<name>] with a basedOn naming a shipped rest declares a second, and a node names it with rest = . It takes the same keys, from the same table, because the keys a rest has do not depend on how it came into being; everything the block does not mention comes from the donor. Putting a node on a declared rest CHANGES THE WEB FINGERPRINT, so a suspended run refuses to resume into it — correct, and the same thing adding a node does. What is still out of reach is the rest room: layoutPrefab is refused because no rest layout is catalogued, and cataloguing the one that exists would buy nothing — the only spatial content a campaign can author is a .room drawing, and that grammar has no vocabulary for a RestSite, ForgeSite, RunModifierSite, PathDoor or RestExit. And because the game ships exactly one RestDefinition, a retune reaches every rest on your web at once — you cannot yet have a forge rest and a breather rest in the same campaign. Both are stated deferrals, tracked in OUTSTANDING.md, not oversights.
Retuning a rest does not strand a suspended run. The resume guard hashes the web's SHAPE — ids, biomes, rest NAMES, edges, topology — and deliberately not tunables, so nudging a heal fraction or switching the forge off leaves every in-flight run on that campaign resumable. Changing which rest a node points at does not.

Choosing the shape of a level

Six keys pick between three generators. Chain is only the enum's default — every biome the game ships is Branching, and GameContent.ini reads these same keys, so a block copied out of it means here exactly what it means there.

KeyApplies toWhat it takes
topologyallChain (a spine left to right with dead-end spurs) · Lattice (a rolled grid of columns and bands, which can carry loops) · Branching (a trunk, a vertical fan column at its end, and one eastbound path leaving each storey — as many ways out of the level as branches asks for, one behind the boss and the rest slip-aways. Shipped biomes ask for 4, except Galewatch and the Hollow Deep at 2).
latticeTierLatticeArc (one loop) · Stack (a loop with a shaft standing on it) · Web (an arc off the arc — two nested loops). The generator comes DOWN this list until a shape your rooms can build fits, and names the room that would have bought the one above. Asking for more than you have costs a log line, never the level.
branchesBranchingHow many PATHS the level offers, including the boss road. Path 0 always carries the boss corridor, arena and exit; the rest end in SlipAway rooms. 1 is legal and means a forced-boss level with no way to skip the fight.
pathRoomsMin · pathRoomsMaxBranchingHow many rooms ONE path owns. The boss road spends part of that budget on its corridor and arena. Defaults are 4–6, and they are measured — swept over 200 seeds of the shipped pool, that is the largest budget that keeps every level inside 28–41 rooms and a minimap more readable than the chain it replaces. 5–8 gives 34–46 rooms and a worst case of 0.62 px/cell against the chain's 0.55: bigger levels, drawn as a smear.
bandHeightBranchingHow tall one path's lane is, in cells. Must exceed the tallest room in your pool or nothing can be placed — and the fan base is deliberately exactly one band tall, which is what makes the storey above it land on the next band's floor. The slack above your tallest room is exactly how much vertical jog a path is allowed.
An unknown value here is named, not swallowed. topology and latticeTier parse as enums; a value that is not one is reported with the list of valid ones, and the shipped setting is kept. That care exists because these keys were once the opposite: the generators were written and tested while no reader accepted a key for them, so a shape the runtime fully honoured was one no author could ask for. A knob nobody can turn is welded shut — and a generator no content can reach does not exist as far as a player is concerned.

Your own rooms

A campaign can supply its own level geometry as text: every Campaign/Rooms/*.room file is read at load and built into a real room, which you then name in a biome's roomPool like any shipped one. This is the one place the "you cannot invent new assets from a text file" rule does not hold.

Your drawings take the biome's look. A room built from text paints its collision with the greybox tile — it has to, that tile is what the player stands on — and then the biome's wallTile, floorTile and platformTile are laid over it on collider-less copies, exactly as they are for a room we shipped. So a [Biome:] or [NewBiome:] block dresses your rooms too, and there is no per-room tile key to learn. Today it dresses them in nothing, and that is not about your file: no shipped biome authors any of those three tiles, so the catalogue your name resolves against is empty and every room — ours and yours — stays greybox. The overlay itself is built and tested; what is missing is a look for it to lay down, and until one exists the two colour keys below are the whole of a biome look you can change. Tracked in OUTSTANDING “No shipped biome authors a look tile, so the campaign look grammar resolves against an empty palette”. (Until 2026-08-20 only the thin platforms in a drawing were dressed and everything solid stayed grey, with nothing logged — if you saw that, it is fixed.)

A .room file is genuinely a drawing: a two-line header (room: for the name, tags: for its role) and then a grid: of characters, where the doors are drawn into the walls rather than declared. The ten in Documentation/ExampleMod (§05) are written to be read as the tutorial: lat-junction.room in particular shows why an ability gates a journey rather than a room. Every declared room goes through the same auditor the shipped prefabs do, at load — so a drawing that would strand the player (a door you can arrive through and then leave by no other) is refused with the reason, rather than wasting a run.

The glyphs are # solid, . air, - thin platform, + door, v pit, @ entry, X exit, e enemy, s secret, t treasure and r relocate point. t marks where the biome's branch treasure goes if the layout pays out in this room — it is a SPOT, not a chest, because which biome is playing decides what the treasure is. Draw none and the payout lands in the middle of the room as it always has; draw two and you get two. r is a perch a boss's relocate state jumps between — it is what lets a drawing be an ARENA rather than only a corridor, and it carries the default perch name, so a boss you have not retuned finds it with nothing to set up. (A boss that wants two separate sets of perches still needs a prefab room: a glyph is one character and cannot carry a name.) Four letters are still reserved and refused by name (B boss gates, h hazards other than pits, w water, d locked doors) so that a file you write today cannot quietly change meaning when they arrive.

Enemies you declared still work here — in every biome by default, and in the ones you name if you say so. A campaign that adds a creature in Enemies/ and retunes a biome in Campaign/ gets both: the retuned biome still rolls from the same spawn table, so your new enemy appears in it with nothing extra to wire. That is the default and it is deliberate — most packs want it. To narrow it, add a tables line to the [NewEnemy:] header:

tables = SpawnTable_Emberfall, SpawnTable_Depths

and the creature joins those tables only. Leave the line out and it joins every table it is rolled from, exactly as before. Write tables = with nothing after it and it joins none — the same as weight = 0, said the other way round. So "only in the Mire" is one line.

"The Mire has no hounds" is the other half, and it is [SpawnTable:]:

[SpawnTable:AshRoster]
basedOn = SpawnTable_Emberfall
enemies = CinderHoundDef:3, ImpScoutDef:0

basedOn starts you from a shipped table (leave it out and the table starts empty, which is allowed — a quiet biome is a real thing to want, and the report says so). enemies sets weights by name, and a weight of 0 removes. Point a biome at it with spawnTable = AshRoster, or a boss at it with addsTable.

Enemies you declared are not named here, and the refusal will tell you so: a declared enemy reuses its donor's prefab, so a row in a table could not tell the two apart and would quietly spawn the donor. That is what the tables key above is for. Both halves work as of 2026-08-20.

When it is wrong, it refuses

A name that does not resolve, or a web that cannot be played — an entry pointing nowhere, a door to a node that does not exist, a node nothing can reach, a loop with no ending — refuses the campaign. The slot will not start, and it tells you which line is at fault. That is deliberate: dropping you into a half-broken run would waste more of your time than refusing to start does.

A value that will not parse is different: minRooms = eight is reported and the shipped number is kept, so one typo does not silently flatten a biome to zero rooms. Same for a key nobody recognises — reported, and the rest of the file still applies.

Editing a web under your own save. A suspended run remembers the shape of the web it was suspended on. Change that shape — add a node, rewire a door, point a node at a different biome — and that run is reported as unresumable rather than quietly continuing into a different game. The save survives; only the run in progress is lost, and you start a fresh one on the new web. Retuning a biome's numbers does not do this, so you can tune room counts all day with a run in flight.

One biome key is the exception, and it is the only one: topology. Every other biome number changes how BIG a level is; topology changes what a level IS — a Chain node has one way out where a Branching one has several, and layouts are regenerated from the seed rather than stored. So a run suspended under one topology and resumed under another would not strand, it would silently RELOCATE: same seed, same node, an entirely different level, and nothing said so. That is worse than a refusal, which is why topology rides the fingerprint along with the web's own shape. A [Biome:] retune reaches it because the retune is what the node is bound to.

A campaign that supplies its own rooms, enemies, weapons and conversations is still selling Gleamwood's upgrades at Gleamwood's prices. Progression/ is the last thing a campaign was renting: what a profile can buy, what a run can become, and what a run earns.

An upgrade takes perLevel (how much one level grants), maxLevel, baseCost and costGrowth (added per level after the first). A modifier takes maxStacks — plus scalePerStack for the ones that multiply a value rather than count something. Of the fourteen effects, four COUNT — ComboCancels, AerialAttacks, ArrowPierce and AirJumps, where the stack itself is the magnitude — nine MULTIPLY, and Imbue is neither: it turns a flag on, and takes the three dotted keys below. Leave scalePerStack at 1 on a multiplying effect and the entry is refused, because one stack of it would change nothing.

AirJumps is the one effect no shipped boon carries. It raises how many jumps one airtime allows — base 1, the single ground-or-coyote jump every player has — and it is fully wired: raise it and the extra jump is real on the authored edges and on the dash’s code edge alike. Gleamwood ships nothing that grants it because a double jump is a traversal verb, and the room generator floods per-ability against what the player owns, so handing one out changes what layouts mean. Your campaign may absolutely declare one — [NewRunModifier:…] with effect = AirJumps and a maxStacks — just know that the rooms were planned for a player without it. Its companion CoyoteTime multiplies the ledge’s grace period instead, which the generator never reads at all.

An Imbue takes three keys of its own

Imbue is the one effect that is not a number: it turns a single named flag on, for a single move, for one run. Those do not fit a scalar field, so they are written as dotted sub-keys — and until they existed, Imbue was an effect this page listed and a campaign could not actually declare. An entry naming effect = Imbue and nothing else names no move, and is refused.

KeyWhat it is
imbue.flagWhich flag to turn on. IsLauncher or CanBeCancelled — those two and no others, because those are the two the game can set. The name is the config field name, spelled exactly as a weapon .ini spells it. A typo is refused rather than ignored: it would otherwise be a modifier that saves, restores, shows in the panel and does nothing.
imbue.defaultThe move it points at when nothing has rolled one — and what a save written before the modifier was targeted resolves to. A move key: aerial:up, ground:forward. It must satisfy the mask below.
imbue.legalEvery move the run is allowed to roll it onto. A list separated by | or ,, where each item is either a move key (aerial:down) or a MoveSet name including the composite Melee — mix them freely. A raw number is refused: it means whatever the bits meant on the day it was typed, and that set has grown before. There is no subtraction; the melee set is seven items, so list what you want.
Only melee moves can be imbued, and leave out anything that already does the thing. An imbue writes into a MeleeAttackConfig, so a bow target could never fire — a mask that reaches outside the melee set is refused by name. The second half is your design rather than a rail: ground:up always launches, so imbuing IsLauncher onto it is a reward the player cannot see. That is why the game's own launcher lists five moves and not seven.

A modifier can be WITHHELD until the player can use it

A boon that raises a budget the player has not bought the verb for is a reward beat spent on nothing — the run hands over Chain Break to a profile that cannot cancel at all, and the player learns only that rewards are sometimes fake. So any modifier, shipped or your own, can name what a profile must already own before a run will offer it. Three keys, the same dotted shape as an imbue's.

KeyWhat it is
requires.abilityAbility ids — dash, wall-jump — separated by | or ,. Any ONE of them satisfies it. A name the game does not have is refused with a "did you mean", and the entry is dropped.
requires.upgradeA kit-upgrade effect, never an upgrade's id: MaxHp · DamagePercent · WeaponStartLevel · MeleeCancel · BowCancel. This is the important half — you may have declared your own [NewUpgrade:] granting the same verb, and naming an id would withhold the boon from every player who bought yours. The same reason the game sums budgets by effect rather than by id.
requires.moveMoves, spelled exactly the way imbue.legal spells them — move keys or MoveSet names, mixed freely, raw numbers refused. Any ONE of them satisfies it. Watch dash: since 2026-08-25 it is a valid move key (the dash strike) as well as an ability id (the dash itself), so requires.move = dash and requires.ability = dash both resolve and mean different things. They are separate save arrays by design — moveIds and abilityIds are two of the three id namespaces — and before the move key existed the first spelling was simply refused, so this is a new way to write the wrong one. In practice the strike implies the ability, so the two overlap heavily; write requires.ability when you mean "can they dash at all".

The three kinds are ANDed; the items inside one are ORed. The example above therefore reads "the cancel verb, and any one of those three ground attacks" — which is what the shipped combo-cancels asks for, because the cancel needs both a verb to spend and a directional attack to spend it on.

It gates the OFFER and nothing else. A run already holding a modifier keeps it, whatever the profile owns — resuming a suspended run must never confiscate something the player earned, and a campaign that grants one through its own content still resolves. And a line the loader cannot read drops the modifier rather than leaving it ungated: everywhere else in this file a refused line falls back to a real working value, but a requirement's fall-back is "ask nothing", which would ship exactly the problem the line was written to prevent. A requirement naming something every profile already starts with is reported as dead weight and otherwise ignored.
maxStacks is a safety cap, not a balance knob. Several modifiers raise a budget that is the only thing bounding a loop — the combo cancel is the clearest, because a large enough budget is an attack state the player never leaves. Raise them a little at a time and play the result. There is a hard ceiling of 10, and it is a refusal rather than a clamp: an entry asking for more is dropped by name, whole, and the modifier stops existing. The highest any shipped modifier declares is 3 (the combo cancel; the other thirteen are 1 or 2), so the ceiling leaves room to more than triple the most generous one and still catches the order-of-magnitude typo, which is the actual hazard.

What a run EARNS

Setting every price and no income only rebalances half the loop — halve what the Shopkeeper charges without touching these and the game is simply twice as generous. [Economy] is the other half. It takes no id: there is exactly one economy per campaign, so it is a section rather than a family, and it clones the shipped one the same way everything else here does.

This tier buys RETUNE, not EXTEND — and the difference is worth knowing before you plan around it. You can rename, reprice, redescribe and re-cap every entry the game ships, and you can declare your own [NewUpgrade:] and [NewRunModifier:] — carrying an effect the game already has. You cannot add a move, an ability, or a new kind of effect. [NewMove:] and [NewAbility:] are refused by name rather than ignored, and the log says why: the vocabularies (MoveSet, PlayerAbilities, RunEffect, MetaEffect, AttackDirection) are compiled C# enums read at fixed seams, so a new entry would have no bit to grant and nothing would consult it — it would show up in the shop, be bought, and do nothing at all. Refusing loudly beats selling that. [Move:] and [Ability:] reach only the entries the game already ships, for the same reason — but a header naming anything else is not silent: it is reported by name, with the count of settings it changed (none), the list of real ids, and a "did you mean". That report covers all four families, so a misspelled [Upgrade:vigour] is caught the same way. It exists because this tier is otherwise strict — an unknown key inside a section was always named, so a modder who has learned the loader catches their typos had been taught to trust a clean console.

Extend is deferred, not abandoned. The eventual answer is string-keyed registries, and the reason it has not happened yet is a real cost rather than a missing afternoon: MoveSet is an allocation-free bitset tested on the per-swing path, and a registry lookup there is a per-hit cost paid by every player so that a few campaigns can add a move. That trade gets made deliberately, on the way to maker mode — the destination where Gleamwood is a 2D roguelite maker that ships as its own first campaign — not by accident. Until it is made: deferred, and this page will keep saying so.
Say what you MEANT to load, and the game will tell you when it did not. The reports say what happened and never what you intended, so a pack that quietly loses one of its three enemy files reads as a clean success. Two optional keys in mod.ini close that:

[Mod]
expectEnemies = 3
expectWeapons = 1

Each is compared against retuned + declared for that tier — the two numbers its report already prints, so you can read the figure straight off the screen rather than work it out. A mismatch is a warning, never a refusal: the entries that did load are fine, and taking a playable campaign away to report a typo would be the wrong trade. Say nothing and nothing is checked, which is every campaign that has not opted in. There is no key for the skin (it is one-or-none, not a count) or for dialogue (its report prints no total) — a key that cannot be checked against is the mistake requires made before it was deleted.
The name in the header is a save key. vigor, combo-cancels — those strings are written into save files. You cannot set id from a file (the game says so if you try), and renaming a section in a campaign somebody has already played silently drops that upgrade from every save holding it. A [NewUpgrade:] or [NewRunModifier:] that repeats a shipped name is refused for the same reason.

When it is wrong

Refusal is per entry, never per file. A misspelled field, a value that is not a number, or an entry that could never do anything — an upgrade granting 0 per level, an Imbue modifier naming no move — is reported in the report (§04) and dropped, and the rest of the file still applies. An upgrade is also refused for a negative perLevel or cost (you would be charging the player for a penalty, which is a sign error rather than a design), and for granting more than 10 melee cancels in total — perLevel × maxLevel on a MeleeCancel upgrade. That last one is not balance: a cancel restarts the same attack with a fresh timer, so the budget is the only thing that ends the loop, and the [RunModifier:] half of the same budget is capped at 10 already. A modded entry goes through the same validation a designer's does, so a mod cannot ship a reward that silently does nothing.

A retune can never break something you already bought. [Upgrade:] works this way as of 2026-08-19: a kit upgrade’s name is a save key with your owned LEVELS stored against it, so if a retune leaves it unusable the campaign’s edit is refused and the shipped values are kept — dropping the upgrade would orphan levels somebody spent Gleam on. [Move:] and [Ability:] are the same shape and were already the two entries with teeth outside the shop — a move is a save key a weapon file also addresses, and an ability is a flag the room generator reads when it decides which levels are clearable. So if a retune leaves one unusable — a display name blanked, an input line deleted — the campaign's version is dropped and the shipped move or ability is used instead: a campaign may not break a move the player has already bought. Everywhere else a bad entry is simply dropped; here there is a purchase behind it.
