Quick Start

Two things you'll do constantly: add content to what already exists, and add whole new mechanics. Here's the fast path for both — and the one rule that keeps you from breaking what already works.

01Sixty-second orientation

Everything in Gleamwood is data on ScriptableObjects, edited through tools, guarded by validators. Three rules make it all safe to touch:

Add, don't mutate

New content is a new asset. You almost never edit code or existing assets — and never at runtime. This is the whole reason adding things doesn't break old things.

Declare, don't wire

An attribute grows the tools: [WorkbenchCategory] a workbench tab, [Tunable] an F1 slider. You never maintain editor glue.

Validate before you trust

Gleamwood ▸ Validate Run Content and the PlayMode suite catch unreachable rooms, unregistered weapons and broken wiring before a run does.

Where you'll work: Gleamwood ▸ Content Workbench for authoring, the Scene view for hitboxes/ranges, F1 in play mode for live feel, and Assets/_Game/Content/GameContent.ini for the run's shape. Full tours are one click away on every page above.

02Guide A — add content to a system that exists

The 90% case: another weapon, enemy, biome or status. It's always the same shape — duplicate a working asset, retune it, register it, validate — and it's inherently non-breaking because you're only adding.

The universal recipe

  1. Duplicate the closest working asset. In the Project window, Ctrl+D an existing one (e.g. DefaultSword.asset → your new blade). Starting from a known-good asset means every required field is already sane.
  2. Open it in the workbench. Right-click ▸ Open in Content Workbench. Retune only the live fields it shows — the tool hides the dead ones on purpose.
  3. Register it where the game looks. This is the step that makes it real. The workbench tells you if you missed it — a red [!!] row at the top of the Overview tab.
  4. Tune hitboxes/ranges in the Scene view if it fights — drag handles, don't type. (Player for weapons, the enemy prefab for enemies.)
  5. Validate. Gleamwood ▸ Validate Run Content → 0 errors, then Gleamwood ▸ Run PlayMode Tests → green.

03Guide B — add a brand-new mechanic

A mechanic that doesn't exist yet — a hazard, a pickup, a trap. The pattern: data SO → runtime behaviour that reads it → let the tools find it by declaration. One new file gets you the full authoring surface.

Step 1 — the data

Create the ScriptableObject that holds the mechanic's tunable numbers. Tag the class and designers get a Content Workbench tab for free — no editor code:

// Anywhere under Assets/_Game/. This one file is the entire authoring surface.
[WorkbenchCategory("Hazards", Accent = "#4dd2ff")]   // → a "Hazards" rail tab
[CreateAssetMenu(menuName = "Gleamwood/Hazard Definition")]  // → Assets ▸ Create entry
public class HazardDefinition : ScriptableObject
{
    [WorkbenchField("Feel", Note = "0 = single burst")]  public float PulseInterval = 0.5f;
    [WorkbenchField("Impact")]                          public int   Damage = 1;
    [WorkbenchField("Presentation")]                    public AudioClip TriggerSound;
}

CombatStatusDefinition ships exactly this pattern today — the real Statuses tab, drawn from nothing but these attributes.

Step 2 — the behaviour

A MonoBehaviour that reads the definition and acts. The golden discipline: read the shared asset, never write it (see §04).

public class Hazard : MonoBehaviour
{
    [SerializeField] HazardDefinition def;   // authored data, drag it in the inspector
    float _t;
    void Update()
    {
        _t += Time.deltaTime;
        if (_t >= def.PulseInterval) { _t = 0; Pulse(def.Damage); }
    }
}

Step 3 — reach the rest of the toolbox (optional)

Live tuning

Want to feel it in play mode? Put [Tunable("Hazards", 0f, 5f)] on a runtime field and call TunableRegistry.Register(this) in Awake — it becomes an F1 slider. → Tuning

Text authoring

Want it INI-driven? Add a key to the importer's mapping. The pattern is mechanical once the SO is flat data. → Tuning & INI

A rich workbench tab

Need sub-tabs, checks or derived values instead of the plain form? Implement IWorkbenchCategory. → Workbench

Animation / audio hooks

Animator-state strings become validated dropdowns with [AnimatorStateRef]; sounds are just AudioClip fields (auto preview button). → Extending

Every one of these is declaration only — you never touch the workbench, the F1 panel, or the importer's core. The complete seam catalog and meta-recipes live on Extending.

04The one rule — add, don't mutate

Adding content is safe by construction; changing shared state is where old features break. Internalise these and you can author fearlessly.

Never mutate a shared SO at runtime

Definitions are shared by every instance. A run's upgrades ride a per-run copy (the player weapon is a WeaponInstance; the runtime player is an Instantiated clone of PlayerSettings). If you write to the asset in play mode, you've edited the game for everyone — and on disk. Read the definition; keep mutable state on the component.

nodeIds and shipped ids are save data

Suspended runs store node ids by name. Renaming a shipped nodeId breaks existing saves. Add new nodes; don't rename old ones. (Renaming a biomeId instead breaks the INI's [Node] biome = references at import — also additive-only.)

A campaign folder name is save data for the same reason: a slot records the campaignId it was created with, so renaming the folder orphans every save made with it. And changing the SHAPE of the shipped web — a node added, an edge repointed — drops every suspended run in every save (RunWebFingerprint); the saves themselves survive. Retuning a biome's numbers is free.

Register, don't replace

Add your weapon to the catalog's list; don't repurpose an existing entry. Add a spawn-table row; don't retune the shared enemy other biomes use. New row = new behaviour, isolated. Editing a shared row changes every user of it.

Stamp values on the asset, not the code default

Runtime reads the asset, not the C# field initializer. A new field defaults to 0 on existing assets until you set it. After adding a field, open the affected assets in the workbench and give them real values — don't rely on the compiled default.

Widen enums, don't reorder them

Serialized assets store enum values by index. Append new enum members; never reorder or delete, or every asset silently shifts to the wrong value.

Let the validators be your safety net

Unreachable branch? Unregistered weapon? Missing dead state? Validate Run Content makes them build-breaking errors. If it's green and the suite is green, your addition didn't break the wiring.

Why this works: the game reads definitions, never hardcode. New definitions are invisible to old systems until something references them — so a new enemy, weapon or mechanic literally cannot affect an existing run it isn't wired into. The only ways to break the past are the five hazards above: mutating a shared SO at runtime, renaming a saved id, replacing a shared row instead of adding one, trusting a compiled default you never stamped onto the asset, and reordering an enum. The sixth card is not a way to break anything — it is the net that catches the other five.

05Pre-flight — before you commit

Four checks, in this order. Each one catches a class of breakage the next cannot see — the validator catches wiring, the suite catches behaviour, playing catches feel, and the doc pass catches the lie your change just made true.

  1. Gleamwood ▸ Validate Run Content — 0 errors. (Rooms: also Gleamwood ▸ Audit Room Reachability.)
  2. Gleamwood ▸ Run PlayMode Tests — all green — the run writes the count and any failures to Logs/playmode_test_results.txt.
  3. Play it. New content only counts once it's shown up in an actual run.
  4. Touched a system a wiki page documents? Update that page in the same commit — see Maintaining.
