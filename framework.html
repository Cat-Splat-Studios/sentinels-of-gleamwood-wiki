Framework & Architecture

The state machine that runs every player and enemy, the data-driven transition system designers author against, the one known bug that eats config edges, and the boot/services spine underneath it all. This is the condensed map — the state_machine_*.md pages carry the full prose.

01The five-piece model

The framework lives at Assets/_Framework/StateMachine/ — namespaces StateMachine (core + states) and StateMachine.Core (transition/condition data types); editor code under StateMachine.Editor / StateMachine.Editor.Creator. Five pieces, always the same five:

ReactiveContext is ScriptableObject-based (PlayerContext); Lightweight is the same API without the SO for frequently-spawned entities (EnemyContext) — no Remove/Clear methods on the lightweight one. 02Runtime behavior — what the machine actually does

The exact API of StateMachine<TContext> (Core/StateMachine.cs). Everything a programmer touches; designers mostly meet this indirectly through configs.

MemberBehavior
CurrentState / PreviousState / ContextPreviousState returns CurrentState if there is no previous yet.
Initialize(TContext context)Just assigns the context — the public path for wiring one in. In practice both concrete machines write the protected context field directly in Awake (Initialize has zero call sites today); the base class has no abstract members to implement.
RegisterState<T>(string stateId, T state)Throws InvalidOperationException on a duplicate id; calls state.Init(this, context).
GetState(string) · TryGetState(string, out …) · GetState<T>()GetState throws if missing; TryGetState is the safe lookup (added in Phase 3 for fallbacks — see the EnemyHitState safety net in §03); GetState<T>() returns the first state of that type, throws if none.
AddTransition(from, to, Func<bool> condition, Action onTransition = null, int priority = 0)Registers an edge, then re-sorts that state's edges descending by priority. See the rule box below — this call overwrites.
SetInitialState(string | IState)Sets and calls Enter() immediately.
ChangeState(string | IState) · RevertToPreviousState()Manual switches, same Exit→Enter flow.
event OnStateChanged(IState previous, IState current)Fired on every switch — this is where the enemy machine hooks EnterSound one-shots.
EnableDebug() / [SerializeField] bool debugModeState-change logging for live debugging.
states · stateTransitionsBoth dictionaries are public fields. Convenient, unguarded — treat them as read-only unless you know why you're writing.
AddTransition = last writer wins per from→to pair. Before adding, it silently RemoveAlls any existing transition from from to the same target. This is the exact mechanism behind the hybrid-state bug in §04: a hardcoded edge added after base.SetupTransitions() deletes the config-authored edge to that same target without a whisper.
Update order: Update() runs CheckTransitions() before currentState.Update() — at most one transition fires per frame (priority order, breaks after the first hit). FixedUpdate() only forwards to the state; it never checks transitions. A doc comment claiming "base.Update() updates transitions" is wrong (§06).

Transition<TContext> (State/Transition.cs) carries TargetState, Priority, TransitionCount (increments each firing), ShouldTransition(), PerformTransitionAction(). For hand-built edges there's a fluent builder via StateExtensions:

// TransitionBuilder (State/Builder/TransitionBuilder.cs)
state.AddTransition(stateMachine)
     .To("idle")                    // state instance or id
     .When(() => ctx.IsGrounded)
     .WithAction(() => PlayLandDust())
     .WithPriority(1)
     .Build();

03Data-driven transitions — the designer path

Every state config carries a Transitions list. That list is the designer-facing edge authoring surface — no code, no rebuild.

TypeFileContract
TransitionDefinition<TStateConfig, TContext>Core/TransitionDefinition.cs[Serializable] row: ToState (a config in the same Definition) + List<TransitionCondition> Conditions + List<DynamicCondition> DynamicConditions. Everything ANDs — all conditions in both lists must pass.
TransitionCondition<TContext>Core/TransitionCondition.csScriptableObject; override bool Check(TContext context). Type-safe, hand-coded — generate new ones with the Creator's Condition Creator tab (§05).
DynamicConditionCore/DynamicCondition.csNo-code property rule: Create ▸ StateMachine ▸ Dynamic Condition. Fields: PropertyName (exact context property, e.g. IsGrounded), Operator (Equal / NotEqual / Greater / Less / GreaterOrEqual / LessOrEqual / IsTrue / IsFalse), FloatValue, BoolValue. Compiles an expression-tree predicate cached per (asset, context type) — context-agnostic, so one asset can serve player and enemy machines.
DynamicCondition failure mode: if the property name doesn't compile against the context, it logs an Error once and the predicate permanently returns false — the transition just never fires. Typo in PropertyName = a dead edge with one console line to show for it. DynamicCondition.ClearCache() exists if you need to recompile after a hot fix.

How config edges register: ConfigurableState.SetupTransitions() walks IStateConfigWithTransitions<TContext>.GetTransitions() (Core/IStateConfigWithTransitions.cs), resolves each target by ToState.StateId, pre-compiles the dynamic predicates, folds everything into one composite Func<bool>, and registers it via AddTransition — always priority 0, never an onTransition action. An unresolvable target logs a Warning and is skipped. Both machines register in two passes: all states first, then SetupTransitions() on every state — so forward references always resolve, regardless of list order.

Recipe: add a transition to an existing state

  1. Select the state config — it's a sub-asset of the Definition (expand the .asset in the Project window), or edit it on the workbench's States tab.
  2. In the Transitions list, add an element and set ToState to another config in the same Definition.
  3. Add Conditions (existing TransitionCondition assets) and/or DynamicConditions — for a dynamic one, Create ▸ StateMachine ▸ Dynamic Condition, set PropertyName to an exact context property, pick the Operator, fill FloatValue/BoolValue.
  4. Enter Play mode and watch it in the Visualizer (§05). Remember: all conditions AND together, and config edges sit at priority 0.
The EnemyHitState safety net (Assets/_Game/Enemies/Code/States/EnemyHitState.cs ~lines 34–52): data-driven Hit→X transitions are the primary path; once hitstun elapses it falls back to config.FallbackStateName (default "idle") via TryGetState — a missing fallback warns once instead of throwing. This is why TryGetState exists.

04The hybrid model — and the known bug that eats config edges

Some player states are hybrids: they call base.SetupTransitions() (config-authored edges) and then keep hardcoded AddTransition calls afterward. Combine that with the overwrite rule from §02 and you get the top item in HANDOVER.md §6.A0.

KNOWN BUG (HANDOVER §6.A0 — the missing early return). Several hybrid player states call base.SetupTransitions() then run their hardcoded AddTransition edges unconditionally — no early return. Because AddTransition silently removes any existing edge to the same target, hardcoded edges override config-authored edges to the same target state. A designer editing the Transitions list on these configs sees no effect for any overlapping target. Affected files (Assets/_Game/Player/Code/States/):
  • MovementStates/PlayerWallSlideState.cs (~line 24)
  • MovementStates/PlayerJumpState.cs (~line 149 — its own comment admits "Priorities might need adjustment if Config transitions conflict")
  • MovementStates/PlayerDashState.cs (~line 27)
  • AttackStates/PlayerMeleeAttackState.cs (~line 32)
  • AttackStates/PlayerDashAttackState.cs (~line 29)
Pure data-driven states where your config edits do win: PlayerRunState, PlayerIdleState, PlayerFallState, PlayerBowAimState ("legacy manual path retired"). Until the audit lands: before tuning a transition on a hybrid state, check its SetupTransitions override for a hardcoded edge to the same target — if one exists, your config row is dead weight.
// The hybrid shape (abridged — this is the bug pattern, not a model to copy):
public override void SetupTransitions()
{
    if (config != null) { base.SetupTransitions(); }   // config edges land first…

    // …then these run unconditionally — no early return — and each call
    // RemoveAll()s any existing edge to the same target. Hardcoded wins.
    stateMachine.AddTransition(this, stateMachine.GetState("idle"), () => Done());
}

Recipe: a brand-new state type, end to end

  1. Only if the state TYPE doesn't exist yet: Cat Splat State Machine ▸ Tools ▸ State Machine Creator → State Creator → pick the Target System, name it, choose the base config, add variables → Generate. Wait for the compile. (Reusing an existing type? Skip straight to step 2.)
  2. Gleamwood ▸ Content Workbench → Enemies (or Player) → States → + Create State: pick the type, name it. That one action creates the sub-asset, sets StateName, adds it to States, promotes it to InitialState if it's the first, and runs the post-processors.
  3. Same tab: wire its Transitions (To State + Conditions), and Set as Initial State if this is the entry state.
  4. Check the validation rows are green, then test in the Visualizer.
Authoring lives in the workbench precisely because the old flow spanned two windows: the Creator made the asset and the definition inspector's + appended an empty slot, leaving StateName to be set by hand — the field that decides whether any transition can reach the state. See Workbench §07.

Debugging live: open the Visualizer, pick the machine, flip on Live View — or call EnableDebug() / tick debugMode on the machine component for state-change console logs.

07Boot & services — the spine under everything

One static class owns startup order. Everything else hangs off it. Source of record: HANDOVER.md §2.

GameBootstrap — the single owner of startup

Assets/_Game/Systems/Boot/GameBootstrap.cs (static). Fires from any scene. Every step is wrapped: a failure logs [Boot] Step 'X' failed and later steps still run.

PhaseUnity hookDoes
ResetStaticsSubsystemRegistrationRuns every play session, even with domain reload off. Resets CoreReady, _uiRoot, GameSignals.Reset(), MenuRouter.Reset(), MenuState.Reset(), RunDirector.Reset(), SaveSystem.ResetSession().
InitPlayerLoopAfterAssembliesLoadedTickManager into the player loop.
InitCoreBeforeSceneLoadGameSettings → console brand provider (#if consoles) → InputDeviceTracker → CoreReady = true.
InitAfterFirstSceneAfterSceneLoadSteam (#if GLEAMWOOD_STEAM) → SpawnUIRoot(). Skipped when the active scene name starts with InitTestScene; tests opt in by calling the public, idempotent GameBootstrap.SpawnUIRoot().
Two hard rules. (1) Do not add [RuntimeInitializeOnLoadMethod] to services anywhere else — GameBootstrap is the single owner of startup order. (2) New static state anywhere in the game must be reset in ResetStatics, or it leaks across play sessions with domain reload off.

Entry flow and the services root

  • BootConfig — SO at Assets/_Game/Systems/Boot/Resources/BootConfig.asset (Create ▸ Game ▸ Boot Config), loaded via BootConfig.Load() = Resources.Load<BootConfig>("BootConfig"). Fields: firstSceneName = "1.Title", splashEnabled = true, splashSeconds = 2f (any button skips), gameServicesPrefab.
  • Bootstrapper (Systems/Boot/Bootstrapper.cs) drives the entry scene 0.Bootstrapper (build index 0): waits for CoreReady → splash → LoadScene(firstScene).
  • GameServices.prefab (Systems/Boot/GameServices.prefab) — the DontDestroyOnLoad root spawned by SpawnUIRoot(). Hosts the global Loading screen (sort order 10) and SettingsMenu (sort 2). Scene menus use sort 0–2, ConfirmPrompt 3. Never add per-scene copies of Loading/Settings.

Signals, router, prompt

  • GameSignals (static, Systems/Boot/GameSignals.cs) — the gameplay→UI event surface: LevelCompleted(RunStats), ObjectiveEntered(string chapter, string title, string objective), WeaponsChanged, each with a Raise* method. A raise with zero listeners logs a Warning — silence is a bug signal here.
  • MenuRouter (static, Assets/_Game/UI/Code/Framework/MenuRouter.cs) — type-keyed registry of live screens: Open<T>(Action onClosed) where T : MenuScreen, IMenuOverlay (warns if the panel is missing), Get<T>(), TryGet<T>(out T). Screens auto-register via MenuScreen OnEnable/OnDisable.
  • ConfirmPrompt — the shared modal; resolve it via MenuRouter.TryGet. The builder/labels API is deferred, not missing by accident.
Never add a static Instance to a menu screen — the router is the registry. And all scene loads go through LoadingScreenController.LoadScene(…), never SceneManager.LoadScene directly.

PlayerSettings: clone at boot, never mutate the asset

PlayerStateMachine.Awake() (execution order −110) loads Resources.Load<PlayerContext>("PlayerSettings") — the asset at Assets/_Game/Player/Resources/PlayerSettings.asset — and assigns context = Instantiate(initalState): a clone. Runtime tweaks (states, the F1 panel) hit the copy and evaporate on scene change; the Workbench's Player category edits the asset itself, which is the durable path. Same philosophy as the run loadout: RunDirector hands out WeaponInstance wrappers (upgrade levels ride the instance) and the shared weapon definitions are never mutated.
