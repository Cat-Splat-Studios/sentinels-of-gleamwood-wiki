Framework & Architecture

The state machine that runs every player and enemy, the data-driven transition system designers author against, the one known bug that eats config edges, and the boot/services spine underneath it all. This is the condensed map; state_machine_api_reference.md beside it carries the signatures.

01The five-piece model

The framework lives at Assets/_Framework/StateMachine/ — namespaces StateMachine (core + states) and StateMachine.Core (transition/condition data types); editor code under StateMachine.Editor / StateMachine.Editor.Creator. Five pieces, always the same five:

02Runtime behavior — what the machine actually does

The exact API of StateMachine<TContext> (Core/StateMachine.cs). Everything a programmer touches; designers mostly meet this indirectly through configs.

MemberBehavior
CurrentState / PreviousState / ContextPreviousState returns CurrentState if there is no previous yet.
Initialize(TContext context)Just assigns the context — the public path for wiring one in. In practice both concrete machines write the protected context field directly in Awake, so Initialize has no game call sites — StateMachineRuleTests is its only consumer, using it to stand a machine up without a prefab. The base class has no abstract members to implement.
RegisterState<T>(string stateId, T state)Throws InvalidOperationException on a duplicate id; calls state.Init(this, context).
GetState(string) · TryGetState(string, out …) · GetState<T>()GetState throws if missing; TryGetState is the safe lookup (added in Phase 3 for fallbacks — see the EnemyHitState safety net in §03); GetState<T>() returns the first state of that type, throws if none.
AddTransition(from, to, Func<bool> condition, Action onTransition = null, int priority = 0)Stable-inserts the edge before the first strictly-lower-priority one — it does not re-sort. Equal priorities therefore keep insertion order, and that is load-bearing: config edges all register at priority 0 and CheckTransitions takes the first match, so an unstable List.Sort made authored order a coin flip between runs. PlayerJumpState relies on it explicitly — its bow edge shares a priority with the melee edge and is registered after it so melee still wins a simultaneous press. See the rule box below — this call also overwrites.
SetInitialState(string | IState)Sets and calls Enter() immediately.
ChangeState(string | IState) · RevertToPreviousState()Manual switches, same Exit→Enter flow.
event OnStateChanged(IState previous, IState current)Fired on every switch — this is where the enemy machine hooks EnterSound one-shots.
EnableDebug() / [SerializeField] bool debugModeState-change logging for live debugging.
states · stateTransitionsBoth dictionaries are public fields. Convenient, unguarded — treat them as read-only unless you know why you're writing.
AddTransition = last writer wins per from→to pair — and on a hybrid state, the last writer is whoever registers after base.SetupTransitions(). Before adding, it RemoveAlls any existing transition from from to the same target. That is the exact mechanism behind the hybrid-state bug in §04: a hardcoded edge added after base.SetupTransitions() deletes the config-authored edge to that same target.

It no longer does it in silence. Every collision now emits a Debug.LogWarning naming both sides, deduped once per (from-type → to-type) pair per session — a player prefab re-registers its code edges in every scene load and every test fixture, so warning per call would print the same known collisions hundreds of times a suite run, which is a warning nobody reads. Once per pair makes the console an inventory: what is printed is exactly the set of edges where authored data has been overwritten by code. The replacement itself is correct — CheckTransitions takes the first match, so two edges to one target would leave the second unreachable regardless. What was wrong was doing it without a word. The fix is always the same shape: ONE edge whose condition ORs both cases together.
Update order: Update() runs CheckTransitions() before currentState.Update() — at most one transition fires per frame (priority order, breaks after the first hit). FixedUpdate() only forwards to the state; it never checks transitions.

Transition<TContext> (State/Transition.cs) carries TargetState, Priority, TransitionCount (increments each firing), ShouldTransition(), PerformTransitionAction(). For hand-built edges there's a fluent builder via StateExtensions:

// TransitionBuilder (State/Builder/TransitionBuilder.cs)
state.AddTransition(stateMachine)
     .To("idle")                    // state instance or id
     .When(() => ctx.IsGrounded)
     .WithAction(() => PlayLandDust())
     .WithPriority(1)
     .Build();

03Data-driven transitions — the designer path

Every state config carries a Transitions list. That list is the designer-facing edge authoring surface — no code, no rebuild.

TypeFileContract
TransitionDefinition<TStateConfig, TContext>Core/TransitionDefinition.cs[Serializable] row: ToState (a config in the same Definition) + List<TransitionCondition> Conditions + List<DynamicCondition> DynamicConditions. Everything ANDs — all conditions in both lists must pass.
TransitionCondition<TContext>Core/TransitionCondition.csScriptableObject; override bool Check(TContext context). Type-safe, hand-coded — generate new ones with the Creator's Condition Creator tab (§05).
DynamicConditionCore/DynamicCondition.csNo-code property rule: Create ▸ StateMachine ▸ Dynamic Condition. Fields: PropertyName (exact context property, e.g. IsGrounded), Operator (Equal / NotEqual / Greater / Less / GreaterOrEqual / LessOrEqual / IsTrue / IsFalse), FloatValue, BoolValue. Compiles an expression-tree predicate cached per (asset, context type) — context-agnostic, so one asset can serve player and enemy machines.
DynamicCondition failure mode: if the property name doesn't compile against the context, it logs an Error once and the predicate permanently returns false — the transition just never fires. Typo in PropertyName = a dead edge with one console line to show for it. DynamicCondition.ClearCache() exists if you need to recompile after a hot fix — and boot already calls it every play session (GameBootstrap.ResetStatics, §07): the cache is keyed by (asset instance id, context type) and with Disable Domain Reload on both halves of that key survive a play session, so without it an edited condition kept evaluating the OLD expression until the editor restarted.

How config edges register: ConfigurableState.SetupTransitions() walks IStateConfigWithTransitions<TContext>.GetTransitions() (Core/IStateConfigWithTransitions.cs), resolves each target by ToState.StateId, pre-compiles the dynamic predicates, folds everything into one composite Func<bool>, and registers it via AddTransition — always priority 0, never an onTransition action. An unresolvable target logs a Warning and is skipped. Both machines register in two passes: all states first, then SetupTransitions() on every state — so forward references always resolve, regardless of list order.

Recipe: add a transition to an existing state

  1. Select the state config — it's a sub-asset of the Definition (expand the .asset in the Project window), or edit it on the workbench's States tab.
  2. In the Transitions list, add an element and set ToState to another config in the same Definition.
  3. Add Conditions (existing TransitionCondition assets) and/or DynamicConditions — for a dynamic one, Create ▸ StateMachine ▸ Dynamic Condition, set PropertyName to an exact context property, pick the Operator, fill FloatValue/BoolValue.
  4. Enter Play mode and watch it in the Visualizer (§05). Remember: all conditions AND together, and config edges sit at priority 0.
The EnemyHitState safety net (Assets/_Game/Enemies/Code/States/EnemyHitState.cs ~lines 34–52): data-driven Hit→X transitions are the primary path; once hitstun elapses it falls back to config.FallbackStateName (default "idle") via TryGetState — a missing fallback warns once instead of throwing. This is why TryGetState exists.

04The hybrid model — and the known bug that eats config edges

Some player states are hybrids: they call base.SetupTransitions() (config-authored edges) and then keep hardcoded AddTransition calls afterward. Combine that with the overwrite rule from §02 and you get the open debt in Documentation/OUTSTANDING.md, the row "AddTransition still deletes authored edges".

KNOWN BUG — OUTSTANDING.md, the row "AddTransition still deletes authored edges", and the missing early return. Read the console first: it names the dead edges for you. Every same-target collision now logs [StateMachine] FromType->ToType: a registered transition REPLACED n existing one(s)…, once per pair per session (§02). Play once and that warning list is the set of authored edges code has overwritten — no file reading required. The slow fallback, for a state you cannot yet run: open its SetupTransitions override and look for a hardcoded edge to the same target. If one exists, your config row is dead weight.

The bug itself: several hybrid player states call base.SetupTransitions() then run their hardcoded AddTransition edges unconditionally — no early return. Because AddTransition removes any existing edge to the same target, hardcoded edges override config-authored edges to the same target state, and a designer editing the Transitions list on these configs sees no effect for any overlapping target. Affected files (Assets/_Game/Player/Code/States/):
  • MovementStates/PlayerWallSlideState.cs (~line 24)
  • MovementStates/PlayerJumpState.cs (~line 171 — its own comment admits "Priorities might need adjustment if Config transitions conflict")
  • MovementStates/PlayerDashState.cs (~line 27)
  • AttackStates/PlayerMeleeAttackState.cs (~line 124 — also the model for the fix: its landing branch is folded into the existing idle/run edges as one ORed condition each, with a comment saying exactly why a second edge would have deleted the first)
  • AttackStates/PlayerDashAttackState.cs (~line 28)
Pure data-driven states where your config edits do win: PlayerRunState, PlayerIdleState, PlayerFallState — each is nothing but base.SetupTransitions().

A third case, and it is the shape a hybrid SHOULD have: PlayerBowAimState. It is a hybrid — after base.SetupTransitions() it registers the M6 Quick Quiver edge, bowAim→meleeAtk gated on RunDirector.MetaBowCancel && !hasReleased && context.IsMeleeInputBuffered. But its two authored rows in PlayerDef.asset target idle and fall, so the code edge's target is one no authored row points at and nothing is eaten. Config edits still win here, by construction rather than by luck — and if that ever changes, the collision warning says so.
// The hybrid shape (abridged — this is the bug pattern, not a model to copy):
public override void SetupTransitions()
{
    if (config != null) { base.SetupTransitions(); }   // config edges land first…

    // …then these run unconditionally — no early return — and each call
    // RemoveAll()s any existing edge to the same target. Hardcoded wins.
    stateMachine.AddTransition(this, stateMachine.GetState("idle"), () => Done());
}

07Boot & services — the spine under everything

One static class owns startup order. Everything else hangs off it. This section is the source of record — HANDOVER.md is a pointer page now and no longer carries the boot/services architecture, so there is nowhere else to check.

GameBootstrap — the single owner of startup

Assets/_Game/Systems/Boot/GameBootstrap.cs (static). Fires from any scene. Every step is wrapped: a failure logs [Boot] Step 'X' failed and later steps still run.

PhaseUnity hookDoes
ResetStaticsSubsystemRegistrationRuns every play session, even with domain reload off. Resets, in order: CoreReady, _uiRoot, GameSignals.Reset(), MenuRouter.Reset(), MenuState.Reset(), RunDirector.Reset(), SaveSystem.ResetSession(), ModSet.Reset(), StateMachine.Core.DynamicCondition.ClearCache(), CampaignSession.ReloadTiers(). The last three are recent and each pays for itself: ModSet forgets which campaigns are installed before any tier resets, so one added since the last play session is discovered rather than served stale; ClearCache is the compiled-predicate cache from §03; ReloadTiers drops the cloned definition graphs and loaded mod art, which are in-memory objects with no asset backing that nothing else would collect.
InitCoreBeforeSceneLoadGameSettings → console brand provider (#if consoles) → InputDeviceTracker → the three mod status reports (ModStatusReport enemies, WeaponStatusReport weapons, PlayerSkinOverrides player skin, each LogIfModded) → CoreReady = true. The reports run here rather than at first spawn so a modded build states its inventory before anything asks for an enemy: a graph that fails only complains when something needs it, which in a build is minutes into a run, and "the enemy never showed up" is the least diagnosable symptom there is. Silent when there is no mod folder.
InitAfterFirstSceneAfterSceneLoadSteam (#if GLEAMWOOD_STEAM) → SpawnUIRoot(). Skipped when the active scene name starts with InitTestScene; tests opt in by calling the public, idempotent GameBootstrap.SpawnUIRoot().
Two hard rules. (1) Do not add [RuntimeInitializeOnLoadMethod] to services anywhere else — GameBootstrap is the single owner of startup order. (2) New static state anywhere in the game must be reset in ResetStatics, or it leaks across play sessions with domain reload off.

Scene singletons — exactly two are sanctioned

SingletonFileContract
CombatTimeManagerAssets/_Game/Combat/Code/CombatTimeManager.cspublic static CombatTimeManager Instance. Header comment: "Intentional scene-scoped singleton… callers use Instance?. … Not part of the MenuRouter/GameSignals migration — do not convert." API: TriggerHitstop(duration, timeScale), TriggerDramaticFreeze(duration, timeScale) and CancelHitstop(), plus the IsHitstopActive flag. Both entry points take a default freeze depth — read them off the file rather than copying them here. The dramatic freeze outranks the ordinary one: an ordinary hit landing during a perfect shot's freeze is dropped rather than restarting the clock at ordinary length, which would make precision end the freeze earlier than a botched hit does. OnDestroy nulls Instance before restoring the clock, because Instance?. does not respect Unity's fake-null and a later hit would otherwise call into a destroyed component.
BiomeHostControllerAssets/_Game/Systems/Run/BiomeHostController.cspublic static BiomeHostController Instance — set in the scene lifecycle, nulled on destroy.
Stale claim alert: there is no LevelManager. It was deleted in the M1 run-based redesign along with Checkpoint/LevelExit/RunTracker — none of those four types exists anywhere in Assets/, which is the check to run rather than trusting a doc. Any doc or memory line saying "LevelManager/CombatTimeManager stay scene singletons" is out of date — RunDirector (the static run phase machine under Systems/Run/) plus the host controllers replaced it. The sanctioned pair is CombatTimeManager + BiomeHostController.

PlayerSettings: clone at boot, never mutate the asset

PlayerStateMachine.Awake() (execution order −110) loads Resources.Load<PlayerContext>("PlayerSettings") — the asset at Assets/_Game/Player/Resources/PlayerSettings.asset — and assigns context = Instantiate(initalState): a clone. Runtime tweaks (states, the F1 panel) hit the copy and evaporate on scene change; the Workbench's Player category edits the asset itself, which is the durable path. Same philosophy as the run loadout: RunDirector hands out WeaponInstance wrappers (upgrade levels ride the instance) and the shared weapon definitions are never mutated.

08Panel sort order — the ladder

A new panel defaults to sorting order 0, and 0 renders UNDERNEATH the screen that opened it. Mirror an existing panel's order from the ladder below; the rest of this section is why that rule costs so much when it is missed.

Sort order lives on each panel's own PanelRenderer (m_SortingOrder), not on the PanelSettings asset. Every menu and gameplay panel shares one Assets/UI Toolkit/PanelSettings.asset, so the per-renderer value is the only thing that stacks them.

Why 0 is a trap. A panel at 0 opened from a screen at 1 sits behind that screen's dim: invisible, with no compile error and no console message, and a screen test that instantiates the panel on its own still sees it render perfectly. Not hypothetical — the Run Map shipped at 0 and is opened from the Pause menu at 1, so it opened behind a 74%-opaque backdrop.

PanelSortOrderTests catches this now, and the pairs are DERIVED, not listed: it sweeps the source for both router verbs — MenuRouter.Open<T> and MenuRouter.TryGet — and fails if an overlay does not sort above its opener. Both verbs, or the coverage is a third of what it looks like: Open<T> is constrained where T : MenuScreen, IMenuOverlay, which ConfirmPrompt and CampaignPickerController do not implement, so an Open<T>-only sweep made the three routes out of the save-slots screen invisible to a test whose whole purpose is that class of bug. Two route classes are skipped rather than fudged: an opener that is a world object with no panel of its own (ShopkeeperNPC, ForgeSite, RunModifierSite, BossArenaSequence), and LoadingScreenController resolving itself — nothing can sort strictly above itself.

One exception to the shared-PanelSettings rule: the F1 debug panel uses its own Assets/UI Toolkit/DebugPanelSettings.asset at sorting order 100. A second PanelSettings sorts at the panel level, above every renderer order in the ladder — which is the point, so the debug tree never merges into the HUD's panel. It is wired that way on Player.prefab, and that is the only debug panel there should be.

There was briefly a second one, and it is worth knowing why it was invisible to everything. 3.BiomeHost.unity carried a root GameObject named DebugPanel: active, bound to DebugUI.uxml on the shared PanelSettings at order 0, with no DebugUI script on it. Nothing constructed or hid it — .debug-panel has no display: none, and the only line that hides the tree (DebugUI.cs:228) runs from a component that object did not have — so the main gameplay scene drew a 450×115 85%-opaque black box over the HUD that F1 could not toggle. It was also a legacy UIDocument rather than a PanelRenderer, so a sweep for PanelRenderers did not list it even while its element was live in the panel. Deleted 2026-08-09.

09The menu framework — build screens on these

Every menu (title, save slots, settings, shop, pause, credits, story, run map, loadout, campaign picker) sits on one base class and a handful of shared pieces. Each of these exists because a hand-rolled copy of it drifted into a real bug — a list that scrolled on hold in one screen and not the next, a tab bar that wrapped, an ember layer at four different sizes. Reach for the piece, not for a copy of it.

PieceWhat it owns
MenuScreen (abstract)All per-screen plumbing: the PanelRenderer reload lifecycle (idempotent re-query), the ambient ember field, controller-glyph hints, device-change refresh, input subscription, the navigation latch, show/hide. Subclasses set RootName and override only the hooks they use — OnReload, OnNavigateStep, OnSubmit, OnCancel, OnPauseInput, OnVisualUpdate, RefreshGlyphs, OnDeviceChanged. Overlays set AutoSubscribeInput => false and manage input around their own Open/Close.
NavRepeatThe navigation latch and hold-to-repeat, in one place, so every list scrolls on hold for free. It ticks on the frame clock rather than the input event, because InputReader hooks performed/canceled only — a held D-pad raises exactly one event and nothing more. Return true from OnNavigateStep only when the selection actually moved; that and only that plays the click, so a held direction pinned at the end of a list goes quiet.
MenuList / MenuEntryData-driven vertical menu — declare new MenuEntry("Label", Action, enabled) and it builds the labels and handles nav/highlight/submit. One source of truth: no parallel UXML labels or index switches.
MenuTabBarThe shared tab strip (LB/RB, Q/E). Owns the one-row constraint — a wrapped second row is a layout bug, and there is a geometry test pinning it.
MenuPolledInputPolled input for screens that cannot use the event path.
SettingRowThe row model — Header / Option / Slider / Action — used by the Settings menu — its only consumer. Selectable is kind != Header && enabled, which is how a dimmed row stays visible but unreachable.
CrawlScreenAuto-scrolling crawl + hold-to-skip with progress (the credits roll).
ConfirmPromptThe shared modal, resolved via MenuRouter.TryGet. Refuses to act when the panel is missing rather than assuming yes.

Recipe: a new screen

  1. UXML with a root element named "<name>-root"; optional "embers" container and "hint-nav"/"hint-submit"/"hint-back" glyph slots. Tag text font-display or font-body.
  2. USS that starts with @import url("/Assets/_Game/UI/Theme/MenuCommon.uss"); — that is where .embers, .hint-glyph and .hint-label live. Do not re-declare them; they shipped at four different sizes across fifteen panels before they were shared.
  3. Controller : MenuScreen (or : CrawlScreen), set RootName, build content in OnReload, use MenuList for any menu.
  4. Drop the panel into the scene: PanelRenderer → source UXML + Assets/UI Toolkit/PanelSettings.asset, assign the shared InputReader.asset, keep the GameObject active (controllers show/hide themselves), and set the sorting order per the ladder in §08. No fonts to assign — the theme supplies them.

Save slots — what the picker is actually listing

Assets/_Game/Systems/Save/ — SaveSlot (the data) and SaveSystem (a static). One JSON file per slot at Application.persistentDataPath/saves/slot_{i}.json. What each permanent purchase means lives on Progression; this is the slot machinery underneath it.

  • Slots are an expanding list, not a fixed row of boxes. LoadAll() enumerates the saves directory and returns only files that exist; NextFreeSlot(existing) reuses the gap a deletion leaves. SaveSystem.MaxSlots (200) is a ceiling that bounds "find a free index" — nothing iterates it to build a list, and the comment at SaveSystem.cs:63 records why that distinction was expensive to learn. A row's position in the picker is not its slot index; the picker keeps the real one per row.
  • A slot is bound to a campaign for life. SaveSlot.campaignId ("" = vanilla) is written once at creation and never changes, so a modded run cannot reach a vanilla save or another campaign's. The campaign is activated before ResumeFromSlot, because saved weapon ids resolve through that campaign's catalog — do it the other way round and a save holding a mod-declared weapon silently reverts to the default. campaignName is recorded alongside the id so the row still draws when the campaign folder is gone (that slot warns, refuses to launch, and stays deletable).
  • SaveSystem.ActiveSlot is the slot the session reads and writes; the picker sets it on Start/Continue.
Never bump SaveSystem.CurrentVersion. Load() treats a file whose version is below it as an empty slot — a bump does not migrate a save, it destroys the profile behind it: playtime, Gleam, every unlock. New fields are additive, with a C# initializer whose default already means the right thing. Related: read parallel save arrays per index, never joined under one Math.Min, or a pre-feature save reads as zero of everything.

The theme — one file for every colour and font

Assets/_Game/UI/Theme/GleamwoodTheme.tss is the single source of truth, assigned to Assets/UI Toolkit/PanelSettings.asset as its Theme Style Sheet. It imports Unity's default runtime theme, then defines the palette on :root and the fonts on .font-display / .font-body.

  • Change a colour: edit the token in :root — --bg, --ember, --ember-hot, --ember-deep, --text, --text-dim, --rule. Every panel updates, because panels reference var(--ember) rather than declaring their own. A panel may still override one token locally for a deliberate one-off accent.
  • Change a font: edit the -unity-font-definition urls. -unity-font-definition is inherited, so the :root default cascades and .font-body overrides per element.
  • The HUD and EnemyUI keep a few local combat tokens; they are on the same PanelSettings and theme.
