Progression & the Gleam Economy

The Hades-style spine: a run earns Gleam, death or victory banks it, and between runs it buys permanent kit upgrades and weapon unlocks. This page is the map of every number, seam and save field in that loop — and the one rule that keeps a locked weapon from bricking a saved run.

01The loop in one picture

Every run makes permanent progress — that is the whole reason to replay. Currency accrues during the run, and is banked into the permanent profile whether you clear or die.

One owner, one choke point. RunDirector (static) owns run state; EndRun(RunOutcome) is the single run-over path — every ending routes through it, so banking can never be skipped. All slot writes go through its private WriteSlot funnel.
Three endings, not two. RunOutcome replaced a bool died, "which could only say two things about a game that has three endings":
OutcomeWhat happenedWhat it pays / claims
DiedKilled, anywhere.Depth pays; nothing else does.
SlippedOutReached the end and walked past the arena.A finish, not a clear — a real payout (SlipBonus), but no grade, and runsCleared does not move.
ClearedThe final boss went down.The only ending that claims a clear, and the only one graded.
The discriminator is the boss's death, not the door. Since in-level branching the slip-away is a path through the final biome rather than a bypass edge — both routes call CompleteBiome and both reach RunPhase.Clear — so the exit you took cannot tell them apart. Whether the Demon King actually fell can.

02The currency — one asset, six numbers

Everything about how much a run earns lives in Assets/_Game/Systems/Run/Resources/Economy.asset — an EconomyDefinition. Economy.cs is six get-only properties over it (Economy.Current), so the curve is still read in one place, and a campaign retunes every number from an [Economy] block in its Progression/ folder exactly as it retunes an upgrade's price.

NumberValueMeaning
CurrencyName"Gleam"Display name everywhere. Rename here to re-theme the whole economy.
PerKill2Awarded per enemy felled inside a biome — the moment-to-moment trickle (RunDirector.ReportKill).
PerDepth20Run-end bonus per depth tier reached — rewards pushing deeper. Depth pays for every ending: reaching the end is worth something however you leave it.
PerBoss60Bounty per boss actually felled — counted, not inferred, so a run that fells three and dies to the fourth keeps those three bounties. Before this a boss was worth PerKill, the same 2 Gleam as a Cinder Hound; that is what made "the slip-away costs you something" a lie.
ClearBonus100Extra on a full clear, over a death at the same depth.
SlipBonus25Extra for reaching the end and walking past the arena. Deliberately far below ClearBonus: slipping out is a real ending with a real payout, not a punishment, but it must never be the efficient way to farm. The gap IS the decision.

The run-end lump is RunEndBonus(depth, outcome, bossesDefeated) = max(0, depth) × 20 + max(0, bossesDefeated) × 60 + (Cleared ? 100 : 0) + (SlippedOut ? 25 : 0), added on top of the accumulated per-kill trickle. The same function feeds the run-over screen's "+N Gleam" line and the actual bank, so the number the player sees is exactly what is credited.

Earned — during the run

Each kill inside a biome adds PerKill to RunDirector.RunCurrency (the in-run wallet). It is written into the suspended-run blob (RunSave.runCurrency) at every room entry, so quitting mid-run never loses it.

Banked — at run end

EndRun adds RunCurrency + RunEndBonus(Depth, outcome, BossesDefeated) to MetaProgress.currency. On a death too — that is the Hades promise: no run is wasted.

Shown — on the run-over screens

The Death and Results screens read BuildStats().currencyEarned and show "+N Gleam". RunDirector.CurrencyBalance reads the banked total for the hub (reads disk — call it on hub entry, not per frame).

The curve is authored live — this was once a "promote the constants to a ScriptableObject someday" note, and the someday shipped. EconomyDefinition carries all six as [WorkbenchField] rows, so they are editable in the inspector or under the Workbench's own Economy category, and a campaign overrides any of them by field name (case-insensitive, like every other tier) in an [Economy] section of a Progression/*.ini: currencyName · perKill · perDepth · clearBonus · slipBonus · perBoss. It takes no id, because there is exactly one economy per campaign.

The C# field initialisers are not the live numbers. They are the shipped defaults and the fallback for when there is no asset in Resources at all — which is what keeps a bare test scene earning exactly what the shipped game earns. While Economy.asset exists it wins, so editing those initialisers compiles green and changes nothing.

03Permanent kit upgrades

Between runs, Gleam buys permanent boosts — Hades' "Mirror of Night". Five ship today, in the shop order below; three are levelled numbers and two are one-level verbs. They are authored one asset per upgrade in Systems/Run/Resources/KitUpgrades/, listed in shop order by MetaUpgradeCatalog.definitions, and baked into the upgrades array everything actually reads (§07).

UpgradeEffectPer levelMaxCost curveApplies at (seam)

Cost of the nth level is baseCost + (n−1) × costGrowth; the magnitude owned is level × perLevel. At StartRun / resume, RunDirector.RecomputeMetaBonuses reads the slot's owned levels through MetaUpgradeCatalog.TotalBonus and caches the five totals — MetaMaxHpBonus, MetaDamageMult, MetaWeaponStartLevel, MetaComboCancels, MetaBowCancel — so the per-hit / per-scene consumers read a cheap value and never touch disk.

A verb resets to OFF, not to a no-op — and the sandbox is a grant, not arithmetic. The three numeric totals fall back to clean no-ops off a run (damage ×1, +0 HP, +0 start level). The two verb totals do not: ResetBonuses() sets MetaComboCancels = 0 and MetaBowCancel = false, because "a REAL profile with no upgrades bought resets to zero cancels — the verb is the purchase." A bare test scene still swings like today's game only because RunDirector.Reset() hands it back explicitly (MetaComboCancels = 1; MetaBowCancel = true; — "the sandbox owns the verbs, exactly as it owns the moves"). Written down where the reason lives, rather than smuggled in as a field initializer every reader has to notice.

That is also why CanCancel carries its own ownership guard on top of the budget: RunModifiers.Budget sums every held modifier, so a base of 0 plus a Chain Break pickup would hand the verb to a player who never bought it, through the back door, with the shop none the wiser. The purchase gates the verb; the budget only counts how often it may be used.
Why the apply lives where it does. The player's context is re-cloned for every biome, so max-HP is re-stamped in Awake each scene rather than once. Damage rides the per-run WeaponInstance (shared weapon SOs are never mutated — see the Combat page's instance rule). One effect → one seam; new effects arrive as new mechanics land.
Deferred by design: dash-charge and forge-charge upgrades are drafted but not shipped — the player has a single cooldown-gated dash (no charge pool) and the forge is a per-rest boolean (not a count). Both need a charge mechanic before the MetaEffect can apply, so they are intentionally absent rather than dead.

04Weapon unlocks

A weapon can be held back until it is bought at the hub — the "new weapon" carrot. Two ship locked: the Solar Greatsword (300 Gleam) and the Dagger Unseen (250 Gleam).

Any WeaponDefinition carries an optional lock, authored in the inspector (or the Workbench):

FieldMeaning
lockedUntilUnlockedWhen true, the weapon is not offered in loot rolls / hub pedestals until its unlock is owned on the active slot.
unlockCostGleam price to permanently unlock it. The unlock is keyed by the weapon asset name and appended to MetaProgress.unlockIds.

RunDirector.IsWeaponUnlocked(def) answers "may this be offered?" — true for any non-locked weapon, and for a locked one whose id is on the slot. TryUnlockWeapon(def) is the buy: it checks the weapon is locked, unbought and affordable, debits the Gleam and records the unlock. Off a save slot (sandbox) locked weapons simply stay hidden.

The one rule — gate at OFFER time, never at RESOLVE time. The unlock check lives in exactly one predicate: LootTable.Qualifies, the filter every roll and pedestal offer passes through. A locked weapon stays in the catalog and the loot tables; it is only kept out of the offer. That is deliberate — WeaponCatalog.Resolve turns saved weapon ids back into definitions when a suspended run resumes, so gating there would brick a saved run that already holds the weapon. Add unlock logic to Qualifies; never to Resolve.

04bMovement abilities

The Wall Jump (200 Gleam) and the Dash (200 Gleam) are earned, not given. They are the only purchase that changes the shape of the level: the generator refuses to hand out rooms the player cannot clear, so buying one visibly widens what the game builds.

Where they live

One AbilityDefinition asset each, in Assets/_Game/Systems/Run/Resources/Abilities/, listed in shop order by Resources/AbilityCatalog.asset. PlayerAbilityCatalog.All loads that catalog and passes it through ProgressionOverrides.Resolve, so a campaign retunes an ability from its Progression/ folder with [Ability:<id>], exactly as it retunes an upgrade or a run modifier (Modding §08). The Defaults array in code is no longer the catalog — it is the loud fallback when the asset is missing, and the seed Gleamwood ▸ Dev ▸ Run ▸ Generate Progression Assets writes the assets from. What a campaign still cannot do is add one: PlayerAbilities is a compiled flags enum read at hard-coded seams, so [NewAbility:] is refused by name — a declared third ability would have no bit to grant and no seam would consult it, so it would render in the shop, be bought, and do nothing. Ownership is MetaProgress.abilityIds, its own array rather than unlockIds (which is keyed by weapon asset name).

The one design knob

PlayerAbilityCatalog.Baseline is what a brand-new profile can do. It ships as None, so both abilities are earned. Set it to PlayerAbilities.All and the entire system becomes inert plumbing — nothing else changes. A profile saved before abilities existed reads as owning none, so existing players buy them too.

An ability is a flag on PlayerAbilities, and adding one touches exactly three places — miss any and the feature is incoherent:

PlaceWhat it decidesWhat breaks if you miss it
RoomReachability.Metrics.ForWhat the movement model believes the flag lets you do.Every room's requirement re-derives to the wrong answer.
Nothing — the generators are genericWhich connections the layout routes through a room.Handled for you: the spine is gated per pair, side paths are not.
PlayerContext + the FSM edgesWhether the player can actually perform it.Rooms are withheld from a player who could have cleared them all along — the gate becomes a tax rather than a progression.
The gate is on the JOURNEY, not the room. What must be clearable is the path the layout actually routes — entry to exit. Every other door is a marker: the ledge you can see and cannot take yet, which is the thing that tells a player an upgrade would open something. RoomTemplate.RequiredForPath(from, to) answers per ordered pair, so one room can be a stroll along its floor and a wall-jump climb to its ceiling at the same time.

Judging a room as a whole is not a stricter version of this — it is a different and wrong question, and it shipped. A lattice junction whose left-to-right corridor is a plain walk was condemned for its ceiling door, the pool lost the only shape that closes a loop, the generator returned nothing, and the player dropped into an empty scene.
PathGated?Why
Entry → Exit (the spine)YesThe run has to be finishable with what they hold on arrival.
Lattice arc (the upper band)NoIt is a loop — both risers land back on the spine — so removing every arc edge still leaves Entry connected to Exit. An unclimbable riser costs nothing.
Branches (side dungeons)NoNothing behind one is needed to finish. A wing you cannot climb today is a reason to come back.
The one refusal that remains. RoomBuilder rejects a room only when a door you can arrive through reaches no other door — judged with every ability unlocked, so it means broken geometry rather than a locked one. A door you merely cannot reach builds fine and is reported as a note, naming which journey is locked behind what.
And the backstop. If a gated pool still cannot build, the gate is lifted for that biome with a loud error rather than returning no layout — a room the player may struggle with beats an empty scene. It should never fire; if it does, the pool is missing a bare-handed room for some shape the topology needs on the main path.

Where the ability set comes from (2026-08-03)

RunDirector.Abilities mirrors the ACTIVE SLOT — except during a run, where it is frozen at whatever the layout was generated from.

It used to be PlayerAbilities.All whenever no run was in flight, and PlayerContext repeated that exemption a second time as !RunDirector.IsRunActive ||. The result was one profile with two kits: you could dash in the hub and not in the run. Hisham, on a build — "it should be the same player so they should have the same abilities."

The escape hatch is now about having no PROFILE, not about being outside a run. With no slot bound, PlayerAbilityCatalog.Owned(null) already answers All, so 3.TestSandbox and any scene opened straight from the Project window still hold the full kit. That needed no special case — it falls out of the same expression, which is the tell that the exemption never should have been about runs.
MomentSeamWhy it must recompute
A slot is bound (new game, continue, restored after a failed launch)RunDirector.BindSlotBinding a slot and deriving what it can DO are one operation. The two bare SaveSystem.ActiveSlot = writes in SaveSlotsController were how a hub ended up holding the previous session's kit.

An ability is bought at the Shopkeeper, or dev-toggledTryUnlockAbility / DebugSetAbilityOwned, guarded by if (!IsRunActive)In the hub it applies at once — otherwise you buy the dash and cannot dash in the room you bought it in. Mid-run it waits, because widening the set would desync it from the level already built.

Pushed, not computed. SaveSystem.Load hits disk with no cache, and PlayerContext.HasDash is compiled into a DynamicCondition and evaluated every frame — so a per-read getter is impossible. Abilities also stays a settable static because BiomeGenerator widens it to All around generation and restores it in a finally; a computed property would break that seam.

Visible consequence, and it is intended: a brand-new profile stands in the hub with neither dash nor wall jump. The hub is traversable bare-handed, and what you see there is now exactly what you take into the run.
Still gated on IsRunActive, deliberately unresolved: PlayerStateMachine adds MetaMaxHpBonus only during a run, so the hub player also has less max HP than the run player. Vigor is a run boost in a way a dash is not, and RunDirectorTests pins the reset on purpose — so that is a separate decision, not an oversight.

04cThe directional moveset

Seven of the ten directional moves are permanent Gleam purchases, and their prices live in ASSETS — a cost edited in C# after its asset exists changes nothing at runtime, so read the asset when a number matters.

The moveset went from one swing to nine in a day. Handing all of it over at once is both a worse first hour and a wasted progression axis — Hisham: "in order to make the perm upgrade shop more interesting - should we have to purchase all aerial and directional attacks? this makes a lot of sense". Everything outside MoveCatalog.Baseline is bought at the shopkeeper's Ground, Air and Bow tabs — one tab per input family, so the tab name and the row's own instruction line ("Ground: UP + attack") say the same word. It was ONE "Moves" tab until the bow's moves took it to eight rows and the panel outgrew the screen; the split is filtered through MoveKey.TryParse, so a new move lands in its tab with no category field to keep in sync.

Where those prices live. One MoveDefinition each in Resources/Moves/, ordered by Resources/MoveCatalog.asset; MoveCatalog.Defaults is the seed the generator writes them from and the fallback when the asset is missing — hence the lead's warning. The baseline three have no asset and no shop row — MoveCatalog.Baseline is a list of keys, so their input lines above are descriptions rather than authored strings.
Why the neutral moves are never sold. aerial:neutral is the fallback every aerial leans on: with it unowned, an unowned Up resolves to nothing and an airborne swing plays the grounded combo clip — a planted stance hanging in mid-air, the exact bug the aerial moveset was built to fix. bow:neutral is that same structural argument on the bow, every bow entry's fallback. bow:forward is baseline for a different reason: firing while running is what the bow does, not a thing you buy — the split rig has always let the torso draw while the legs carry on, and selling it back as a weaker instant shot played worse than the behaviour it replaced.

The launcher used to be up there with them, and is now the cheapest row in the shop. ground:up is still the only move in the shipped data that puts an enemy in the air, and four of the ten executions are gated on a juggled target — which was the whole argument for giving it away. Hisham's call overrode it: "I don't think executions are necessarily things the player should be worried about on their first couple of runs." So it sells, and the price is the mechanic: MoveUnlockTests.TheLauncher_IsSold_AndIsTheCheapestThingInTheShop pins it as both the cheapest entry and the first row, because it is the purchase that opens the game up rather than one that widens it. A launcher priced like a luxury would be the wall the old rule was protecting against.

MoveUnlockTests pins the neutral air out of the shop, the launcher's price, and the invariant that every move is either baseline or sellable (a move that is neither is authored, animated, permanently dead content).

One vocabulary, three uses

MoveKey (Assets/_Game/Combat/Code/Definitions/) is the modding tier's move address, promoted. [Weapon:DefaultSword.aerial:up] was already a published contract with anyone who has written a mod; the same string is now the shop's save key and the imbue's target. Inventing a second spelling would have meant two vocabularies for one idea, and only one of them getting updated. Keys are interned, so the combat seam's per-hit compare is a reference check.

The gate is inside the resolver loop

TryResolve/TryResolveExact take an optional owns predicate, applied per candidate — not to the result. That placement is the whole design: an unowned aerial Up has to fall through to the Neutral aerial exactly as an unauthored one does. Filtering afterwards would return false and leave the swing with no clip at all.

Two questions, two methods. TryGetAerial/TryGetGrounded stay asset oracles — "does this weapon author a move for this direction" — and the Workbench, the wiki capture and the mod loader all keep asking that, because a designer has to be able to see and tune a move nobody has bought. TryGetAerialOwned/TryGetGroundedOwned ask the gameplay question, and only the attack state calls them. Collapsing the two would turn a shop gate into an authoring gate.
Unlike an ability, a move applies IMMEDIATELY — in the hub or mid-run. Abilities are frozen mid-run because the level was generated from them; RoomReachability has no attack term at all, so nothing the generator decided depends on the moveset. You walk out of the shop swinging what you just bought.
Existing profiles buy the sellable list back. A save written before this shipped has an empty moveIds, so it reads as the baseline — the same thing that happens to a new profile. That is the identical call movement abilities made, and for the identical reason: the alternative is granting them silently, which would mean no existing player ever sees the feature. Three testers, early-stage saves, and the launcher priced at 20 so the first re-purchase costs almost nothing.

04dPer-run modifiers — rules, not numbers

The third tier, and the newest. A run modifier is a mechanical rule change the player picks up during a run and loses when it ends. Hisham's framing, which is why the tier exists: "the idea is we can have a bunch of mechanical things like this on a per run basis."

Where they live

RunModifierCatalog and RunModifiers (Assets/_Game/Systems/Run/). The catalog is now one asset per modifier plus an ordered catalog asset in Resources/, authored in the Workbench's Run Upgrades tab and retunable from a campaign's Progression/ folder (Modding §08). The order is load-bearing: the offer roll walks the catalog, so a seed only reproduces if the list does. The built-in set survives in code as RunModifierCatalog.Defaults — the fallback when the catalog asset is missing, and what the generator writes the assets FROM — and because moving to assets deleted the compile-error-on-rename protection the const strings gave, which is why an id-stability test now pins them against a literal list. RunModifiers is a static dictionary of id → stacks; reading it is one lookup, so a combat seam can ask on every swing.

A campaign can DECLARE one, not just retune it — [NewRunModifier:<id>], resolved inside RunModifierCatalogAsset.ToRuntime so a modded entry faces exactly the Problems() gate a designer's does. That is a structural difference from the moves and abilities of §04b/§04c, which refuse [NewMove:] / [NewAbility:] by name: a modifier is addressed by its RunEffect, and the seams already sum by effect rather than by id, so a declared entry reusing an existing effect needs no C# at all. (Kit upgrades take [NewUpgrade:] for the same reason — a MetaEffect is likewise an address.)

Including an imbue. The applier binds public scalar fields, and an imbue is neither — its flag, its default target and its legal mask are private serialized fields on MoveImbue — so Imbue used to be the one effect this tier advertised and could not declare: the entry parsed, named no move, and its own Problems() gate dropped it. It now has a dotted sub-grammar routed through MoveImbue.SetFromText — imbue.flag, imbue.default, imbue.legal — which keeps the fields private (an imbue that changed shape at runtime would invalidate the index RunModifiers builds from it) and gives each line its own refusal. Writing any of the three is what marks the entry targeted; the mask takes move keys and MoveSet names alike and refuses a raw number. Spelled out on Modding §08.

And a requirement. A second dotted family — requires.ability, requires.upgrade, requires.move, routed through RunModifierRequirement.SetFromText — says what a profile must already own before a run will offer the modifier. Same reasoning as the imbue's (a public flags field would re-open the raw-number hazard), with one deliberate difference: a refused imbue.legal is a warning because "wider than asked" still does what the modder wrote, while every refused requires.* line drops the entry, because a requirement's fall-back is "ask nothing" and an ungated boon is precisely what the line was written to prevent.

Every modifier has a CAP, and it is load-bearing

maxStacks is not a balance knob bolted on afterwards. Several of these raise a budget that is the only thing bounding a loop — a cancel restarts the same combo index with a fresh timer, so an unbounded cancel budget is a state the player never leaves. RunModifierTests.EveryCatalogEntry_IsUsable refuses an uncapped entry.

Updraft is TARGETED: it imbues one rolled move. The ground up-attack is the launcher by default and always will be — but which other move also launches is rolled per run from the seed, so a run where the down-air launches plays differently from one where the running attack does. RunModifierRoll owns the roll; the target is stored on the run rather than re-derived, because a weapon's moveset can be rewritten from text between sessions and a seed-derived target would silently relocate on resume — the failure class RunWebFingerprint exists to refuse for layouts.

Two moves are never rolled. ground:up already launches, so imbuing it spends the modifier on nothing. ground:down is the Crumple, and the two are contradictory in a way that deletes the move: Crumple zeroes knockback to pin a target where it stands, and launching immediately overwrites the body's velocity — "pin them" would become "throw them", and the Pinfall execution would stop being reachable.

Grouped here by how they are read. The catalog asset's own order is what the offer roll walks, and reordering it changes what a seed produces.

The five movement scales deliberately do NOT reach RoomReachability. That model loads the shared PlayerSettings asset, so the generator plans for the base kit — a room that is only clearable with a run upgrade you might not have rolled is a room that can strand a run. Two stacks each for the same reason: enough that a lucky run feels different, few enough that the compounded product stays inside what the rooms can absorb. A wildly faster player should outrun the generator's assumptions, never get stuck inside them.

Both dash modifiers are pure upside, and that is forced rather than generous. M9 planned to rebaseline the dash "cheap and worse" and sell it back; a measured sweep says the shipped numbers sit on a cliff edge (TheDashBase_SitsOnACliff). Deferred, out loud.
Updraft cannot become an infinite, and that is structural rather than tuned. EnemyStateMachine only honours isLauncher against a grounded target — you cannot launch something that is already up there. So an up-air that launches is a second opener, never a way to keep a target airborne. Any future "X also launches" modifier inherits the same guarantee for free.

Four are withheld until you can use them

Hisham, on the bug this closes: "[boons] don't consider what the player has unlocked, so sometimes if you receive something you can't use it right away." Measured on a fresh profile: the pool was nine entries and three of them were dead — roughly one wasted offer per reward beat, and about 23% of beats showing at most one working boon. Four of the fourteen declare a RunModifierRequirement, and RunModifierOffers.Roll is the one seam that reads it.

ModifierNeedsBecause — measured at the read site
Chain Break combo-cancelsthe MeleeCancel verb and any one of ground:up / ground:down / ground:forwardTwo prerequisites, and the second is easy to miss. CanCancel returns false on MetaComboCancels <= 0 before the budget is compared, so without the technique all three stacks raise a number no path reads. And a grounded cancel resolves through TryGetGroundedOwned, which is TryResolveExact — no Neutral fallback, unlike the aerial side — so a player owning no ground directional attack holds a verb with nowhere to spend it. (The airborne branch is no escape: it also demands resolvedConfig.CanBeCancelled, which no shipped aerial authors.)
Loose Grip loose-gripthe MeleeCancel verbIts imbue mask is NOT the gate, and the two are deliberately not merged. The ground-only mask already hides it from a fresh profile — but the mask answers "is there a move to put this on", and the requirement answers "does the flag do anything once I get there". Buy ground:forward and no technique and the mask passes while the flag it turns on is read by a CanCancel that has already refused. No move requirement is added on top: the mask already guarantees the roll landed on an owned ground move, and that same move is what the cancel resolves into.
Long Stride long-stride
Second Breath second-breath		the dash ability (200 Gleam)Every route into PlayerDashState folds in HasDash — four data edges through Dy_IsDashReady and three code edges through CanDashNow, all reading PlayerContext.IsDashReady, which is HasDash && …. So both scale numbers on a state the player cannot enter. It is the worst of the four: abilities are frozen for the duration of a run (§04b), so a dashless player handed one of these cannot make it useful before the run ends.
The other ten are left alone on purpose. Featherfall, Fleetfoot, Quickstart, Steady Hands, Second Wind, Updraft and M13’s four are all live on a baseline profile, and a prerequisite naming something that gates nothing is dead weight the maker mode has to keep honouring forever — while shrinking the fresh pool for no reason. RunModifierRequirement.Warnings() reports a requirement that is always satisfied (a baseline move, or an ability in PlayerAbilityCatalog.Baseline) at catalog load, as a warning rather than a drop: the modifier still works.

Four exist so a profile that owns nothing still gets a choice

Hisham, on what the withholding exposed: "we should also consider having enough boons created so that we can offer boons even if the player has nothing unlocked." The gate above left a fresh profile a pool of six, and the count was never the problem — three of the six were movement stat bumps (jump height, move speed, run accel), so a first run of four to six rest sites at three offers each kept presenting the same three numbers. M13 adds four that each name a different verb, and every one of them was picked because a bare kit already reaches its read site.

BoonWhy a bare kit reaches it
Splitshaft splitshaftThe bow is always equipped: PlayerStateMachine falls back to Resources/Weapons/DefaultBow, and both baseline bow directions (bow:neutral, bow:forward) clear MoveCatalog.OwnsBow. Pierce was already built and tested with nothing selling it.
Deep Rest deep-restThe rest asks for no ability, no move, no weapon and no upgrade — RestSite.OnInteract checks only that you have not rested here yet. Every run passes four to six of them.
Long Guard long-guardThe neutral ground combo is not a gated "move": the *Owned resolvers apply to directional variants only, and the sword is always equipped. The swing every player has from the first second is the one this widens.
None of the four declares a prerequisite, and that is the design rather than an oversight. A requires on one of these would put it straight back into the pile the gate already withholds from a fresh profile — which is the exact problem they were added to fix. RunModifierOfferTests.TheBareKitFour_DeclareNoPrerequisiteAtAll pins it. If one of them ever turns out to need a purchase to matter, the seam was the wrong one and the boon should move, not grow a requirement.
DecisionWhy it is that way
The OFFER only. Grant, Read, SetCount, Budget and Scale stay unguardedRule 6's spirit: a resumed run holding a boon keeps it. A run suspended with Long Stride and resumed on a profile that reads as dashless — a campaign switch, a downgrade — must resume holding it rather than have it confiscated. Same rule as LootTable.Qualifies: gate at OFFER time, never at resolve time.
Each tier addressed the way that tier is stableKit upgrades by MetaEffect, never by upgrade id — a campaign may declare its own [NewUpgrade:] granting MeleeCancel, and an id would withhold Chain Break from everyone who bought that one. Abilities by id, because PlayerAbilities is a compiled flags enum [NewAbility:] refuses to extend and AbilityDefinition.id is the stable save key. Moves by MoveKey.
AND across the three kinds, OR within oneNaming an ability and a move means both; naming three moves means any one will do. | already reads as OR everywhere else in this file format (imbue.legal), and one symbol with two meanings is how a modder gets the opposite of what they wrote. A conjunction within a kind is not expressible — deferred, out loud, because nothing needs it.
A parsed string, not a public flags fieldIniFieldApplier binds public scalars through Enum.TryParse, which accepts "1023" — the raw-number hazard MoveImbue.TryParseSet exists to refuse, and the one that silently widened the shipped launcher's mask when the bow bits joined MoveSet.All. So this mirrors MoveImbue exactly: private fields, public readers, one dotted sub-key each.
RunKit, not RunDirector statics inside the rollRoll promises to be a pure function of (catalog, weapon, kit, seed, salt), and that promise is what lets the reward beat be tested with no screen. Reading the statics at the seam would have been two lines shorter and made the roll untestable in the one case that matters — a literal baseline profile. RunKit.Capture() reads the same statics the gameplay seams read, so the offer and the controller cannot disagree.
RunWebFingerprint untouchedFiltering changes what a given seed offers for runs already in flight. That is one-time churn: no save is invalidated, nothing is stranded, and a run's layout is unaffected. Migrating the fingerprint for it would invalidate suspended runs to fix nothing.
Where the base value lives. At the seam, not in the catalog: RunModifiers.Budget(RunEffect.AerialAttacks, 1) written out at the call site reads as "you get one, and the modifier adds more". A bare Budget(effect) returning 1 by magic would hide the number a designer actually wants to change. Note the first argument is the effect, never an id — the seam sums every held modifier carrying that effect, which is what makes a second "+1 cancel" a catalog entry and no code.

How the player gets one

At a rest: three RunModifierSites present three DIFFERENT offers, and you walk to the one you want. That is the first thing in the shipped game that grants a run modifier — the tier had been saved, capped and tested with RunModifiers.Grant at zero production callers, obtainable only through a dev panel that is compiled out of release builds. A mechanic the player cannot obtain is not shipped.

PropertyHow it works, and why
Shaped on ForgeSiteThe same InteractZone base, so it inherits the device-aware prompt glyph; the same walk-to-pick spatial choice rather than a menu, which is the vocabulary the rest of the game already speaks.
One charge per roomTaking any offer disarms every sibling site, exactly as the forge does. SuspendAtRoomEntry fires right after the grant, so quitting immediately after taking a reward keeps it.

Capped modifiers never appearThe pool is built in catalog order from everything not already at its cap — and, for an imbue, everything with a legal move left to land on. It returns fewer than asked rather than padding: late in a run there may genuinely be only one thing left to give, and duplicates to fill three slots would be a choice that is not a choice. A site with no offer says "Nothing left to give."
Unusable modifiers never appear either, and the pedestal says nothingThe same pool build drops anything whose requirement this profile does not meet. It is silent on purpose: a reward beat is a choice between things you can use, and a pedestal that greyed itself out would spend one of the room's three slots explaining a shop. The withholding is said on the Loadout screen instead — see the row below.
Turn it off per restRestDefinition.rewardsEnabled (default true). Off = the sites hide, exactly as the forge does — for a rest that should be a pure breather.

What you are holding is visible on the HUD's modifier strip (PlayerHUDController), which rebuilds only when RunModifiers.Revision changes rather than diffing the list per frame, and on the loadout screen (Assets/_Game/UI/Code/Screens/LoadoutScreen.cs), built from the same RunModifiers.Owned() call.

The Loadout's "NOT YET OFFERED" section is where a withheld boon becomes visible, and it is the rule-9 half of the gate: a mechanic the player is never offered and never told about is a mechanic they do not know exists. One greyed row per withheld modifier, naming the purchase that unlocks it — LoadoutScreen.DrawWithheld, built from the ability and upgrade catalogs rather than hard-coded, so a campaign that renames or reprices a purchase renames it here too. Greyed rather than hidden, the same precedent the cancel list on that screen already sets: a player deciding whether the Gleam is worth it needs to see what it buys.

The HUD strip does not change at all. It answers "what do I hold", which is a different question, and a strip that also listed what you cannot be offered would be a permanent list of things you do not have.

Testing one right now

The dev loop, not the player's: open the debug panel (F1) → Run (dev) → Per-run modifiers. Toggles and sliders apply immediately, mid-run — unlike the ability toggles above them, which wait for the next run because the level was already generated from the old set. The Budgets now row underneath shows the numbers the controller actually reads, so a slider that says 2 against a game that behaves like 1 is visible rather than mysterious.

All these rows are saveValue = false. A persisted debug value is re-applied at boot over whatever the run earned, silently — the trap that once broke hub camera follow. Run state must never be a panel preference.

05The shopkeeper

All spending happens at ONE hub NPC — the Shopkeeper in 2.Hub — that opens a full-screen tabbed menu: Upgrades, Weapons, Abilities (§04b) and the three move tabs Ground / Air / Bow (§04c). This replaced the old per-item greybox altars: every tab reads a catalog, so a new upgrade, a newly-locked weapon, a new ability or a new move appears automatically with nothing to place in the world.

ShopkeeperNPC — the world trigger

Assets/_Game/Systems/Run/Weapons/ShopkeeperNPC.cs. An InteractZone (so it shares the device-aware interact glyph). Its only job: on interact, MenuRouter.Get<ShopScreen>()?.Open(). One NPC, placed on the path between the spawn and the weapon pedestals.

ShopScreen — the tabbed menu

Assets/_Game/UI/Code/Screens/ShopScreen.cs, a MenuScreen modeled on Settings (shoulder buttons / Q-E switch tabs). Each tab is a (name, builder) pair in one array — they used to be a names array beside a separately-filled row list, joined only by position, so adding a name without its rows threw the moment the player tabbed onto it. Upgrades iterates RunDirector.MetaCatalog.upgrades; Weapons iterates RunDirector.Weapons.LockedWeapons(); Abilities and the three move tabs iterate their catalogs. The row list is a ScrollView bounded at 420px — sized against the 21:9 logical viewport (~636px), not 16:9 — with ScrollTo following the selection: an unbounded list grew the panel until the title and the hint bar were clipped off both edges of the screen. Rows show a name + a blurb (MetaUpgrade.description / WeaponDefinition.Description — this tab is the only place a weapon's Description reaches the player) on the left, level/cost + your balance on the right; Submit buys inline via TryBuyUpgrade / TryUnlockWeapon (no confirm popup); a done row can't be re-bought, and its cost column says a word instead of a price — UNLOCKED (weapons, abilities), LEARNED (moves) or MASTERED (upgrades).

Opened from the world, so — unlike Settings, whose opener already froze the game — the shop pushes MenuState itself (freeze + UI input map), like Pause/Death. Owned/affordable state is snapshot on open and after each buy, never polled per-frame (those reads hit the save file). The weapon pedestals (Combat §09) stay separate: the shop is where you unlock a weapon permanently; the pedestals are the per-run random pick from what you've unlocked.

All progression lives on MetaProgress (the survives-death profile) and the suspended RunSave. JsonUtility has no dictionaries, so maps are parallel arrays; the format is wiped, not migrated — new fields are safe with no version bump.

07Recipes

Retune the reward curve

Edit Assets/_Game/Systems/Run/Resources/Economy.asset — an EconomyDefinition, in the inspector or under the Workbench's Economy category. Everything downstream — trickle, run-end bonus, the "+N Gleam" display — recomputes from it, because all eight read sites go through Economy.Current. Re-run Gleamwood ▸ Run PlayMode Tests; RunDirectorTests asserts the earn/bank math.

Do not go looking for constants in Economy.cs. It has none — it is six properties over the resolved asset, and the nearest thing that looks like constants, EconomyDefinition's field initialisers, is the shipped default and the no-asset fallback (§02). Retuning those gives a green build and no runtime change at all, silently, because the asset wins. To retune for one campaign instead of for the game, write an [Economy] section in that campaign's Progression/*.ini rather than touching the asset.

Add a kit upgrade (existing effect)

  1. Author a MetaUpgradeDefinition asset into Systems/Run/Resources/KitUpgrades/ (inspector or Workbench): a stable id (it is a save key), displayName, description, an effect from the MetaEffect enum, perLevel, maxLevel, baseCost, costGrowth.
  2. List it in MetaUpgradeCatalog.definitions, in shop order, then run Gleamwood ▸ Dev ▸ Run ▸ Bake Kit Upgrades. The baked upgrades array is what everything reads — the definitions are not expanded at load, because expanding would mean cloning the shipped ScriptableObject and a clone breaks the invariant ProgressionModTests pins (with no campaign active, Load() must hand back the SHIPPED asset). Baking moves the risk to drift between the two, which is exactly what ProgressionIdTests.TheUpgradeDefinitions_ExpandToExactlyTheShippedArray catches — so a forgotten bake fails a test rather than shipping a phantom row.
  3. That's it — the shopkeeper's Upgrades tab reads the baked array, so the new row appears automatically. No prop to place, no wiring; the apply seam for that MetaEffect already exists.

Add a kit upgrade (NEW effect)

  1. Add a value to the MetaEffect enum.
  2. In RunDirector.RecomputeMetaBonuses, cache its total; expose a read-only property.
  3. Read that property at the ONE place the effect applies (mirroring the max-HP / damage / start-level seams). Add a test to RunDirectorTests.

Lock a weapon behind an unlock

  1. On the WeaponDefinition, set lockedUntilUnlocked = true and an unlockCost. Keep it in the WeaponCatalog + its loot table — the offer gate handles the rest.
  2. Write its Description (Workbench → Identity). Gating the weapon is what makes that field player-facing: it becomes the blurb under the name on its shop row. Leave it empty and the row shows a bare name.
  3. Done. It hides from offers until bought, resumes cleanly if a saved run already holds it, AND appears in the shopkeeper's Weapons tab automatically (that tab is WeaponCatalog.LockedWeapons()).

Add a movement ability

  1. Add a flag to PlayerAbilities.
  2. Teach RoomReachability.Metrics.For what it does — this is the only place a flag becomes movement, and every room's requirement re-derives itself from it with no content touched.
  3. Gate it in the controller so the player genuinely cannot use it unlocked: a bool property on PlayerContext (a field is invisible to DynamicCondition), folded into every edge that reaches the ability — both the data-driven ones in PlayerDef.asset and the code-driven ones in PlayerStateMachine. Count them; the dash has seven.
  4. Author an AbilityDefinition asset (Workbench → Abilities, or Create ▸ Gleamwood ▸ Ability into Resources/Abilities/): a stable id (it is a save key), the flag it grants, and a cost. Add it to Resources/AbilityCatalog.asset — or seed it into PlayerAbilityCatalog.Defaults and run Gleamwood ▸ Dev ▸ Run ▸ Generate Progression Assets, which creates what is missing and never overwrites an existing asset. The shopkeeper's Abilities tab reads the catalog, so the row appears automatically.
  5. Write a discriminator in ReachabilityDiscriminatorTests: geometry that is traversable with the ability and not without. A term nobody can demonstrate is a term that has quietly stopped working.

Add a directional move to the shop

  1. Author the move on the weapons (AerialAttacks / GroundAttacks) as usual — the shop sells access, not content.
  2. Add a bit to MoveSet and a case to MoveKey.Of / MoveKey.For's table. Never hand-write MoveSet.All — it is composed from its members precisely so a new bit cannot be silently left out of it.
  3. Author a MoveDefinition asset (Workbench → Moves, or Create ▸ Gleamwood ▸ Move into Resources/Moves/) with a stable key (it is a save key and a mod-file address), the input line, and a cost — then list it in Resources/MoveCatalog.asset. Same generator and the same trap as the abilities: the seed creates, the asset rules, so editing MoveCatalog.Defaults after its asset exists changes nothing at runtime. Nothing else to wire: the shop tab and the F1 toggles both build from the catalog.
  4. Decide whether it is free. The baseline is not generosity — it holds the moves other systems depend on existing: the aerial fallback, the bow's neutral aim, and the running shot the split rig has always allowed. If withholding your move would break a fallback rather than gate content, it belongs in Baseline, and say why in a comment. Gating content is not a reason to make it free — the launcher gates four executions and sells anyway, at a price low enough to be the first purchase.
  5. MoveUnlockTests.TheBaselineAndTheShop_TogetherCoverEveryMove will fail until the move is either free or sellable — that is the point: a move that is neither is authored, animated, permanently dead content.

Add a per-run modifier

  1. Author a RunModifierDefinition asset (Workbench → Run Upgrades, or Create ▸ Gleamwood ▸ Run Modifier into Resources/RunModifiers/): a stable id (it is a save key), a display name, a description that says what the rule becomes, an effect, and a maxStacks. Then list it in Resources/RunModifierCatalog.asset — the offer roll walks that list, so an asset nobody listed exists and is never offered.
  2. Decide the cap by asking what it bounds. If the modifier feeds a budget, is that budget the only thing that ends a loop? If so, the cap is a safety property, not balance — say so in the entry.
  3. Read it at exactly one seam, with the base value written out: RunModifiers.Budget(RunEffect.AerialAttacks, 1), its float sibling Scale, or RunModifiers.Has(id). Two seams reading the same modifier is two rules that will drift. Budget and Scale are keyed by the effect, not the id — so a modifier reusing an effect that already has a seam needs no C# at all.
  4. Nothing to wire for the dev panel — F1 ▸ Run (dev) builds a row per catalogue entry. Add the new budget to the Budgets now readout if it is a number.
  5. Test it through the game, not through the counter. Asserting RunModifiers.Count passes even when the seam never reads it; ComboCancelTests.TheRunCanBuyMoreCancels counts swings instead.
Persistence and clearing are free — RunDirector already writes on suspend, reads on resume, and clears at StartRun and ClearActive. A new modifier inherits all of it.

08How it's guarded

The whole loop is headless-testable — no scenes needed — because RunDirector is a static service over a real save slot. A dozen test classes hold it, and each of them exists because a different thing on this page can rot independently.

Test classWhat it refuses to let break
RunDirectorTestsThe earn/bank/survive-death currency math, suspend/resume of the in-run wallet, buying upgrades (debit, cap, unaffordable), the applied bonuses at StartRun and their reset at the hub, weapon unlock/hide, and the LootTable offer gate — locked out until bought, offered after.
