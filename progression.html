Progression & the Gleam Economy

The Hades-style spine: a run earns Gleam, death or victory banks it, and between runs it buys permanent kit upgrades and weapon unlocks. This page is the map of every number, seam and save field in that loop — and the one rule that keeps a locked weapon from bricking a saved run.

01The loop in one picture

Every run makes permanent progress — that is the whole reason to replay. Currency accrues during the run, and is banked into the permanent profile whether you clear or die.

One owner, one choke point. RunDirector (static) owns run state; EndRun(bool died) is the single run-over path — death anywhere and the Results screen after a clear both route through it, so banking can never be skipped. All slot writes go through its private WriteSlot funnel.

02The currency — one file, four numbers

Everything about how much a run earns lives in Assets/_Game/Systems/Run/Economy.cs — a static tuning class, so the curve is read and changed in one place.

ConstantValueMeaning
CurrencyName"Gleam"Display name everywhere. Rename here to re-theme the whole economy.
PerKill2Awarded per enemy felled inside a biome — the moment-to-moment trickle (RunDirector.ReportKill).
PerDepth20Run-end bonus per depth tier reached — rewards pushing deeper.
ClearBonus100Extra on a full clear, over a death at the same depth.

The run-end lump is RunEndBonus(depth, clear) = max(0, depth) × 20 + (clear ? 100 : 0), added on top of the accumulated per-kill trickle. The same function feeds the run-over screen's "+N Gleam" line and the actual bank, so the number the player sees is exactly what is credited.

Earned — during the run

Each kill inside a biome adds PerKill to RunDirector.RunCurrency (the in-run wallet). It is written into the suspended-run blob (RunSave.runCurrency) at every room entry, so quitting mid-run never loses it.

Banked — at run end

EndRun adds RunCurrency + RunEndBonus(depth, clear) to MetaProgress.currency. On a death too — that is the Hades promise: no run is wasted.

Shown — on the run-over screens

The Death and Results screens read BuildStats().currencyEarned and show "+N Gleam". RunDirector.CurrencyBalance reads the banked total for the hub (reads disk — call it on hub entry, not per frame).

Want the curve authored live instead of in code? Promote these four constants to [Tunable] fields or a small ScriptableObject — the seam is called out in Economy.cs's own summary. Until then, it is deliberately one file.

03Permanent kit upgrades

Between runs, Gleam buys stacking, permanent boosts — Hades' "Mirror of Night". The catalog is one shipped asset, Assets/_Game/Systems/Run/Resources/MetaUpgradeCatalog.asset, loaded by name; three upgrades ship today.

UpgradeEffectPer levelMaxCost curveApplies at (seam)
VigorMaxHp+1 max health580 · 140 · 200 · 260 · 320PlayerStateMachine.Awake, before ResetProperties
MightDamagePercent+6% weapon damage5120 · 210 · 300 · 390 · 480WeaponInstance.DamageScale (every hit site)
Honed EdgeWeaponStartLevelWeapons start +1 level2150 · 350WeaponInstance ctor at EquipDefaults

Cost of the nth level is baseCost + (n−1) × costGrowth; the magnitude owned is level × perLevel. At StartRun / resume, RunDirector reads the slot's owned levels through MetaUpgradeCatalog.TotalBonus and caches the three totals (MetaMaxHpBonus, MetaDamageMult, MetaWeaponStartLevel) — so the per-hit / per-scene consumers read a cheap value and never touch disk. Off a run every total is a clean no-op (damage ×1, +0 HP), so the sandbox is unaffected.

Why the apply lives where it does. The player's context is re-cloned for every biome, so max-HP is re-stamped in Awake each scene rather than once. Damage rides the per-run WeaponInstance (shared weapon SOs are never mutated — see the Combat page's instance rule). One effect → one seam; new effects arrive as new mechanics land.

Deferred by design: dash-charge and forge-charge upgrades are drafted but not shipped — the player has a single cooldown-gated dash (no charge pool) and the forge is a per-rest boolean (not a count). Both need a charge mechanic before the MetaEffect can apply, so they are intentionally absent rather than dead.

04Weapon unlocks

A weapon can be held back until it is bought at the hub — the "new weapon" carrot. Two ship locked: the Solar Greatsword (300 Gleam) and the Dagger Unseen (250 Gleam).

Any WeaponDefinition carries an optional lock, authored in the inspector (or the Workbench):

FieldMeaning
lockedUntilUnlockedWhen true, the weapon is not offered in loot rolls / hub pedestals until its unlock is owned on the active slot.
unlockCostGleam price to permanently unlock it. The unlock is keyed by the weapon asset name and appended to MetaProgress.unlockIds.

RunDirector.IsWeaponUnlocked(def) answers "may this be offered?" — true for any non-locked weapon, and for a locked one whose id is on the slot. TryUnlockWeapon(def) is the buy: it checks the weapon is locked, unbought and affordable, debits the Gleam and records the unlock. Off a save slot (sandbox) locked weapons simply stay hidden.

The one rule — gate at OFFER time, never at RESOLVE time. The unlock check lives in exactly one predicate: LootTable.Qualifies, the filter every roll and pedestal offer passes through. A locked weapon stays in the catalog and the loot tables; it is only kept out of the offer. That is deliberate — WeaponCatalog.Resolve turns saved weapon ids back into definitions when a suspended run resumes, so gating there would brick a saved run that already holds the weapon. Add unlock logic to Qualifies; never to Resolve.

04bMovement abilities

The Wall Jump (200 Gleam) and the Dash (200 Gleam) are earned, not given. They are the only purchase that changes the shape of the level: the generator refuses to hand out rooms the player cannot clear, so buying one visibly widens what the game builds.

Where they live

PlayerAbilityCatalog (Assets/_Game/Systems/Run/Rooms/) lists them in code, not in an asset — deliberately. It used to share that call with MetaUpgradeCatalog, whose argument was that an asset would only add a second thing a campaign could not retune. That is no longer true of upgrades — a campaign retunes and declares permanent upgrades in Progression/ (Modding §08). Abilities are the one still waiting: they need the same asset migration first, and until then a campaign cannot add or re-gate one. Ownership is MetaProgress.abilityIds, its own array rather than unlockIds (which is keyed by weapon asset name).

The one design knob

PlayerAbilityCatalog.Baseline is what a brand-new profile can do. It ships as None, so both abilities are earned. Set it to PlayerAbilities.All and the entire system becomes inert plumbing — nothing else changes. A profile saved before abilities existed reads as owning none, so existing players buy them too.

An ability is a flag on PlayerAbilities, and adding one touches exactly three places — miss any and the feature is incoherent:

PlaceWhat it decidesWhat breaks if you miss it
RoomReachability.Metrics.ForWhat the movement model believes the flag lets you do.Every room's requirement re-derives to the wrong answer.
Nothing — the generators are genericWhich connections the layout routes through a room.Handled for you: the spine is gated per pair, side paths are not.
PlayerContext + the FSM edgesWhether the player can actually perform it.Rooms are withheld from a player who could have cleared them all along — the gate becomes a tax rather than a progression.
The gate is on the JOURNEY, not the room. What must be clearable is the path the layout actually routes — entry to exit. Every other door is a marker: the ledge you can see and cannot take yet, which is the thing that tells a player an upgrade would open something. RoomTemplate.RequiredForPath(from, to) answers per ordered pair, so one room can be a stroll along its floor and a wall-jump climb to its ceiling at the same time.

Judging a room as a whole is not a stricter version of this — it is a different and wrong question, and it shipped. A lattice junction whose left-to-right corridor is a plain walk was condemned for its ceiling door, the pool lost the only shape that closes a loop, the generator returned nothing, and the player dropped into an empty scene.
PathGated?Why
Entry → Exit (the spine)YesThe run has to be finishable with what they hold on arrival.
Lattice arc (the upper band)NoIt is a loop — both risers land back on the spine — so removing every arc edge still leaves Entry connected to Exit. An unclimbable riser costs nothing.
Branches (side dungeons)NoNothing behind one is needed to finish. A wing you cannot climb today is a reason to come back.
The one refusal that remains. RoomBuilder rejects a room only when a door you can arrive through reaches no other door — judged with every ability unlocked, so it means broken geometry rather than a locked one. A door you merely cannot reach builds fine and is reported as a note, naming which journey is locked behind what.
And the backstop. If a gated pool still cannot build, the gate is lifted for that biome with a loud error rather than returning no layout — a room the player may struggle with beats an empty scene. It should never fire; if it does, the pool is missing a bare-handed room for some shape the topology needs on the main path.

Where the ability set comes from (2026-08-03)

RunDirector.Abilities mirrors the ACTIVE SLOT — except during a run, where it is frozen at whatever the layout was generated from.

It used to be PlayerAbilities.All whenever no run was in flight, and PlayerContext repeated that exemption a second time as !RunDirector.IsRunActive ||. The result was one profile with two kits: you could dash in the hub and not in the run. Hisham, on a build — "it should be the same player so they should have the same abilities."

The escape hatch is now about having no PROFILE, not about being outside a run. With no slot bound, PlayerAbilityCatalog.Owned(null) already answers All, so 3.TestSandbox and any scene opened straight from the Project window still hold the full kit. That needed no special case — it falls out of the same expression, which is the tell that the exemption never should have been about runs.
MomentSeamWhy it must recompute
A slot is bound (new game, continue, restored after a failed launch)RunDirector.BindSlotBinding a slot and deriving what it can DO are one operation. The two bare SaveSystem.ActiveSlot = writes in SaveSlotsController were how a hub ended up holding the previous session's kit.
Run start / resumeRecomputeMetaBonusesFreezes the set the level is generated from.
An ability is bought at the Shopkeeper, or dev-toggledTryUnlockAbility / DebugSetAbilityOwned, guarded by if (!IsRunActive)In the hub it applies at once — otherwise you buy the dash and cannot dash in the room you bought it in. Mid-run it waits, because widening the set would desync it from the level already built.
Death, clear, or quit to titleResetMetaBonusesUsed to hand back All. That was the hub's second source of a kit nobody earned.
Pushed, not computed. SaveSystem.Load hits disk with no cache, and PlayerContext.HasDash is compiled into a DynamicCondition and evaluated every frame — so a per-read getter is impossible. Abilities also stays a settable static because BiomeGenerator widens it to All around generation and restores it in a finally; a computed property would break that seam.

Visible consequence, and it is intended: a brand-new profile stands in the hub with neither dash nor wall jump. The hub is traversable bare-handed, and what you see there is now exactly what you take into the run.
Still gated on IsRunActive, deliberately unresolved: PlayerStateMachine adds MetaMaxHpBonus only during a run, so the hub player also has less max HP than the run player. Vigor is a run boost in a way a dash is not, and RunDirectorTests pins the reset on purpose — so that is a separate decision, not an oversight.

04dThe directional moveset

The moveset went from one swing to nine in a day. Handing all of it over at once is both a worse first hour and a wasted progression axis — Hisham: "in order to make the perm upgrade shop more interesting - should we have to purchase all aerial and directional attacks? this makes a lot of sense". Five of the nine are now bought at the shopkeeper's Ground, Air and Bow tabs — one tab per input family, so the tab name and the row's own instruction line ("Ground: UP + attack") say the same word. It was ONE "Moves" tab until the bow's two purchases took it to eight rows and the panel outgrew the screen; the split is filtered through MoveKey.TryParse, so a new move lands in its tab with no category field to keep in sync.

Why those two are never sold. ground:up is the only move in the shipped data that puts an enemy in the air, and four of the ten executions are gated on a juggled target — selling it means a fresh profile has no launcher, no juggle and four unreachable executions, which is a wall dressed as progression. aerial:neutral is the fallback every aerial leans on: with it unowned, an unowned Up resolves to nothing and an airborne swing plays the grounded combo clip — a planted stance hanging in mid-air, the exact bug the aerial moveset was built to fix. MoveUnlockTests pins both, plus the invariant that every move is either free or sellable (a move that is neither is authored, animated, permanently dead content).

One vocabulary, three uses

MoveKey (Assets/_Game/Combat/Code/Definitions/) is the modding tier's move address, promoted. [Weapon:DefaultSword.aerial:up] was already a published contract with anyone who has written a mod; the same string is now the shop's save key and the imbue's target. Inventing a second spelling would have meant two vocabularies for one idea, and only one of them getting updated. Keys are interned, so the combat seam's per-hit compare is a reference check.

The gate is inside the resolver loop

TryResolve/TryResolveExact take an optional owns predicate, applied per candidate — not to the result. That placement is the whole design: an unowned aerial Up has to fall through to the Neutral aerial exactly as an unauthored one does. Filtering afterwards would return false and leave the swing with no clip at all.

Two questions, two methods. TryGetAerial/TryGetGrounded stay asset oracles — "does this weapon author a move for this direction" — and the Workbench, the wiki capture and the mod loader all keep asking that, because a designer has to be able to see and tune a move nobody has bought. TryGetAerialOwned/TryGetGroundedOwned ask the gameplay question, and only the attack state calls them. Collapsing the two would turn a shop gate into an authoring gate.
Unlike an ability, a move applies IMMEDIATELY — in the hub or mid-run. Abilities are frozen mid-run because the level was generated from them; RoomReachability has no attack term at all, so nothing the generator decided depends on the moveset. You walk out of the shop swinging what you just bought.
Existing profiles buy the five back. A save written before this shipped has an empty moveIds, so it reads as the baseline — the same thing that happens to a new profile. That is the identical call movement abilities made, and for the identical reason: the alternative is granting them silently, which would mean no existing player ever sees the feature. Three testers, early-stage saves, ~570 Gleam total.

04cPer-run modifiers — rules, not numbers

The third tier, and the newest. A run modifier is a mechanical rule change the player picks up during a run and loses when it ends. Hisham's framing, which is why the tier exists: "the idea is we can have a bunch of mechanical things like this on a per run basis."

TierScopeChangesLives on
Kit upgrades & abilities (§03, §04b)PermanentNumbers, and two movement verbsMetaProgress; frozen for the duration of a run
The forge (UpgradeTrack)Per runNumbers only — a damage and execution-point multiplierWeaponInstance.UpgradeLevel

Where they live

RunModifierCatalog and RunModifiers (Assets/_Game/Systems/Run/). The catalog is now one asset per modifier plus an ordered catalog asset in Resources/, authored in the Workbench's Run Upgrades tab and retunable from a campaign's Progression/ folder (Modding §08). The order is load-bearing: the offer roll walks the catalog, so a seed only reproduces if the list does. The shipped four survive in code as a fallback and as what the generator writes the assets FROM — and because moving to assets deleted the compile-error-on-rename protection the const strings gave, which is why an id-stability test now pins them against a literal list. RunModifiers is a static dictionary of id → stacks; reading it is one lookup, so a combat seam can ask on every swing.

Every modifier has a CAP, and it is load-bearing

maxStacks is not a balance knob bolted on afterwards. Several of these raise a budget that is the only thing bounding a loop — a cancel restarts the same combo index with a fresh timer, so an unbounded cancel budget is a state the player never leaves. RunModifierTests.EveryCatalogEntry_IsUsable refuses an uncapped entry.

Updraft is TARGETED: it imbues one rolled move. The ground up-attack is the launcher by default and always will be — but which other move also launches is rolled per run from the seed, so a run where the down-air launches plays differently from one where the running attack does. RunModifierRoll owns the roll; the target is stored on the run rather than re-derived, because a weapon's moveset can be rewritten from text between sessions and a seed-derived target would silently relocate on resume — the failure class RunWebFingerprint exists to refuse for layouts.

Two moves are never rolled. ground:up already launches, so imbuing it spends the modifier on nothing. ground:down is the Crumple, and the two are contradictory in a way that deletes the move: Crumple zeroes knockback to pin a target where it stands, and launching immediately overwrites the body's velocity — "pin them" would become "throw them", and the Pinfall execution would stop being reachable.

Updraft cannot become an infinite, and that is structural rather than tuned. EnemyStateMachine only honours isLauncher against a grounded target — you cannot launch something that is already up there. So an up-air that launches is a second opener, never a way to keep a target airborne. Any future "X also launches" modifier inherits the same guarantee for free.
Where the base value lives. At the seam, not in the catalog: RunModifiers.Budget(id, 1) written out at the call site reads as "you get one, and the modifier adds more". A bare Budget(id) returning 1 by magic would hide the number a designer actually wants to change.

Testing one right now

Open the debug panel (F1) → Run (dev) → Per-run modifiers. Toggles and sliders apply immediately, mid-run — unlike the ability toggles above them, which wait for the next run because the level was already generated from the old set. The Budgets now row underneath shows the numbers the controller actually reads, so a slider that says 2 against a game that behaves like 1 is visible rather than mysterious.

All these rows are saveValue = false. A persisted debug value is re-applied at boot over whatever the run earned, silently — the trap that once broke hub camera follow. Run state must never be a panel preference.

05The shopkeeper

All spending happens at ONE hub NPC — the Shopkeeper in 2.Hub — that opens a full-screen tabbed menu: Upgrades, Weapons, Abilities (§04b) and the three move tabs Ground / Air / Bow (§04d). This replaced the old per-item greybox altars: every tab reads a catalog, so a new upgrade, a newly-locked weapon, a new ability or a new move appears automatically with nothing to place in the world.

ShopkeeperNPC — the world trigger

Assets/_Game/Systems/Run/Weapons/ShopkeeperNPC.cs. An InteractZone (so it shares the device-aware interact glyph). Its only job: on interact, MenuRouter.Get<ShopScreen>()?.Open(). One NPC, placed on the path between the spawn and the weapon pedestals.

ShopScreen — the tabbed menu

Assets/_Game/UI/Code/Screens/ShopScreen.cs, a MenuScreen modeled on Settings (shoulder buttons / Q-E switch tabs). Each tab is a (name, builder) pair in one array — they used to be a names array beside a separately-filled row list, joined only by position, so adding a name without its rows threw the moment the player tabbed onto it. Upgrades iterates RunDirector.MetaCatalog.upgrades; Weapons iterates RunDirector.Weapons.LockedWeapons(); Abilities and the three move tabs iterate their catalogs. The row list is a ScrollView bounded at 420px — sized against the 21:9 logical viewport (~636px), not 16:9 — with ScrollTo following the selection: an unbounded list grew the panel until the title and the hint bar were clipped off both edges of the screen. Rows show a name + a blurb (MetaUpgrade.description / WeaponDefinition.Description — this tab is the only place a weapon's Description reaches the player) on the left, level/cost + your balance on the right; Submit buys inline via TryBuyUpgrade / TryUnlockWeapon (no confirm popup); owned/mastered rows read UNLOCKED/MASTERED and can't be re-bought.

Opened from the world, so — unlike Settings, whose opener already froze the game — the shop pushes MenuState itself (freeze + UI input map), like Pause/Death. Owned/affordable state is snapshot on open and after each buy, never polled per-frame (those reads hit the save file). The weapon pedestals (§00) stay separate: the shop is where you unlock a weapon permanently; the pedestals are the per-run random pick from what you've unlocked.

06What is saved

All progression lives on MetaProgress (the survives-death profile) and the suspended RunSave. JsonUtility has no dictionaries, so maps are parallel arrays; the format is wiped, not migrated — new fields are safe with no version bump.

Ids are save data. An upgrade id and a weapon asset name are the keys players own progress by — renaming one silently orphans everything bought under the old name. Treat them like a database primary key. (The tooltip on MetaUpgrade.id says exactly this.)

07Recipes

Retune the reward curve

Edit the four constants in Economy.cs. Everything downstream — trickle, run-end bonus, the "+N Gleam" display — recomputes from them. Re-run Gleamwood ▸ Run PlayMode Tests; RunDirectorTests asserts the earn/bank math.

Add a kit upgrade (existing effect)

  1. Open Resources/MetaUpgradeCatalog.asset (inspector or Workbench) and add an entry: a stable id, displayName, description, an effect from the MetaEffect enum, perLevel, maxLevel, baseCost, costGrowth.
  2. That's it — the shopkeeper's Kit Upgrades tab reads the catalog, so the new row appears automatically. No prop to place, no wiring; the apply seam for that MetaEffect already exists.

Add a kit upgrade (NEW effect)

  1. Add a value to the MetaEffect enum.
  2. In RunDirector.RecomputeMetaBonuses, cache its total; expose a read-only property.
  3. Read that property at the ONE place the effect applies (mirroring the max-HP / damage / start-level seams). Add a test to RunDirectorTests.

Lock a weapon behind an unlock

  1. On the WeaponDefinition, set lockedUntilUnlocked = true and an unlockCost. Keep it in the WeaponCatalog + its loot table — the offer gate handles the rest.
  2. Write its Description (Workbench → Identity). Gating the weapon is what makes that field player-facing: it becomes the blurb under the name on its shop row. Leave it empty and the row shows a bare name.
  3. Done. It hides from offers until bought, resumes cleanly if a saved run already holds it, AND appears in the shopkeeper's Weapon Unlocks tab automatically (that tab is WeaponCatalog.LockedWeapons()).

Add a movement ability

  1. Add a flag to PlayerAbilities.
  2. Teach RoomReachability.Metrics.For what it does — this is the only place a flag becomes movement, and every room's requirement re-derives itself from it with no content touched.
  3. Gate it in the controller so the player genuinely cannot use it unlocked: a bool property on PlayerContext (a field is invisible to DynamicCondition), folded into every edge that reaches the ability — both the data-driven ones in PlayerDef.asset and the code-driven ones in PlayerStateMachine. Count them; the dash has seven.
  4. Add an entry to PlayerAbilityCatalog.All with a stable id (it is a save key) and a cost. The shopkeeper's Abilities tab reads the catalog, so the row appears automatically.
  5. Write a discriminator in ReachabilityDiscriminatorTests: geometry that is traversable with the ability and not without. A term nobody can demonstrate is a term that has quietly stopped working.

Add a directional move to the shop

  1. Author the move on the weapons (AerialAttacks / GroundAttacks) as usual — the shop sells access, not content.
  2. Add a bit to MoveSet and a case to MoveKey.Of / MoveKey.For's table. Never hand-write MoveSet.All — it is composed from its members precisely so a new bit cannot be silently left out of it.
  3. Add a MoveDef to MoveCatalog.All with a stable key (it is a save key and a mod-file address), the input line, and a cost. Nothing else to wire: the shop tab and the F1 toggles both build from the catalog.
  4. Decide whether it is free. The baseline is not generosity — it holds the moves that other systems depend on existing (the launcher, the aerial fallback). If withholding your move would break a fallback or make content unreachable, it belongs in Baseline, and say why in a comment.
  5. MoveUnlockTests.TheBaselineAndTheShop_TogetherCoverEveryMove will fail until the move is either free or sellable — that is the point: a move that is neither is authored, animated, permanently dead content.

Add a per-run modifier

  1. Add an entry to RunModifierCatalog.All: a stable id (it is a save key), a display name, a description that says what the rule becomes, and a maxStacks. Add a const for the id beside the others so seams do not spell it by hand.
  2. Decide the cap by asking what it bounds. If the modifier feeds a budget, is that budget the only thing that ends a loop? If so, the cap is a safety property, not balance — say so in the entry.
  3. Read it at exactly one seam, with the base value written out: RunModifiers.Budget(id, 1) or RunModifiers.Has(id). Two seams reading the same modifier is two rules that will drift.
  4. Nothing to wire for the dev panel — F1 ▸ Run (dev) builds a row per catalogue entry. Add the new budget to the Budgets now readout if it is a number.
  5. Test it through the game, not through the counter. Asserting RunModifiers.Count passes even when the seam never reads it; ComboCancelTests.TheRunCanBuyMoreCancels counts swings instead.
Persistence and clearing are free — RunDirector already writes on suspend, reads on resume, and clears at StartRun and ClearActive. A new modifier inherits all of it.

08How it's guarded

The whole loop is headless-testable — no scenes needed — because RunDirector is a static service over a real save slot.

  • RunDirectorTests covers the earn/bank/survive-death currency math, suspend/resume of the in-run wallet, buying upgrades (debit, cap, unaffordable), the applied bonuses at StartRun and their reset at the hub, weapon unlock/hide, and the LootTable offer gate — locked out until bought, offered after.
  • Part of the PlayMode suite. Run it with Gleamwood ▸ Run PlayMode Tests → Logs/playmode_test_results.txt.
