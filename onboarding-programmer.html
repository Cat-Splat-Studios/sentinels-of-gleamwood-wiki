Programmer Onboarding

Day one, for an engineer who is good at their craft and knows nothing about this project. What the architecture is and why, the ten rules that were each paid for with a real bug, the directory and assembly map, the state machine that is the spine of every character, the Content Workbench in full, how to prove you did not break anything, and the recipes for the things you will be asked for first.

01What this is, architecturally, in one screen

Sentinels of Gleamwood is a 2D side-on action roguelite in Unity 6000.5.2f1 on the 2D Universal Render Pipeline. A run walks a web of biome nodes, each biome generates its rooms from a pool, and the player keeps permanent currency between runs. That is the game. The architecture is decided by something bigger than the game.

The north star: a campaign is a whole game. The destination is a maker mode — Gleamwood becomes a 2D roguelite maker, and the game you can play today ships as its own first campaign. Test every design you propose against one question: "if a campaign supplied all of it, would anything of mine still be load-bearing?"

That is why data-driven is not a preference here, it is the architecture. A feature that only a C# edit can author is a feature the maker mode cannot offer. If you find yourself writing a switch over content, or hard-coding a list of weapons, or adding a per-type branch to a tool — stop. The shape you want is a ScriptableObject that declares itself and a system that discovers it. Source: the root CLAUDE.md.

Three consequences you will feel within an hour:

Content is assets, never code

Weapons, enemies, biomes, statuses, run modifiers, moves, abilities, dialogue — every one is a ScriptableObject. The runtime reads definitions; it never names a specific one except through a catalog asset.

Tools are grown by declaration

[WorkbenchCategory] grows a Workbench tab. [Tunable] grows an F1 slider. [AnimatorStateRef] turns a string into a validated dropdown. You never edit the tool.

Say "deferred to X" out loud

Descoping silently reads as abandonment. When you cut something, write the deferral into the doc in the same commit. This is a stated project rule, not politeness.

04The state machine — the spine of the player and every enemy

One generic FSM drives both characters. Framework §01–§05 is the reference for the type model and the editor tools, and state_machine_api_reference.md carries the signatures. This section is the part you need in your head before you read either: how a graph is assembled at runtime, why the asset is not the truth, and the four ways an edge dies without an error.

The shape

StateMachine<TContext>            // MonoBehaviour. Owns states + transitions.
  └─ PlayerStateMachine          // : StateMachine<PlayerContext>   [DefaultExecutionOrder(-110)]
  └─ EnemyStateMachine           // : StateMachine<EnemyContext>, IHittable

IState<TContext>
  └─ StateBase<TContext, TStateMachine>                 // TWO generics. There is no single-generic base.
       └─ ConfigurableState<TContext, TConfig, TStateMachine>
            └─ PlayerState / every Enemy*State

A state is a plain C# object, not a component. It is constructed from a config ScriptableObject which is a sub-asset of the definition (PlayerDef.asset, each *Def.asset under Enemies/Data/). Expand the .asset in the Project window and the configs are inside it.

How a graph is actually assembled — two passes, and this is the seam

  1. Register every state first. PlayerStateMachine.InitializeFromDefinition() walks Definition.States, calls config.CreateState(), and registers it under config.StateName — falling back to the sub-asset's name when StateName is blank. RegisterState calls state.Init(this, context) and throws on a duplicate id.
  2. Then call SetupTransitions() on every registered state. Two passes, in that order, is what lets an edge name a state that had not been created when its own config was read. Both machines do it.
  3. ConfigurableState.SetupTransitions() walks the config's Transitions list, resolves each ToState by StateId, pre-compiles the dynamic predicates, folds every condition into one composite Func<bool>, and registers it — always at priority 0, never with an onTransition action. An unresolvable target logs a warning and is skipped.
  4. A hybrid state then adds its own hardcoded edges after base.SetupTransitions(). That is where rule 5 lives.
StateName vs StateId vs the asset name — three things, and they are not the same. The two machines register differently. EnemyStateMachine registers under the raw StateName; PlayerStateMachine falls back to the sub-asset's name when StateName is blank, exactly as StateId does (step 1 above). Transitions on both sides resolve by StateId, which is StateName if set and the asset name otherwise. Two failure modes fall out and neither is visible until something breaks mid-run:
  • A blank StateName on an enemy config registers a state under "" that no transition can ever reach. This is the one the player's fallback saves you from — and only the player's.
  • A duplicate StateName makes RegisterState throw, on either machine.
The shipped player graph used to rely on this fallback, and no longer does: the sub-asset PlayerRunConfig inside PlayerDef.asset shipped with an empty StateName until 2026-08-12, so the run state was registered and addressed as PlayerRunConfig rather than run. It reads run now, matching its eight siblings, so the Workbench no longer greets a designer with a permanent red row on first-party content. Nothing broke either way, because no player code looks the run state up by string — the only string lookup in PlayerStateMachine is TryGetState("idle", …) for the sandbox respawn edge, and everything else uses GetState<T>(). The fallback itself is still real and still load-bearing for any asset made by hand — do not assume an id from a state's colloquial name. The Workbench's States sub-tab shows blanks and duplicates as red rows before you leave the window.

Authored transitions — two condition lists, both ANDed

A TransitionDefinition row carries a target plus two lists, and this is the pair that catches people reading an authored graph: an edge that "has no conditions" may have all of them in the other list.

ListTypeWhat it is
ConditionsTransitionCondition<TContext> (ScriptableObject)Hand-written, type-safe: override bool Check(TContext context). The Creator's Condition Creator tab (Framework §05) generates one into …/Definitions/Transitions/Conditions/, and since 2026-08-12 it honours the Target System all the way down: FindProjectBase hunts for whatever abstract type already derives from TransitionCondition<thatContext> and takes its name and its namespace from it. Player therefore resolves to Player.Definitions.Transitions.PlayerTransitionCondition under Player/Code/, Enemies to Enemies.Definitions.Transitions.TransitionCondition under Enemies/Code/, and both compile. It used to hard-code the enemy pair while letting only the Check parameter follow the selector, which wrote a file into the player folder overriding Check(PlayerContext) on a base whose method takes EnemyContext — the half-honoured dropdown that made an unfinished path look like a supported one. What survives is the fallback, and it is the enemy pair: a context with no abstract condition base of its own still resolves to Enemies.Definitions.Transitions/TransitionCondition and lands back in exactly that trap. Both shipped contexts have a base, so nothing hits it today — if you add a third system, write its abstract condition base before you generate a condition for it.
DynamicConditionsDynamicCondition (ScriptableObject)No-code: name a property on the context, pick an operator (Equal, NotEqual, Greater, Less, GreaterOrEqual, LessOrEqual, IsTrue, IsFalse), give a value. Create via Assets ▸ Create ▸ StateMachine ▸ Dynamic Condition. The player's live set is Assets/_Game/Player/Data/SharedRules/Dy_*.asset — Dy_IsGrounded, Dy_CanGroundJump, Dy_AerialAttackNotUsed, Dy_IsDashReady and the rest of the Dy_ family. Look there before authoring a new one; they are shared across edges by design, and the enemy side has its own set under Assets/_Game/Enemies/Data/EnemyDefinitions/SharedRules/.

Everything ANDs. Every condition in both lists must pass. An empty pair of lists means fires unconditionally the moment it is checked.

Three things about DynamicCondition that will cost you an afternoon each.
  • Only PROPERTIES are addressable. It builds Expression.Property(param, PropertyName). A public field with the right name compiles nothing and fails — the error message says so explicitly.
  • It fails closed and it caches the failure. A bad PropertyName logs one error and the predicate permanently returns false for the rest of the session. The edge does not error, it just never fires. Caching the failure is deliberate: SetupTransitions runs per machine instance, so an uncached failure re-threw on every single enemy spawn.
  • Binding is by name and type, so a type change breaks the edge with no compile error. A bool read by a DynamicCondition must stay a bool — this is why PlayerContext.AerialAttackUsed is a bool and not a count.
The compiled-predicate cache is keyed by (asset instance id, context type) and both halves survive a play session with Disable Domain Reload on — which is why GameBootstrap.ResetStatics calls DynamicCondition.ClearCache() every play session. Without it an edited condition keeps evaluating the OLD expression until the editor restarts.

Reading a graph: the live dictionary, never the asset

This is the single most useful habit on this page. PlayerDef.asset lists edges that may not exist at runtime, because a hybrid state's hardcoded AddTransition deleted them (rule 5). Four of meleeAtk's five authored edges are already in that state.

  1. Play once and read the console. Every collision logs [StateMachine] FromType->ToType: a registered transition REPLACED n existing one(s)…, once per pair per session. That list is the set of authored edges your code has overwritten — no file reading required.
  2. Open the Visualizer — Cat Splat State Machine ▸ State Machine Visualizer. One state centred, incoming edges left, outgoing right, with a Live View toggle. Machines self-register at runtime: the player as PlayerStateMachine, enemies as "Name (EntityId)".
  3. Or tick debugMode on the machine component (or call EnableDebug()) for a console line on every state change.
  4. Only then open the asset — and read it as a proposal, not as the graph.

Which player states are pure data (your config edits win) and which are hybrids (they may not) is tabulated on Framework §04. PlayerRunState, PlayerIdleState and PlayerFallState are nothing but base.SetupTransitions(); Jump, Dash, WallSlide, MeleeAttack, DashAttack and BowAim are hybrids.

Drive the real input, not ChangeState. Player FSM edges live in DynamicConditions on the definition asset, not in string-named conditions. A test that forces ChangeState false-passes on every path the game never actually takes. Reproduce with buffered input, and log the clip / normalized time / sprite before asserting. ChangeState in a test is defensible only when the entry edges are covered elsewhere and everything under test happens inside one state entry — ComboCancelTests says exactly that in its header, and that is the bar.

Adding to the machine — the one correct route

  1. Only if the state TYPE does not exist: Cat Splat State Machine ▸ Tools ▸ State Machine Creator → State Creator → pick the Target System, name it, choose the base config, add variables → Generate. It writes two files into two different folders under the feature's code root: {Name}Config.cs into <root>/Definitions/States/ and {Name}State.cs into <root>/States/ — so Assets/_Game/Player/Code/Definitions/States/ and Assets/_Game/Player/Code/States/, or the same pair under Assets/_Game/Enemies/Code/. The state class is the one you edit, and its stub overrides only Enter(). Wait for the compile.
  2. Create the state asset in the Workbench, never by hand: Gleamwood ▸ Content Workbench → Enemies (or Bosses) → the States sub-tab → + Create State. On the Player tab there is no States sub-tab: select Balen (State Machine) and the whole page is that surface, + Create State included. That one action creates the sub-asset, names it, sets StateName, appends it to States, promotes it to InitialState if it is the first, and runs the IStateMachineAssetPostProcessor hooks — atomically. Doing it by hand is how you get a blank StateName.
  3. Wire transitions on the same tab — To State plus its Conditions and DynamicConditions.
  4. Check the validation rows are green, then watch it in the Visualizer.

If you delete a state script, run Maintenance ▸ Cleanup Orphaned & Broken Sub-Assets on the States tab (or right-click the .asset → State Machine ▸ Cleanup Sub-Assets) — sub-assets whose script is gone leave debris that nothing lists.

05The Content Workbench, in full

The Workbench is the designer-facing authoring surface, and as a programmer you will extend it more often than you use it. The Workbench page is the guided tour of every shipped tab and is the source of record for the tab list — do not restate it. This section is the developer's view: what the window actually is, the full form API with signatures, and two worked examples.

What it is

Raw Unity inspectors show every serialized field, including the dead ones. The Workbench shows only the fields the runtime actually reads, split into sub-tabs, with effective values resolved through their fallbacks, sound preview, animator-state validation, and registration checks that tell you whether the asset is wired into the game at all.

Architecturally it is a thin shell. Assets/_Game/Editor/ContentWorkbench.cs contains no hard-coded tab list and no per-type switch. It discovers categories and drives the rail, banner and form entirely through one interface. That is what makes it maker-mode-shaped: a campaign that ships a new SO type gets a full authoring surface without a workbench edit.

Opening it

  • Gleamwood ▸ Content Workbench — [MenuItem("Gleamwood/Content Workbench")] on ContentWorkbench.Open(). Minimum size 780×500. A fresh window opens on tab index 1, which is Melee.
  • Right-click a tunable asset in the Project window → Assets ▸ Open in Content Workbench. The validator enables it for WeaponDefinition, Enemies.Definitions.EnemyDefinition, PlayerContext, BiomeDefinition, MusicSet, or any ScriptableObject whose class carries [WorkbenchCategory].

Routing goes through CategoryIndexFor(asset), which returns the first category whose Owns(asset) is true — and return 0 when none does. Index 0 is whichever category sorts first, which is PlayerCategory at Order => 0. So an unroutable asset silently lands on the Player tab; that is the fallback, not a bug.

Owns() and the context-menu validator are two different gates, and they disagree on the player's own state graph. PlayerCategory.Owns accepts PlayerDefinition, so PlayerDef.asset routes perfectly well — but the validator above does not list that type and it carries no [WorkbenchCategory], so Open in Content Workbench is greyed out on it. Reach it from the rail instead: Player ▸ Balen (State Machine). PlayerSettings.asset (a PlayerContext) does open from the right-click menu.

How a category is registered — there is no registration

WorkbenchCategoryRegistry.Discover() (Workbench/WorkbenchCategory.cs) runs on the window's OnEnable and does exactly two sweeps:

// 1. Every concrete IWorkbenchCategory implementation.
foreach (Type t in TypeCache.GetTypesDerivedFrom<IWorkbenchCategory>())
{
    if (t.IsAbstract || t.IsGenericTypeDefinition) continue;
    if (t.GetConstructor(Type.EmptyTypes) == null) continue;   // AttributeWorkbenchCategory takes args → skipped here
    list.Add((IWorkbenchCategory)Activator.CreateInstance(t));
}

// 2. Every [WorkbenchCategory]-tagged ScriptableObject, grouped by attribute Name.
foreach (Type t in TypeCache.GetTypesWithAttribute<WorkbenchCategoryAttribute>()) { /* … one AttributeWorkbenchCategory per Name … */ }

list.Sort((a, b) => a.Order != b.Order ? a.Order.CompareTo(b.Order)
                                       : string.Compare(a.Title, b.Title, StringComparison.Ordinal));

Consequences worth internalising: the no-parameterless-constructor filter is what stops AttributeWorkbenchCategory being double-counted as a class; ties in Order break by ordinal title; and untagged Order defaults to 100, so a new tab lands after everything shipped. You never edit ContentWorkbench.cs to add a tab.

How sub-tabs work

There is no sub-tab type. A sub-tab is a switch over the index form.SubTabs(...) returned:

public override void DrawForm(WorkbenchForm form, Object asset)
{
    var weapon = (RangedWeaponDefinition)asset;
    var so = form.SO(weapon);
    switch (form.SubTabs("Overview", "Shot & Timing", "Presentation"))
    {
        case 0: /* checks first, then Identity, then Base Combat */ break;
        case 1: /* Draw, Perfect Release, On Hit, The Arrow          */ break;
        case 2: /* Sound, Visuals, Animation, then a footer Note     */ break;
    }
}

The selected index lives on the window (IWorkbenchHost.SubTab), so it survives repaints — but not a domain reload. _subTab, _swingIndex and _tab are plain private fields with no [SerializeField], so any script recompile drops you back on the default rail tab and the first sub-tab. It is also reset to 0 whenever you switch rail tab or select a different asset. SwingTabs is a completely independent second strip backed by IWorkbenchHost.SwingIndex, reset at the same moments. Both are single-instance per window — you get one primary strip and one secondary strip per page, which is a deliberate ceiling on how deep a form may nest.

The save model

It mirrors Unity's Input Actions editor. Edits hit the in-memory asset immediately; disk writes are explicit.

  • Manual (default). Editing marks the asset dirty; a red unsaved changes label appears and the window title becomes Content Workbench*. Save Asset flushes every dirty object in the cache.
  • Auto-Save. The toolbar toggle writes after every change and immediately saves anything outstanding when switched on. Persisted per machine in EditorPrefs under Gleamwood.Workbench.AutoSave, default off. The Save Asset button is disabled only while Auto-Save owns saving — a clean-state click is a harmless no-op.
  • Sub-assets ride along. Saving resolves each dirty object's path and calls AssetDatabase.SaveAssetIfDirty on the main asset, so enemy state configs and the bow-aim config save with their parent.
  • Undo works — every edit goes through a SerializedObject, so Ctrl+Z behaves exactly as in the raw inspector.
These are the real, shared assets — there is no draft copy. That is the point (tune, play, tune), but it also means never "experiment" on a shared SO you do not intend to commit. And note the interaction with rule 10: the Workbench edits assets at edit time, which is legitimate; mutating the same SO at runtime is the thing that is forbidden.
The caches no longer all clear on OnEnable, and the split is the thing to know. WorkbenchModel.ResetCaches() now also runs from a WorkbenchCacheInvalidator (an AssetPostprocessor) on every import, which repaints open windows too — the workbench is never the focused window when a registration is fixed, and an unfocused IMGUI window does not repaint itself, so clearing alone would have left the stale answer on screen. Import is the right trigger rather than selection-change: the drag that registers an asset happens with the OTHER asset selected, and Unity re-imports nothing on a selection change, so the dependency record would not have moved either. Consequences: registration checks and boss classification refresh when you save (an Inspector drag is dirty in memory and imports nothing, so the row is honestly still red until then). The SerializedObject cache and the category list are still built once on OnEnable, so a new [WorkbenchCategory] type is the one thing that still needs a reopen.

The New verb

The create row renders at the foot of the rail — below the asset list, deliberately, because creating is the rare action on a tab whose normal use is picking something that exists, and a New button above the list is the one people hit by accident. It appears only when the category declares both CreatableType and NewAssetFolder; every other tab shows nothing at all.

WorkbenchAssetFactory.Create(Type type, string folder, string niceName) is a shared primitive rather than a button per tab, and it does the whole job:

  1. Sanitises the typed name toward the project's lower-case-with-hyphens id convention: lower-cased, letters and digits kept, space / - / _ collapsed to -, everything else dropped, trimmed of leading and trailing hyphens. An empty result falls back to the type name.
  2. Takes a uniquified path via GenerateUniqueAssetPath — pressing New twice makes two assets, not an error or an overwrite. The folder is created if missing.
  3. Seeds id and displayName when the type has those string fields and they are empty. Most content types carry an id that is a save key, and one defaulted to "" is a trap a validator would only catch later.
  4. Creates, registers an Undo, marks dirty, saves and re-imports.
  5. Runs every discovered IWorkbenchAssetCreatedHandler that claims the type, then selects the asset and logs where it went.
// Assets/_Game/Editor/Workbench/WorkbenchAssetFactory.cs
public interface IWorkbenchAssetCreatedHandler
{
    bool Handles(Type assetType);
    void AfterCreate(ScriptableObject asset);   // after it exists on disk and has been imported
}
The created-handler hook is why "I made it and nothing happened" stopped being a bug. A new RunModifierDefinition is not usable until the ordered catalog lists it — the runtime loads that catalog, not the folder, because Resources.LoadAll returns files in an order nobody controls and the offer roll walks the catalog to build its pool. So RunModifierCreatedHandler regenerates it on create. The factory was never taught about run modifiers: the side that knows declares a handler and the factory discovers it — the same declare-don't-wire mechanism as the category attribute itself. If your content type needs a post-create step, write a handler; do not touch the factory.

Worked example A — add a field to an existing page

Goal: give the bow's arrow a downward drift, authored per weapon, on Ranged ▸ Shot & Timing ▸ The Arrow.

  1. Add the serialized field to the definition. Assets/_Game/Combat/Code/Definitions/RangedWeaponDefinition.cs. Give it a [Tooltip] and an initializer whose value means "unchanged", so the field is safe on assets that predate it: 
    [Tooltip("Downward drift on the arrow, u/s². 0 = flat flight.")]
public float ProjectileDrop = 0f;
  2. Make the runtime read it. This is not optional politeness — a field nothing reads is exactly the "granted but not wired" shape of rule 3, and it is why the ranged tab already carries a footer listing two dead fields.
  3. Add one line to the form. In Assets/_Game/Editor/Workbench/WorkbenchCategories.cs, find RangedWeaponCategory.DrawForm → case 1 → the block under form.Section("The Arrow"), and put the row where a designer would look for it — beside Speed, not at the bottom: 
    form.Prop(so, "ProjectileDrop", "Drop (u/s²)",
          "Downward drift while the arrow flies. 0 = flat.");
form.Effective($"falls {weapon.ProjectileDrop * 0.5f:0.00} units over the first second");
    The Prop path is the C# field name, and a typo yields a missing row with no error (see the silent-skip box above). Add the Effective line whenever the authored number is not the number the player experiences.
  4. Stamp existing assets. A newly added serialized field is not written into already-serialized assets — open each bow in the Workbench and set a real value rather than trusting the C# initializer. This is rule 2's bug in miniature.
  5. Decide whether it belongs in the INI too. If designers will retune it in text, add the key to ContentIniImporter and check Gleamwood ▸ Check Content INI Sync. See Tuning §08.
  6. Update combat.html §04 and workbench.html §06 in the same commit. Those two pages tabulate this exact field group.
Do not add a field to a rich category's form when an attribute would do. If the type has no sub-tabs, no checks and no derived values, converting it to [WorkbenchField] curation is strictly less code to maintain. The decision rule is in Worked example B.

06Verification — how to know you did not break it

Four independent gates, and each catches a class the next cannot see: the compiler catches syntax and warnings, the validators catch wiring, the suite catches behaviour, and playing catches feel. This section expands CLAUDE.md's Verifying list into something you can follow on day one.

Prerequisite: every shell block below is bash, and this is a Windows toolchain. Run them from Git Bash or WSL. 3 — The PlayMode suite

The suite is PlayMode only and lives in Assets/Tests/PlayMode/. The authoritative test count is Logs/playmode_test_results.txt, never a number written into prose — see Maintaining for why that rule exists.

Tools/run-tests.sh                  # run, wait, print the verdict
Tools/run-tests.sh --no-wait        # fire and return
Tools/run-tests.sh --verdict FILE   # judge an existing results file, run nothing

By hand: Gleamwood ▸ Run PlayMode Tests. Either way the verdict lands in Logs/playmode_test_results.txt.

The exit code is the WHOLE line, not the word Passed. Passed, and zero failed, zero skipped, zero inconclusive. It used to be one grep for ^RUN FINISHED: Passed, and an Assume that fires leaves its test Inconclusive while the NUnit root stays Passed — so a run in which a guard had silently stopped guarding exited 0. One test went its whole life without executing that way. Skipped is the same shape further out: a test removed by an [Ignore], a defineConstraints that stopped matching or a compiled-out file is simply absent, and absent looks exactly like passing. The counts are parsed out of the line, so a runner that reformats it exits 2 ("cannot read the verdict") rather than matching nothing and reporting green. --verdict exists so all of that can be proved against hand-written files in a second instead of by mutating a test and paying for a full run.

The Pipeline server warns that the editor is not in -automated mode: a modal can still block CLI commands, exactly like the dirty-scene wedge. Restarting the editor with -automated is the real fix but costs the open session, which is why the script saves first instead.

Two false-pass traps

  • A stale DLL can produce a false pass. "0 console errors" after an Assets/Refresh can mean the compile never happened and menus are running OLD code. Gate each assembly's DLL mtime against its own source files — a whole-Assets/ mtime scan false-fails constantly and teaches you to ignore it.
  • Use GetConsoleLogs, not ReadConsole, for sticky compile errors. The latter can miss them.

Before you commit

  1. Offline compile with -t:Rebuild — zero warnings, not just zero errors.
  2. Gleamwood ▸ Validate Run Content (plus the reachability audit if you touched rooms) — 0 errors.
  3. The PlayMode suite — green. Then git checkout -- DebugSettings/DebugSettings.json if you ran it by hand.
  4. Play it. New behaviour only counts once it has shown up in an actual run.
  5. Update every wiki page your change made stale, in the same commit. Each domain page ends with a "Keep this page honest" box naming the exact files it mirrors — that box tells you whether yours is one of them.

Commit style: long-form prose in the body — what changed, why, and what was considered and rejected. The commit log is the design record. End with the Co-Authored-By trailer. Commit or push only when asked.

07Recipes — the first five things you will be asked for

Each is the short path with the registration step called out, because the registration step is the one people miss. Follow the link for the depth.

Add a weapon

  1. Assets ▸ Create ▸ Combat ▸ Weapon ▸ Melee Weapon (or Ranged) into Assets/_Game/Player/Resources/Weapons/. Name it its final name now — the asset name is the save id, and renaming a shipped weapon breaks player saves.
  2. Author it: right-click → Open in Content Workbench. Melee has five sub-tabs and a weapon authored from only the first two ships with no moveset.
  3. Register in WeaponCatalog.asset (Assets/_Game/Systems/Run/Resources/) — without it, run-resume cannot restore the weapon.
  4. Add it to a loot table (Loot_HubMelee.asset / Loot_HubBow.asset) — without it, no pedestal will ever offer it.
  5. Verify both Overview registration rows are green. They are exactly steps 3 and 4.

Full recipe, animator wiring and the runtime pedestal flow: Combat & Weapons §09.

Add an enemy

  1. Clips → a SpriteClipSet (Gleamwood ▸ Dev ▸ Animation ▸ Clip Set Builder). The clip is the timer — there are no animation events.
  2. Create ▸ Enemies ▸ Enemy Definition; set MaxHealth (0 means damage cannot kill it — executions still can), ExecutionThreshold, CanBeJuggled.
  3. Build its states on the Workbench States tab with + Create State — never by hand (§04).
  4. Prefab under Assets/_Game/Enemies/Prefabs/ with EnemyStateMachine pointing at the definition. The Workbench only finds a prefab in that folder, and an enemy with no prefab can never be classified as a boss.
  5. Register in an EnemySpawnTable — otherwise it never spawns.
  6. If you wire Executions: most-specific first, status-gated catch-alls last (rule 8).

Full nine-step recipe: Enemies & Bosses §07. Bosses: §08.

Add a player state

  1. New state type only if one does not exist: Cat Splat State Machine ▸ Tools ▸ State Machine Creator ▸ State Creator. It writes to two folders: the config to Assets/_Game/Player/Code/Definitions/States/ and the state class — the one you edit — to Assets/_Game/Player/Code/States/. The stub overrides only Enter().
  2. Create the config sub-asset on the Workbench Player ▸ Balen (State Machine) page — selecting that asset is the states surface; there is no States sub-tab on the Player tab (only Enemies and Bosses reach it through one). That is what sets StateName and appends it to States.
  3. Wire transitions there, choosing Conditions and/or DynamicConditions. Reuse Assets/_Game/Player/Data/SharedRules/Dy_*.asset before authoring a new one.
  4. If your new state's C# also calls AddTransition, check no authored row targets the same state — you would delete it silently (rule 5). Play once and read the console for the collision inventory.
  5. Test by driving real buffered input, not ChangeState.

Which states are hybrids: Framework §04.

Add a tunable

  1. Put [Tunable("Tab", min, max)] on a runtime float/int (slider) or bool (toggle) field or property.
  2. Register the host: TunableRegistry.Register(object target) in Awake or OnEnable — the panel snapshots the registry when it configures its tabs, so registering later is too late. There is a matching Unregister. The player path does not need it: PlayerDebugUI calls AddTabsFrom(playerContext, playerContext.Mover, hitboxViewer) directly, and everything in the registry rides along.
  3. Leave Save off for anything the game owns (rule 1). Only genuine panel preferences persist. TunableParityTests fails the suite if you get this wrong on any tab — a new tab is a gameplay tab by default; declaring one a preference is a deliberate entry in the test's PreferenceCategories, not something you get by naming it.
  4. Need a side effect on change? OnChanged = nameof(Method) — a no-arg method on the declaring type, so the wiring stays declaration-local.
  5. Optional: Section, Label, Tooltip.

The panel, its tabs and the JSON: Tuning & INI §03.

Add a test

  1. New file in Assets/Tests/PlayMode/. Nothing to register — the assembly compiles the folder.
  2. [SetUp]: Time.timeScale = 1f; and restore it in [TearDown] (rule 4). Clear any global state your fixture touches — RunModifiers.Clear() is the common one.
  3. Assert the behaviour, not the flag (rule 3). Ask what the player or the enemy actually experienced.
  4. Sweep the shipped assets where the invariant is about content — AssetDatabase.FindAssets("t:X") inside #if UNITY_EDITOR (rule 2). A hand-built fixture proves the mechanism and says nothing about the game.
  5. Wait on Time.time deadlines, never frame counts. If you must press once per frame, pin Time.captureDeltaTime.
  6. Write the why in an XML doc comment on the class. Every strong fixture in this suite explains the bug it exists to prevent — that is the house style, and it is what makes a failure diagnosable a year later.

08Your first hour, in order

Do these in sequence. By the end you will have read the graph, opened the tool, run the gates and made one safe change.

  1. Read CLAUDE.md top to bottom. It is short and it is binding.
  2. Open Assets/_Scenes/3.TestSandbox.unity and press Play. Move, jump, dash, swing, shoot. Press F1 and drag a slider.
  3. With play mode still running, open Cat Splat State Machine ▸ State Machine Visualizer, pick PlayerStateMachine, enable Live View, and watch the states change as you move. Then read the console for [StateMachine] … REPLACED … lines — that is rule 5's inventory.
  4. Stop play mode. Open Gleamwood ▸ Content Workbench. Click every rail tab. Then select the Player tab and pick Balen (State Machine) — that is Assets/_Game/Player/Data/PlayerDef.asset, and its page is the states surface you just read about in §04. Do not try to get there by right-clicking the asset: Open in Content Workbench is greyed out on it, because the validator in §05 accepts only WeaponDefinition, EnemyDefinition, PlayerContext, BiomeDefinition, MusicSet and [WorkbenchCategory]-tagged types. If you want to see that route work, try it on Assets/_Game/Player/Resources/PlayerSettings.asset.
  5. Run the three gates once on a clean tree so you know what green looks like: the offline compile with -t:Rebuild, Gleamwood ▸ Validate Run Content, and Tools/run-tests.sh. Expect the suite to take roughly five minutes.
  6. Make one small, safe change end to end — Worked example A is a good first PR — and take it through the pre-flight list in §06, wiki edit included.
Then pick the domain you have been handed and read its page. Combat & Weapons · Enemies & Bosses · Levels & Rooms · Progression · UI & HUD · Audio · Dialogue · Modding. Extending is the catalogue of every declarative seam; Maintaining is how this wiki stays true.
