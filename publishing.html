Publishing to Steam

Getting a build into your testers' hands: the build → upload → set-live loop, who can actually play an unreleased app, and the handful of contracts that quietly break everything if you change them.

02The loop — build, upload, set live

Three steps, every time. The upload script only finds a build; it never runs Unity, so you always build first.

  1. Build. Build System ▸ Build Manager → build Windows. Output lands at Builds/StandaloneWindows64/<version>/sentinels-of-gleamwood.exe. The version bumps automatically.
  2. Upload. From Tools/Steam: .\Upload-SteamBuild.ps1 -Preview first (uploads nothing, writes a manifest so you can check the file list), then .\Upload-SteamBuild.ps1 for real.
  3. Set it live. Partner site → SteamPipe ▸ Builds → find the build → Preview Change → Set Build Live Now. Immediate; no review, no store approval.
# one time per machine - your Steam LOGIN NAME, not email, not password
setx STEAM_BUILD_ACCOUNT your_login_name     # then open a NEW terminal

cd Tools\Steam
.\Upload-SteamBuild.ps1 -Preview             # dry run
.\Upload-SteamBuild.ps1                      # real upload

The script picks the newest folder under Builds/StandaloneWindows64 that contains an exe, stamps the git sha into the build description (so a build in SteamPipe traces back to a commit), excludes Unity's _BurstDebugInformation_DoNotShip folder and .pdbs, and hands off to steamcmd.

Credentials never touch this repo. The script passes only your account name. steamcmd prompts for the password and Steam Guard itself, then caches the session locally — that cache is what stops it asking every time. Never put a Steam password in the repo, an environment variable, or the command line.

steamcmd — no PATH setup

Unzip the Steamworks SDK into Tools/Steam/sdk/ and you're done. Resolution order is -SteamCmd → $env:STEAMCMD → anything named steamcmd.exe at any depth under Tools/Steam/ → common install spots → PATH. If the zip extracts into its own versioned folder, that still works. When it can't find steamcmd, the error lists every location it checked.

The SDK folders are gitignored — it's large, and this repo already carries history bloat from vendored binaries. First steamcmd run self-updates for a minute or two; that's normal, not a hang.

03Two contracts you must not casually change

The executable name is pinned

Steam's launch option is a fixed path — it names one executable and never re-resolves it. Builds used to emit {productName}-{version}.exe, which would have broken the launch option on every single upload (installs fine, then refuses to start).

The version now lives in the build folder; the exe name is pinned by BuildNaming.ExecutableName. It is deliberately not derived from productName, so a marketing rename can't silently break shipping. Change it and you must update Steamworks ▸ General Installation Settings to match, on every OS.

Identity decides where saves live

Unity derives Application.persistentDataPath from companyName / productName. Change either after testers have played and every save is orphaned — which matters here because suspended runs store nodeIds.

Settled as Cat Splat Studios / sentinels-of-gleamwood. Treat it as frozen. (Unity holds Project Settings in memory until you save the project — if an identity edit seems not to stick, save the project and re-check ProjectSettings.asset.)

04One-time partner-site setup

Skip these and the upload succeeds while the game still won't run — the most confusing possible failure.

  1. General Installation Settings → add a launch option pointing at sentinels-of-gleamwood.exe. Without one, the build installs and does nothing.
  2. SteamPipe ▸ Depots → depot 2953371: OS Windows, Architecture 64-bit, Language [All].
  3. Publish the config. Depot and launch-option changes do nothing until published.
"Unpublished" means two different things. The app's release state can stay unreleased indefinitely — testers still play. But unpublished config changes (depots, launch options) are simply not in effect. Don't let the first word fool you into skipping the Publish step.

05Who can actually play it

Uploading grants nobody anything. Access is a separate axis, and it is the step people forget.

For a small internal team: add them as Steamworks users. Partner site → Add/Manage Users, invite by email; Visibility Only permission is enough. They land in the "Everyone" group, which auto-grants the Developer Comp package — and its contents are "immediately playable regardless of the Release State." No keys, no waiting. An admin approves the invite within 7 days; the tester should restart Steam afterwards.

The gotcha that looks like a broken build: adding a new depot does not automatically add it to the Developer Comp package, and testers just get download failures. Valve: "Just because you have added a new depot… doesn't mean you can test it." Verify with Steam.exe -dev → Console → licenses_for_app 2953370.

06Branches — when you need a private track

Pre-release you don't need one. The default branch is only reachable by accounts holding a license, and pre-release the only licenses that exist are the ones you handed out — so default is your private track.

Reach for a named branch when you want hands-off uploads (the script can publish automatically), a place to test something risky without disturbing the build the team is playing, or external testers who shouldn't see work-in-progress.

  1. SteamPipe ▸ Builds → Create new app branch. Name it without spaces (e.g. testing); the description is what testers see.
  2. Set the password before putting a build live on it — otherwise the branch is briefly public. A passworded branch hides even its name.
  3. Upload with -Branch testing and the script publishes automatically — no partner-site clicks.
  4. Testers: right-click the game → Properties ▸ Game Versions & Betas (older clients say just "Betas") → enter the access code → Check Code → pick the branch.
SetLive cannot target default — Valve blocks it deliberately, and the script refuses -Branch default too. Promoting to default is always a manual Set Build Live Now. Once the game is released, that also requires a Steam Mobile Authenticator or SMS confirmation, and it auto-updates every owner instantly — so before you flip to released, make sure default holds a build you'd be happy shipping.
