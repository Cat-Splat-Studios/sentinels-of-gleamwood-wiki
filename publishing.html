Publishing to Steam

Getting a build into your testers' hands: the build → upload → set-live loop, who can actually play an unreleased app, the handful of contracts that quietly break everything if you change them, and what the store page has to disclose about where the art and audio came from.

01The constants

Frozen values you look up rather than decide. Two of them — the pinned executable name and the product identity — are contracts that install fine and break the game afterwards if you change them (§04).

02The loop — build, upload, set live

Four steps, every time. The upload script only finds a build; it never runs Unity, so you always build first.

  1. Build. Build System ▸ Build Manager → build Windows. Output lands at Builds/StandaloneWindows64/<version>/sentinels-of-gleamwood.exe. The version bumps automatically — and rolls back if the build fails or is cancelled, so a dead build never consumes a number out of the same monotonic sequence the Steam releases draw from. Three refusals fire BEFORE the build, so they cost nothing. The first is the suite: SuiteGate refuses a missing, red, unreadable or stale Logs/playmode_test_results.txt — stale meaning a green file older than a .cs under Assets/, which reads exactly like a pass and describes code that no longer exists. Re-run Tools/run-tests.sh and build from the green. Then: a version format System.Version cannot parse (VersionFormat.Simple, which emits a bare build number) is rejected outright, because the uploader skips any folder it cannot parse as a version; and a release whose build-<version> tag already exists is refused — that version has shipped, and building it again would write over its folder. Raise the version in BuildInfo, or delete the tag if it was a mistake. A successful release build then offers to create and push the tag build-<version>: that dialog writes to the shared repository, so skip it for anything that is not going to Steam — the build is complete either way. A development build never tags (§03).
  2. Upload. From Tools/Steam: .\Upload-SteamBuild.ps1 -Preview first (uploads nothing, writes a manifest so you can check the file list), then .\Upload-SteamBuild.ps1 for real. The real run is not unattended — it prints the folder it auto-selected and then stops on a [y/N] confirm naming the channel, because an auto-selected folder makes this the last point at which a wrong choice is cheap. -Preview skips the prompt.
  3. Set it live. Partner site → SteamPipe ▸ Builds → find the build → Preview Change → Set Build Live Now. Immediate; no review, no store approval.
  4. Write the notes. Add a section for the version you just set live to Documentation/BUILD-NOTES.md — player-facing, in their language, not the changelog. This page is the only one in the wiki that describes shipping, so if it does not say this, nobody does it: 0.1.0.13's notes had to be written after the fact, from 166 commits. Newest section on top, and a build that only ever went to testers says so in its own section rather than being merged away, because the next release's notes need something to measure "what changed" against. The file's role is the maintaining §05 doc map row.
First time on this app, or adding a tester? Do §05 and §06 first. Skip them and the upload succeeds while nobody can install or start the game.
# one time per machine - your Steam LOGIN NAME, not email, not password
setx STEAM_BUILD_ACCOUNT your_login_name     # then open a NEW terminal

cd Tools\Steam
.\Upload-SteamBuild.ps1 -Preview             # dry run
.\Upload-SteamBuild.ps1                      # real upload

The script picks the highest-versioned folder under Builds/StandaloneWindows64 that contains an exe — parsed as a version, deliberately not by modified time and not by name, because both of those invert on this repo's own folder set. Modified time was wrong because touching anything inside an older folder (dropping in a steam_appid.txt, deleting a _DoNotShip, unzipping a sibling archive) promotes that older build to the upload candidate; by name, 0.0.0.10 sorts below 0.0.0.2 and 0.1.0.9 above 0.1.0.11. A folder whose name is not a version is skipped with a warning. It then stamps the git sha into the build description (so a build in SteamPipe traces back to a commit), excludes Unity's _BurstDebugInformation_DoNotShip folder, the IL2CPP _BackUpThisFolder_ButDontShipItWithYourGame folder and .pdbs, and hands off to steamcmd.

Credentials never touch this repo. The script passes only your account name. steamcmd prompts for the password and Steam Guard itself, then caches the session locally — that cache is what stops it asking every time. Never put a Steam password in the repo, an environment variable, or the command line.

steamcmd — no PATH setup

Unzip the Steamworks SDK into Tools/Steam/sdk/ and you're done. Resolution order is -SteamCmd → $env:STEAMCMD → the three expected spots under Tools/Steam/ (sdk/tools/ContentBuilder/builder/, steamcmd/, the folder root) → common install spots (C:\steamcmd\…, C:\SteamworksSDK\…) → a recursive sweep of Tools/Steam/ up to six levels deep → PATH. The sweep is a fallback, not an early step: it means a zip that extracts into its own versioned folder still works, but a machine that also has C:\steamcmd installed will use that one first. When nothing matches, the error lists every location it checked.

The SDK folders are gitignored — it's large, and this repo already carries history bloat from vendored binaries. First steamcmd run self-updates for a minute or two; that's normal, not a hang.

03Release and development channels

A development player carries the F1 debug panel, script debugging, the profiler hook and the dev cheats — so it never shares a folder with a release build. The folder separation, not a flag, is what keeps it off the store.

ChannelBuilt byLands atUploaded with
release (the default)Build Manager, Development Build untickedBuilds/<target>/<version>.\Upload-SteamBuild.ps1
developmentBuild Manager, Development Build tickedBuilds/<target>/Development/<version>.\Upload-SteamBuild.ps1 -Channel development -Branch playtest

A development build gets its own tier, not a suffix. The uploader enumerates the direct children of one channel's root, so a <version>-dev sibling would still be a candidate and correctness would rest on a PowerShell filter. A separate Development/ tier removes it from the release scan set entirely — the uploader cannot see it even if its guard is removed. The toggle lives in the Build Manager (persisted in EditorPrefs, defaulting to off) and the window prints which channel the next build will use, because a channel you cannot see is a channel you ship by accident. Ticking Unity's own Development Build in Build Settings does not do this: a scripted BuildPipeline.BuildPlayer takes its options as authoritative and ignores that flag.

build-channel.txt is the marker. The Build Manager writes it beside the executable as plain text, because nothing else about the folder tells you which channel it is: same pinned exe name, same version, and BuildInfo is baked inside *_Data where a PowerShell script cannot read it. The uploader reads it and throws on a mismatch in either direction. The direction that matters is an explicit -BuildPath aimed at a development folder while -Channel says release — that would otherwise sail through, because the tier check only runs during auto-selection. A folder with no marker predates it, so the script warns instead of throwing and says plainly that the guard did not run.

build-incomplete.txt is the other marker, and it is a hard stop. The version number is bumped before the build, so a build that fails or is cancelled leaves an output folder carrying the highest version in its channel — which is exactly what the folder pick above selects. It can never carry a build-channel.txt either, because that is written on success only, so the channel guard would find nothing and merely warn. The Build Manager therefore writes build-incomplete.txt into that folder on both of its failure paths, recording why, and the uploader throws on any folder carrying one — an explicit -BuildPath included. It does not quietly fall back to the next-highest good build: uploading a different build than the one you asked for is its own bad surprise. Recovery is to build that version again, or delete the folder — until it is gone it keeps winning the pick. The folder is marked rather than deleted so the failed build's output survives as the evidence for why it failed.

build-commit.txt names the commit the build came from. The Steam build description is the only thing distinguishing builds in SteamPipe › Builds — the list where someone later clicks Set Build Live — and it used to stamp git rev-parse HEAD at upload time. Upload a folder built last week, or upload after committing anything at all, and the one traceability field on that list named a commit that never produced the build. BuildInfo already captures the sha and branch during the version bump, so the Build Manager now writes them beside the executable on success and the uploader reads them from there. A folder built before the marker existed shows (commit unknown) and warns; HEAD is deliberately not substituted, because a confidently wrong sha is worse than an admitted gap.

Pushing a development build is supported, and sometimes exactly what you want — playtesters need the F1 panel and the on-screen version/commit/seed stamp to file a useful report. What is guarded is doing it by accident. Set one live on a beta branch only (-Branch playtest — §07), never default; its Steam description is prefixed [DEVELOPMENT - DO NOT SET LIVE ON DEFAULT] because SteamPipe ▸ Builds is the last place the mistake can be caught by eye. Development builds are also never git-tagged: a throwaway playtest build publishing a build-x.y.z.n tag into the same namespace as the Steam releases is not recoverable without a force-delete on a shared ref.

04The contracts you must not casually change

Two settled decisions. Both fail after a successful install, which is why they are written down instead of remembered.

The executable name is pinned

Steam's launch option is a fixed path — it names one executable and never re-resolves it. Builds used to emit {productName}-{version}.exe, which would have broken the launch option on every single upload (installs fine, then refuses to start).

The version now lives in the build folder; the exe name is pinned by BuildNaming.ExecutableName. It is deliberately not derived from productName, so a marketing rename can't silently break shipping. Change it and you must update Steamworks ▸ General Installation Settings to match, on every OS.

Identity decides where saves live

Unity derives Application.persistentDataPath from companyName / productName. Change either after testers have played and every save is orphaned — which matters here because suspended runs store nodeIds.

Settled as Cat Splat Studios / sentinels-of-gleamwood. Treat it as frozen. (Unity holds Project Settings in memory until you save the project — if an identity edit seems not to stick, save the project and re-check ProjectSettings.asset.)

05One-time partner-site setup

Skip these and the upload succeeds while the game still won't run — the most confusing possible failure.

  1. General Installation Settings → add a launch option pointing at sentinels-of-gleamwood.exe. Without one, the build installs and does nothing.
  2. SteamPipe ▸ Depots → depot 2953371: OS Windows, Architecture 64-bit, Language [All].
  3. Publish the config. Depot and launch-option changes do nothing until published.
"Unpublished" means two different things. The app's release state can stay unreleased indefinitely — testers still play. But unpublished config changes (depots, launch options) are simply not in effect. Don't let the first word fool you into skipping the Publish step.

06Who can actually play it

Uploading grants nobody anything. Access is a separate axis, and it is the step people forget.

For a small internal team: add them as Steamworks users. Partner site → Add/Manage Users, invite by email; Visibility Only permission is enough. They land in the "Everyone" group, which auto-grants the Developer Comp package — and its contents are "immediately playable regardless of the Release State." No keys, no waiting. An admin approves the invite within 7 days; the tester should restart Steam afterwards.

RouteUse whenCatch
Steamworks users (Dev Comp autogrant)People you employ or trust — the default for internal testingThey gain partner-site visibility, so scope permissions deliberately
Release State Override keysTesters outside the partner group; pressFirst-time developers must wait three weeks after AppID creation before requesting keys. Normal release keys do not unlock a pre-release app — you need the override type
Steam PlaytestWide public playtestsWrong tool internally: public-facing, no NDA, needs capsule art and a review pass — it announces the game exists
The gotcha that looks like a broken build: adding a new depot does not automatically add it to the Developer Comp package, and testers just get download failures. Valve: "Just because you have added a new depot… doesn't mean you can test it." Verify with Steam.exe -dev → Console → licenses_for_app 2953370.

07Branches — when you need a private track

Pre-release you don't need one. The default branch is only reachable by accounts holding a license, and pre-release the only licenses that exist are the ones you handed out — so default is your private track.

Reach for a named branch when you want hands-off uploads (the script can publish automatically), a place to test something risky without disturbing the build the team is playing, or external testers who shouldn't see work-in-progress.

  1. SteamPipe ▸ Builds → Create new app branch. Name it without spaces (e.g. testing); the description is what testers see.
  2. Set the password before putting a build live on it — otherwise the branch is briefly public. A passworded branch hides even its name.
  3. Upload with -Branch testing and the script publishes automatically — no partner-site clicks.
  4. Testers: right-click the game → Properties ▸ Game Versions & Betas (older clients say just "Betas") → enter the access code → Check Code → pick the branch.
SetLive cannot target default — Valve blocks it deliberately, and the script refuses -Branch default too. Promoting to default is always a manual Set Build Live Now. Once the game is released, that also requires a Steam Mobile Authenticator or SMS confirmation, and it auto-updates every owner instantly — so before you flip to released, make sure default holds a build you'd be happy shipping.

08Provenance and the AI disclosure

Steam asks, at submission, whether the game contains AI-generated content, and the answer is a public field on the store page. The answer is yes, and it stays yes after the strip — the six music tracks are Suno, generated on a Pro subscription that carries commercial rights, and they ship. Every other AI-generated class goes.

The ledger is Documentation/PROVENANCE.md — one row per media class with the evidence for it, and what the H4 strip does with it. It is checked mechanically, not maintained by memory: Tools/check-provenance.py refuses a media file under Assets/ with no row and a row that covers no file, and Tools/check-wiki.py runs it, so it is part of the ordinary verification loop rather than a second command to remember.

strip111Leaves the repo in H4. The AI sprite sets, the AI portraits and weapon icons, the placeholder hero and level art, and the sword-slash pack. (The SAPI voice-over is already gone — 28 takes deleted 2026-08-24.) Git keeps every byte.

Run python Tools/check-provenance.py --fate strip to see exactly which files that is, by name, before deleting anything.

What the disclosure has to say. Not “none required”. One AI-generated class ships: the six Suno music tracks (Pro tier, account anagrammc, all generated 2026-06-26, per-track ids in the ledger), so the honest declaration is pre-generated AI audio, naming the music. Everything else that ships is ours outright or third-party under a recorded licence; every AI sprite, portrait and icon is a strip — and the SAPI voice-over is no longer pending: its 28 takes were deleted on 2026-08-24, so that class is already out. The sword-slash pack and the hand-drawn hero sheets go too — both are placeholder being redrawn, so their provenance stopped mattering rather than being resolved.
One gap holds regardless of those answers. The OFL text and the required copyright line now ship for Pixelify Sans and Space Mono: PixelifySans - OFL.txt and SpaceMono - OFL.txt sit beside the faces, ThirdPartyNotices.Compose reproduces every such file verbatim, and BuildManagerWindow writes the assembled THIRD-PARTY-NOTICES.txt into the version folder on every successful build. Both copyright lines are also in the ledger, read out of the fonts’ own name tables. And the credits roll has no Art & Animation or Music & Sound row — deliberately, because there is nobody to name yet; CreditsScreenController.cs says the rows come back when the ledger says what the shipped art and audio are. Answering the three questions above is what unblocks the credits, too.

09The Steam Deck — proof happens on hardware

There is no Deck build and no Deck depot: a Deck installs the Windows depot (2953371) and runs it through Proton. Nothing in §02's loop changes — what the Deck adds is a debt on every checkpoint build: the platform claims in the code are proven by tests driving an injection seam, and only hardware can close them.

Why a walk at all. Deck detection is SteamUtils.IsSteamRunningOnSteamDeck(), fenced behind GLEAMWOOD_STEAM — a Standalone scripting define in ProjectSettings.asset, so release and development players alike carry the detection, the overlay pause and the Steam glyph branding. On any machine that is not a Deck, every non-injected path answers not a Deck: the suite's green certifies what the game would do with the platform fact, never that the fact arrives. The designer-facing half — what to author for that screen, and the text-size floors — is tuning §10; this section is the shipping half.

The checkpoint-build Deck walk

Run it on every checkpoint build that touched display, windowing, UI scaling, pause or haptics — and at least once before any public build. Use a development build set live on a passworded beta branch (§03, §07): the F1 panel and the version · commit · seed stamp are what make a Deck report traceable.

Close the desktop copy first, and quit Steam on the desktop. Steam runs a title on one device at a time per account, so launching on the Deck while the game (or the editor signed in to Steam) is open on your PC hangs the Deck at startup — no error, no window, just a stall that reads exactly like a crash in the build you are about to blame. Cost one 0.1.0.15 bug report on 2026-09-02. If the Deck hangs on launch, check the desktop before you check the code.
  1. Install and launch once, normally. First boot seeds config.ini inside the Proton prefix: <Steam library>/steamapps/compatdata/2953370/pfx/drive_c/users/steamuser/AppData/LocalLow/Cat Splat Studios/sentinels-of-gleamwood/config.ini — reachable from Desktop Mode with any file manager.
  2. Set the display keys deliberately wrong — say resW = 640, resH = 480 under [Display] — and relaunch. The picture must not change. A changed picture means a saved resolution reached Screen.SetResolution past the policy, which is the exact regression the display fix exists to prevent.
  3. Open Settings ▸ Display. Window Mode and Resolution must be present, dimmed, reading Set in Steam. Present-but-dimmed is the decision — a greyed row names where the setting really lives — so a missing row is a bug too.
  4. Press the Steam button mid-fight. The game must pause once. Twice is the failure to hunt for: the overlay can take focus and drop the pad in the same moment, and two pause pushes against one pop is a game frozen after Resume. Close the overlay, Resume, play on.
  5. Pair a Bluetooth pad, play with it, switch it off mid-fight. Same expectation: one pause, clean resume.
  6. Take a hit; feel the pad buzz. Then set Screen Shake to Off and take another — it must still buzz. Stilling the camera and silencing the motors are two separate accessibility answers, and the walk is where that separation is felt rather than asserted.
  7. Text Size at Large, then back to Medium — and at Medium, read the smallest HUD text (status stacks, run-modifier names, the pause-menu seed) at arm's length. This is the field test for the floors in tuning §10.
  8. Walk the fan column bare-kit on the pad — the one route with a precision hop, and nobody has walked it on this hardware.

Fold every verdict into its row rather than into memory: OUTSTANDING "The Steam Deck display fix is in, but unproven on hardware" (steps 2–5), OUTSTANDING "Deck legibility: 10–13 px text and a Text Size row read by nothing" (step 7), OUTSTANDING "The UI is not consistent across resolutions" (step 7), OUTSTANDING "The fan column's S12→S14 hop breaks ROOM_STANDARDS' own rule" (step 8). A step that fails becomes an item on its row; a step that passes deletes the row's unproven clause — either way the row moves, which is how the next reader knows the walk actually happened.

The compatibility review

Valve grades every app's Deck experience — Verified / Playable / Unsupported — and the grade is public on the store page. It reviews a build, and it can be pointed at a beta branch, which is how it is sequenced here: at H8 in Documentation/DESIGNER-HANDOFF-PLAN.md, from a beta branch, after the provenance strip and the designers' content land, alongside the rest of the store runway. Nothing on the partner site is configured for it yet — this paragraph documents the plan, not a done thing.

Measured against what ships today: controller-first menus with correct glyphs (SteamInputBrandProvider), no keyboard-dependent entry point, and a default configuration that runs without ever opening a settings screen — the display policy exists for exactly this — are all in place. The known gap is text legibility: the 10–13 px rules on OUTSTANDING "Deck legibility: 10–13 px text and a Text Size row read by nothing" are precisely the sort of thing a Verified grade fails on, so close that row before requesting the review. And the warning this page already carries about Valve's rules applies double here: the criteria drift — re-verify against partner.steamgames.com/doc/ before scheduling anything against them.

A Deck regression is a real regression, not a polish item. The platform bar in CLAUDE.md says it and shipping is where it bites: any change to display, windowing, fullscreen or UI scaling re-opens the hardware debt — the walk above goes back on the next checkpoint build, and it works on Windows goes back to being half a claim.
