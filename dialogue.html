Dialogue

One asset holds everything a character says. Beats are keyed by trigger, each beat rotates across encounters, and the rotation is remembered per save — so a boss you have met three times greets you differently the fourth. Here is the structure, what actually fires in game today, how to author it in text or in engine, and how a player with no Unity can change every word of it.

01The shape of a dialogue set

A DialogueSet is four levels deep, and every level exists for a reason. Getting these names straight makes the rest of the page — and the whole Dialogue tab — read easily.

Before you write a word: all five beats can speak now, and three of them need a component. Intro and Victory fire from BossArenaSequence with nothing to add. Defeat, Phase Two and Banter fire from a DialogueBeat component (added 2026-08-18) — drop it on the enemy or the NPC, point it at a set, pick a trigger and a moment, done. Until that component existed those three beats saved and validated perfectly and were never spoken by anything. §03 has the table.
LevelTypeMeansChosen by
SetDialogueSet (SO asset)One speaker's entire script — every occasion they have lines for.You, by pointing a BossDefinition.dialogue at it.
BeatDialogueGroupAn occasion: Intro, Victory, Defeat, Phase Two, Banter, or a custom name.The game, by calling set.Next("Intro") when that moment happens.
EncounterDialogueSequenceWhat they say this time the beat fires. The story-reveal layer.The save — how many times you've already heard this beat.

The word that trips people up is Encounter. It is not "a fight" — it is one alternative version of this beat. Three encounters on an Intro beat means the boss has three different greetings, not that the boss is fought three times.

02The rotation — how "what they say next" is picked

This is the Hades trick, and the whole reason the structure has an Encounter level. Every beat keeps its own count of how many times it has played, and that count indexes the encounter list.

// DialogueGroup.IndexFor(seen) — the entire selection rule, and the ONE copy of it:
// both DialogueSet.Next(trigger) and VoiceKeyPrefix(trigger) call it. Change it here.
int index = group.cycleWhenExhausted
    ? seen % group.sequences.Length          // wrap back to the first
    : Mathf.Min(seen, group.sequences.Length - 1);  // stick on the last
It lives on DialogueGroup, not in Next, and that is deliberate. The rule had been written out twice — once in DialogueSet.Next and once in VoiceKeyPrefix(trigger) — and those two must agree or the panel speaks one encounter's TEXT while asking the voice bank for another encounter's AUDIO. That is the shape of the 2026-07-25 coverage/bake mismatch. Editing Next alone is the bug the extraction exists to prevent. (IndexFor also clamps a negative seen to 0 rather than throwing: it can only come from a corrupt save counter, and a silent restart from the top beats an exception mid-encounter.)
Times heard3 encounters, cycleWhenExhausted ON3 encounters, cycleWhenExhausted OFF
1stEncounter 1Encounter 1
2ndEncounter 2Encounter 2
3rdEncounter 3Encounter 3
4thEncounter 1 (loops)Encounter 3 (repeats forever)

Pick ON (the default) for banter and taunts that can recycle. Pick OFF when the last encounter is a resting state you don't want to walk back from — a boss who has acknowledged you should not go back to greeting a stranger.

Where the count lives

The counter is per save slot, per beat, keyed dialogueId + ":" + trigger — so cinder-shepherd:Intro and cinder-shepherd:Victory advance independently. It is stored in SaveSlot.meta as two parallel arrays (dialogueIds / dialogueSeen) because JsonUtility cannot serialize a dictionary. The count is bumped by MarkSeen(trigger), which the caller invokes only when the lines actually play. A blank dialogueId logs an editor warning on import (OnValidate, compiled out of builds) — it does not stop the write.

dialogueId is save data. Renaming it on a shipped asset orphans every counter that referenced it — every beat silently resets to encounter 1 for players who already had progress. Treat it like a database key: set it once, never touch it. The set warns on load if it is blank.
Testing gotcha — rotation does nothing without an active save slot. When SaveSystem.ActiveSlot is -1, SeenCount returns 0 and MarkSeen is a no-op, so you will see Encounter 1 every single time. That is exactly what happens when you press Play directly into 3.BiomeHost instead of booting through slot selection. The rotation is not broken — it is unpersisted by design, so sandbox testing never pollutes a save. To actually see encounters 2 and 3, boot from 0.Bootstrapper and pick a slot.

03What actually fires in game today

This is the most important section on the page. Five trigger names are offered in the Workbench dropdown, and all five can be spoken — but only two have an automatic caller. Defeat, Phase Two and Banter speak through a DialogueBeat component you place, so authoring one of those three without placing the component produces content that is saved, validated, and never spoken.

TriggerWired?Fired byWhen
IntroYESBossArenaSequence.Sequence()After the adds and the boss have spawned dormant, before the gate arms.
VictoryYESBossArenaSequence.Outro()Gate opens (every registered enemy dead) → music fades out → ~1.2s breath → reward spawns → these lines.
DefeatYESDialogueBeat, when = OnDeathThe enemy carrying the beat dies — read from the context’s own dead flag, so an execution counts exactly as a killing blow does. (The trigger name reads from the BOSS’s side. For the player dying to the boss, the death sequence still consults no set.)
Phase TwoYESDialogueBeat, when = OnHealthBelowHealth crosses healthFraction going DOWN. Edge-triggered: it fires on the crossing, not every frame below, and the first frame after the component wakes only takes a reading — so a boss a campaign spawns already wounded does not open with its phase-two taunt.
BanterYESDialogueBeat, when = OnInteract or OnEnableThe player interacts with an InteractZone on the same object or a parent (which is what the Shopkeeper needed), or the object simply wakes. No hub NPC owns a DialogueSet yet — that is content, and the route in no longer needs code.
If you author a beat and never hear it, check the COMPONENT before the content. A set with a Defeat, Phase Two or Banter group still speaks only if something asks for that trigger, and for those three the asker is a DialogueBeat on the enemy or the NPC. Nothing in the editor will tell you the component is missing. Moment.OnEnable has one wrinkle worth knowing: it fires when the component is enabled, so a beat added and configured at RUNTIME has already passed that moment — every other moment reads its settings when the moment happens.

A custom trigger is just a string — set.Next("KragMocksYou") resolves a group named KragMocksYou with no registration anywhere. DialogueTriggers.All only controls what the dropdown offers; it is not a whitelist, and the lookup is case-insensitive.

04The boss encounter, beat by beat

Both wired triggers live in one component: BossArenaSequence, on the arena room. Here is the whole choreography, so you can see where your lines land and what is happening around them.

  1. The door seals. The corridor's exit BossDoor closes behind the player and fires OnClosedBehind. The sequence latches — it can only run once.
  2. The hush. MusicDirector.StopForBossIntro() fades the level track out. The exchange happens in near-silence on purpose; see Audio.
  3. The walk-in. Input switches to the UI map (control locked, but the real run animation plays) and the player auto-walks walkInDistance (4u), then holds still for 0.4s. Timeout-guarded at 3s.
  4. The adds. Deferred spawn markers fire one per spawnInterval (0.45s). Each enemy appears dormant — esm.enabled = false, so its idle animation plays but its AI does not — and registers with the BossGate.
  5. The boss. The gap before it appears is spawnInterval + entranceDelay, not entranceDelay alone — the add loop waits spawnInterval after every add including the last, and the boss branch then waits entranceDelay on top. It spawns at the isBossPoint marker, also dormant, also registered.
    BossentranceDelayReal gap (with the shipped 0.45s interval)
    Krag · Cinder Shepherd0.81.25s
    Pyre Regent1.01.45s
    Demon King1.41.85s
    The six Boss_Stopgap_* Wardens0.6–0.91.05–1.35s
    BossDefinition.entranceDelay's own tooltip says "beat between the last add appearing and the boss's arrival" — that tooltip is off by one spawnInterval, so budget the beat from the table, not from the field alone.
  6. ▶ The Intro beat. activeSet.Next("Intro") → VoiceKeyPrefix("Intro") → MarkSeen("Intro") → ui.Play(lines, onDone, freezeTime: false, voiceKeyPrefix: …). That middle step must come before MarkSeen — see §05. The world keeps running: enemies idle-animate through the speech, the player just has no control. The coroutine waits for the box to close.
  7. Fight on. Boss music crossfades in (or the level track resumes if the boss has none), every dormant enemy wakes, the gate arms, gameplay input returns.
  8. ▶ The Victory beat. The gate opens when the last registered enemy dies — or immediately on arming, if nothing spawned (empty table, gated stage), because BossGate never soft-locks a run. Then: MusicDirector.FadeOutForVictory() winds the fight theme down to silence → a ~1.2s breath over the body while it fades → rewardPrefab instantiates at the boss point → Next("Victory") + MarkSeen, so the boss's last words land in quiet, world still running. In an empty arena the Victory beat can therefore follow the Intro with no fight in between.

Two fields can supply the set, and the boss wins:

The Victory beat has one extra condition the Intro beat does not: Outro() returns immediately when the biome has no BossDefinition. Stand-in arenas open silently — the fallback set's Intro plays, but its Victory group never will. Dlg_EmberVanguard reflects this honestly: it carries an Intro group of three encounters and no Victory group at all, because there is no path that could play one.

Every phase is skip-safe. A missing set, a missing group, an empty group, or an absent dialogue panel all degrade to the same thing: the beat is skipped and the fight starts sooner. Next() returning null is a normal, expected value — no consumer guards against it with an error.

05The panel that draws it

DialogueController is a MenuScreen that owns the bottom speech box. Callers never reference it directly — they resolve it through the router, which is what makes the whole system degrade gracefully.

// DialoguePlayback.TryPlay, verbatim — the ONE copy of the dance, and all THREE guards.
// The boss intro, the victory outro, DialogueBeat and the preview driver all come through here.
public static bool TryPlay(DialogueSet set, string trigger, Action onComplete = null,
                           bool freezeTime = false)
{
    if (set == null || string.IsNullOrEmpty(trigger)) return false;

    DialogueSequence sequence = set.Next(trigger);
    if (sequence?.lines == null || sequence.lines.Length == 0) return false;
    if (!MenuRouter.TryGet(out DialogueController ui)) return false;

    // BEFORE MarkSeen: the prefix names the encounter being played, and MarkSeen
    // advances the counter it is derived from.
    string voiceKey = set.VoiceKeyPrefix(trigger);
    set.MarkSeen(trigger);

    ui.Play(sequence.lines, onComplete, freezeTime, voiceKey);
    return true;
}

The lines.Length > 0 test is the one that is easy to drop and expensive to lose. DialogueController.Play treats an empty array as "already finished" — it invokes the callback and shows nothing. Without that guard, an encounter authored but left blank would advance the rotation while the player sees no box at all.

The order of the two lines before Play is load-bearing too. VoiceKeyPrefix resolves which encounter is about to be spoken from the same seen-count MarkSeen is about to increment, so taking the prefix afterwards would key every line to the next encounter's takes. Both shipped beats take it first, and so does the preview driver.

Play() is single-shot, not queued — and it fails silently. Its early-out is if (_active || lines == null || lines.Length == 0), so a call made while a box is already on screen takes exactly the same path as an empty array.
What you'd expectWhat actually happensWhy it hurts
The new lines queue behind the live boxThey are discarded, and nothing is loggedSilent content loss — no error to grep for later.
while (!done) waits for them to playonComplete fires immediately, so the wait sails straight throughThe caller cannot tell "played" from "thrown away".
An unplayed beat can be retriedThe MarkSeen that ran first already advanced the rotationA burnt encounter the player never saw — and there is no way back to it.

The two shipped beats can't collide (the Intro coroutine blocks until its box closes, and Victory can only fire after the gate opens), but this is exactly the trap waiting for the extra call sites §06 invites you to add — a Phase Two beat firing mid-Intro would vanish without a trace. If you wire a beat that can overlap, check Has() and your own state before calling, or defer until the current box closes.

freezeTime — the one flag that changes the feel

false — the world runs

Control locks to the UI map, but time flows. Enemies idle-animate, hazards keep ticking. Both boss beats use this — the arena feeling alive during the speech is the point.

true — full freeze (the default)

Pushes MenuState, the same stop the pause menu and intro card use. Used today by ForgeSite's upgrade confirmation and RunModifierSite's pickup confirmation, and the right mode for hub conversations, where there is nothing to keep alive behind the box.

Advancing is Submit, one line per press, and the box ignores the frame it opened on — otherwise the same button press that triggered a conversation would immediately skip its first line. The spoken take plays on a dedicated voice channel that each new line cuts (and that the box stops on close), so advancing past a long line never leaves two voices talking over each other; incidental sfx stay one-shot, where a brief overlap reads as punctuation.

The panel does not require a DialogueSet. Two components already drive it with a hand-built DialogueLine and freezeTime: true, both on Rest_Traversal.prefab in 4.RestHost: ForgeSite confirms a weapon upgrade, and RunModifierSite confirms a run-modifier pickup. Between them they are the only places the freeze path runs today. Any one-off confirmation can do the same; a set is only needed when you want rotation and save tracking.

06Authoring — text or engine, your choice

Dialogue has two equal authoring surfaces: a .dlg text file and the Workbench Dialogue tab. Neither is the "real" one. They hold the same content and you move between them with an explicit sync in either direction.

The .dlg format

One file per speaker in Assets/_Game/Content/Dialogue/. Line-oriented, no braces, no escaping — commas, apostrophes, em-dashes and colons inside dialogue are just text:

; a whole-line comment
id: krag-emberfall

@Intro
--- encounter
KRAG: Another spark climbs out of the Gleamwood.
    The furnace has eaten a hundred like you.
KRAG: I am Krag, Warden of the Emberfall. Burn quickly — I have a schedule.
--- encounter
KRAG: You. Again. Sparks are not supposed to come BACK.

@Phase Two [nocycle]
--- encounter
KRAG [krag.angry|right|shake|sfx:krag_growl]: Enough.
SyntaxMeans
id: <slug>The dialogueId. Required — it is the save key. One per file.
@NameOpens a beat. May contain spaces (@Phase Two). Optional [cycle] / [nocycle]; cycle is the default.
---Opens an encounter. Anything after it (--- encounter) is a readability note.
SPEAKER: textA line. The first colon after the speaker splits it, so text may contain further colons.
an indented lineContinues the line above, joined with one space. How a writer wraps a long speech without escaping anything.
; at line startA comment. Only whole-line — a ; mid-sentence is text, because dialogue has punctuation.
[a|b|c]Presentation, pipe-separated: left/right = side, shake/flash/none = effect, sfx:id, voice:id, and any other word is the pose id.
That last rule is what makes a typo loud. A mistyped [shke] parses as a pose named "shke" — and pose ids are checked against the PoseCatalog at sync time, so it surfaces as unknown pose 'shke' with a file and line number. The alternative was a missing shake nobody notices until a player sees it.

Sync — always explicit

The Dialogue tab

Four-level nesting is miserable in the raw inspector, which is why this tab exists. Beats are tabs, encounters are a toolbar, lines are speaker+text rows with a presentation strip.

  1. Create the set — Create ▸ Gleamwood ▸ Dialogue Set, named Dlg_<Speaker> beside the biome that owns it.
  2. Set the Dialogue Id to a stable kebab-case slug (cinder-shepherd). Do this now — it is the one field you can never change later.
  3. Add the Intro beat and write encounter 1. One encounter is a complete, shippable beat; the rotation is a bonus, not a requirement.
  4. Add more encounters for the story reveal. The four bespoke bosses use the same shape: an Intro beat of three encounters (two lines each) and a one-line Victory — 7 lines a set. The six Dlg_Stopgap_* sets are shorter: two Intro encounters and a one-line Victory, 5 lines each. Eleven sets, 65 lines, in the shipped game.
  5. Point the boss at it — BossDefinition.dialogue, on the Bosses tab. The Dialogue tab's top row confirms it: green [ok] spoken by a boss, or red when nothing references the set. The red is advisory rather than an error — the message itself says an unreferenced set is fine for hub/NPC banter.
  6. Validate — Gleamwood ▸ Validate Run Content errors on a boss with no set, an unknown pose id, a blank dialogueId or a duplicate beat, and warns when an asset has diverged from its .dlg.

Portraits, effects and voice

Every part of a line beyond its words is optional, and a line that asks for nothing renders exactly as dialogue did before portraits existed.

ModifierResolved throughMissing means
pose — any unreserved wordPoseCatalog (id → Sprite)Editor-time error. A text file cannot hold an object reference, so the catalog is where ids are enumerable — which is what lets the validator name a typo.
left / right—Left. The unused side is hidden, so a two-hander never strands the previous speaker on screen.
shake / flash / none—None. Runs on unscaled time, so it reads the same whether the exchange froze time or not.
sfx:idVoiceBankSilence.
voice:idVoiceBankUsually omit it. With no id a line resolves by its DERIVED key.
Voice keys derive themselves. A line with no voice: id looks itself up as dialogueId:trigger:encounter:line — the same shape as the rotation save key, so one convention covers both. A VO pipeline names files straight from the text and a writer never types an id; an explicit voice: exists only to share one take across lines. The tab shows each line's effective key and whether a take exists; Gleamwood ▸ Dialogue Tools… → Report Voice Coverage does the whole project. A missing take reports rather than blocking — unlike a bad pose id, "not recorded yet" is the normal state of a line mid-production.

Poses and voice are deliberately separate assets: a pose is the same drawing in every language, a take is not. Voice is the one piece of presentation that localises, so shipping a language is "add a VoiceBank" with nothing else touched.

Tracked in Documentation/OUTSTANDING.md, the row "Boss voice-over is Windows text-to-speech, and seven sets are silent".

Previewing — see a beat without reaching the arena

Poses, sides, shake/flash and sfx/voice only render at runtime, and the two wired beats sit at the far end of a boss fight. Gleamwood ▸ Dialogue Tools… plays any beat and encounter of any set through the real DialogueController — the same render path the arena drives — in a throwaway play scene:

  • Pick a DialogueSet (or select one in the Project first), a beat, and an encounter, then press Preview ▶. From edit mode it enters play mode for you; already playing, it spawns immediately.
  • Advance with Submit (Enter / controller A) exactly as in game, or with the on-screen buttons; Auto-advance plays it hands-free on a timer.
  • It plays the chosen encounter by index, bypassing rotation — so you can see encounter 2 or 3 with no save slot, and you can preview an unwired beat (§03) that the game itself never fires.
Shipped content only, unless you opt in. Poses and sfx resolve from the baked PoseCatalog / VoiceBank; a modded pose or a derived-key voice take previews only with Gleamwood ▸ Simulate Mods ▸ Dialogue on (§09).

Wiring a beat that isn't wired yet

Every one of the five canonical triggers has a route in already — Intro and Victory from BossArenaSequence, the other three from a placed DialogueBeat (§03). A call site is only needed for a CUSTOM trigger, or for a moment DialogueBeat.Moment cannot see. Route it through DialoguePlayback.TryPlay rather than by hand — the ordering it owns is the whole reason it exists:

// wherever the moment happens — e.g. the player-death path for this boss
bool spoke = DialoguePlayback.TryPlay(bossSet, DialogueTriggers.Defeat, onDone,
                                      freezeTime: true);
// false = nothing authored for the beat, or no DialogueController on the router.
// onDone never fires in that case, so a caller that waits on it must check the return.

Three rules keep it consistent with the shipped beats:

RuleWhy
Treat null as "skip"A missing or empty beat is a normal value, not an error. Every shipped consumer degrades to "this moment just has no line".
Call MarkSeen only on the path that really playsWhich is why the empty-lines test belongs in the same condition, not after it. Marking early burns an encounter the player never heard.
Take the prefix before MarkSeen, or the beat is unvoicedvoiceKeyPrefix defaults to null, and a null prefix makes DerivedVoiceKey() return null — so the panel resolves no take at all and the whole derived-key convention (§06's "Voice keys derive themselves", §09's mod filename rule) silently does nothing for your beat. Taking it after MarkSeen is the other half of the trap: the counter has already moved, so every line keys to the next encounter's takes.

Then ask the question the shipped beats never had to: can your moment fire while another box is already up? A Phase Two beat triggered by a health threshold can, because the world runs during the Intro exchange. If so, read the Play() warning in §05 first — the overlap is silently swallowed, and it eats an encounter on the way out.

08Traps

Every one of these fails silently — the content saves, the validator is happy, and the words never reach a player. That is the shape of every bug this system has had.

Duplicate trigger names

Group() is a FirstOrDefault, so a second beat with the same name is unreachable dead data — it saves, validates, and never plays. The Dialogue tab flags exact duplicates in red; the raw inspector flags nothing. Case-only duplicates slip through: the check groups case-sensitively while Group() matches OrdinalIgnoreCase, so Intro + intro is silent dead data. + Add Beat avoids collisions by picking the first unused canonical name, then Banter 2, Banter 3…

Renaming dialogueId

Orphans every counter keyed to the old id. Players silently drop back to encounter 1 on every beat. There is no migration path — the arrays are matched by exact string.

Authoring an unwired beat

Nothing warns you. Intro and Victory have automatic callers; Defeat, Phase Two and Banter speak only through a placed DialogueBeat component — a beat with no automatic caller and no placed DialogueBeat saves and validates perfectly and stays silent forever. Check §03 before writing; the route in is a component now, not a C# call site.

A beat landing on a live box

Play() early-outs when one sequence is already on screen: the new lines are dropped, onComplete fires anyway, nothing is logged — and the MarkSeen that ran first still advanced the rotation. Silent content loss plus a burnt encounter. Only reachable once you add a call site that can overlap (§05).

Testing without a save slot

Play-from-scene means ActiveSlot == -1: always encounter 1, no counter written. Boot through 0.Bootstrapper and pick a slot to exercise the rotation.

Duplicated content from arraySize++

Unity's array growth copies the previous element. The Dialogue tab now clears every add — beat, encounter and line — but the raw inspector still doesn't, so growing an array there hands you a verbatim copy of the row above. That is how Dlg_CinderShepherd ended up with four beats all reading "My flock... scatters..."

Diverged asset and file

Editing both surfaces without syncing leaves them disagreeing. The tab says DIVERGED and the validator warns, but neither can know which side you meant — syncing either way overwrites the other. If the file is stale when you ship, the mod template you hand players is wrong.

Hub scene has no panel

2.Hub does not contain Dialogue.prefab. Hub NPC dialogue fails the TryGet and skips silently — no error, no box. Add the prefab first.

09Modding & localisation

The same .dlg format that authors the game also reskins it from outside the build. A player with the Steam build and no Unity can change every line, and a translator can ship a language as a folder.

Folder (beside the executable)What it is
<campaign>/Dialogue/*.dlgLoaded. Overrides the shipped content for any set whose id: matches.
<campaign>/Dialogue/<locale>/*.dlgNOT LOADED — the parameter exists and no caller supplies one. Both loaders take locale as an optional argument that defaults to null, and every path that reaches them is a zero-arg lazy latch, so the folder is never even probed. Deferred until the game has a language SETTING to read one from — there is none today, and no other string in the game is localised either, so a dialogue-only switch would put translated boss lines inside an English UI.
<campaign>/Dialogue/poses/*.pngLoaded. New portrait art, claimed by filename — krag.angry.png satisfies pose id krag.angry.
<campaign>/Dialogue/audio/*.wavLoaded. New sfx and voice takes, same rule. A <locale>/ subfolder here is not read either — same reason as the row above.
Mods/_Templates/example-campaign/Dialogue/Not loaded. The game's real .dlg files, copied at build time as documentation, plus a plain-English README.
A mod can ship content the build has never seen. Without runtime art and audio, .dlg modding would stop half way: a mod could say KRAG [krag.furious], but krag.furious would have to already exist in the baked PoseCatalog. Files in poses/ and audio/ close that gap — an override supplies the id and the thing it names. Resolution is mod folder first, then the baked asset, which is what "override" has to mean.

Naming an asset file

There is no manifest to maintain: an asset is claimed by being named after the id it satisfies. A pose id is already a plain filename (krag.angry.png). A derived voice key is not — it contains colons, and Windows forbids : in filenames — so keys are spelled with dots on disk:

Runtime keyFile on disk
krag.angry (pose)poses/krag.angry.png
krag_growl (sfx)audio/krag_growl.wav
krag-emberfall:Intro:0:1 (derived voice)audio/krag-emberfall.Intro.0.1.wav

That mapping is lossy — a key genuinely containing a dot could collide with one containing a colon — which is why the loader logs what each file claimed. A silent mis-binding would be far worse than a noisy one.

A ready-made example. The base game speaks none of these lines any more — its 28 takes were stripped on 2026-08-24 and the VoiceBank holds only its five stings — so Documentation/ExampleDialogueVoice/ is what an audio mod that supplies them looks like: 28 takes named by the derived-key convention above (krag-emberfall.Intro.0.0.wav), each resolving where the baked bank has nothing. Swap any file for a real recording to re-voice one line. Regenerate with generate_voice.ps1 after Gleamwood ▸ Dialogue Tools… → Export Voice Manifest.
Installing it. Copy the whole Mods folder next to sentinels-of-gleamwood.exe, then pick Example Voice Pack when you start a new save. The loader walks Mods/ for directories containing a mod.ini and skips every one that does not, then reads Mods/<campaign-id>/Dialogue/. Until 2026-08-13 this pack shipped its takes at Mods/Dialogue/audio/ — the pre-campaign shape, with no mod.ini — so it was skipped in silence, and since the base game already speaks all 28 lines you heard the baked takes and nothing said the pack had not loaded. It is now Mods/example-voice/ with a manifest.
WAV only, and deliberately. Unity's runtime audio loader is asynchronous, and dialogue must never wait on a decode when a boss opens its mouth — an async path would also mean the first play of a modded line silently falls back to nothing. So WavReader decodes inline: PCM 8/16/24/32-bit and 32-bit float. .ogg and .mp3 are skipped with a log line saying why. Images are PNG/JPG, loaded point-filtered so a mod is not blurred by bilinear filtering. Both are capped at 16 MB per file — a mod folder is untrusted input, so an oversized "portrait" is a logged complaint rather than an out-of-memory crash.
Files bind to speakers by id:, never by filename. A translator can name files anything; a rename can never silently detach a translation from its speaker. The corollary: changing id: in a mod file points it at a different character, or at none.

What a broken mod does

A file with parse errors is skipped entirely and the shipped dialogue plays instead — one bad file cannot take down a boss fight, and a good file beside it still loads. The reason, with filename and line number, goes to the player log. Binary junk and empty files are handled the same way: a mod folder is untrusted input, so loading never throws.

Editor and build diverge, deliberately

In a build

Overrides load at boot, always. With no <campaign>/Dialogue/ folder the entire cost is one directory probe — no parsing, no allocation, behaviour identical to before the feature existed.

In the editor

Overrides do not load. The editor's contract is the explicit sync, and a folder quietly beating the asset you are looking at is exactly the surprise that costs an afternoon. Opt in with Gleamwood ▸ Simulate Mods ▸ Dialogue to test the mod path itself.

An override never touches the asset. It lives in a runtime table that DialogueSet.ActiveGroups reads in front of its own fields — the project's no-runtime-SO-mutation rule. So an override cannot leak into the editor, cannot survive into another run, and cannot corrupt shipped content.

The INI seam

Dialogue is not authorable from GameContent.ini — that is what .dlg is for. What INI still carries is the boss's one-line victory convenience:

KeyUnderEffect
dialogue[Boss:X]Points BossDefinition.dialogue at a set by asset name.
outroSpeaker / outroText[Boss:X]Writes into the set's Victory group, first encounter, first line — creating the group if absent, and leaving every other group untouched. Each key only writes when present: outroText alone leaves a hand-authored speaker intact, but supplying outroSpeaker does overwrite it. Because it always targets sequences[0].lines[0], a hand-authored multi-encounter Victory rotation loses its first line on every import. Warns if the boss has no dialogue assigned.

These keys are a holdover from when the victory line was a plain string field on BossDefinition. That field is gone; the keys now fold into the grouped structure on import. See Tuning & INI.

Honest limits — what this system does not do yet

  • Three of the five canonical triggers have no AUTOMATIC caller. Defeat, Phase Two and Banter speak only from a DialogueBeat component placed on the enemy or the NPC (§03), and nothing in the editor warns when it is missing. No shipped scene or prefab carries one today.
  • No conditions on encounters. Selection is purely "how many times has this beat fired". You cannot yet say "this line only if the player has the Emberbrand" — that would need a predicate on DialogueGroup and a filter in Next().
  • No branching or player choice. A sequence is linear; Submit is the only input. There are no response options and no jump targets.
  • No per-line camera or emote hooks. Pose, side, effect, sfx and voice exist; anything beyond them is a new field on DialogueLine plus a handler in DialogueController.ShowLine.
  • No shipped line is spoken. The game ships 15 mood portraits and five SFX stings, baked in (portraits in PoseCatalog, the stings in VoiceBank) — and, since 2026-08-24, no spoken takes at all. The 28 Windows SAPI takes that used to cover Dlg_Krag, Dlg_CinderShepherd, Dlg_PyreRegent and Dlg_EmberVanguard were stripped: real voice-over waits for a script worth recording, and SAPI voices are licensed for OS use rather than for redistribution in a commercial product. Every one of the 65 shipped lines is now a silent text box. None of this touches the pipeline — the example pack keeps its 28 takes as the worked example, a real recording still drops in one file at a time, and a <campaign>/Dialogue/audio/ take still resolves. The row is Documentation/OUTSTANDING.md's "Boss voice-over is Windows text-to-speech, and seven sets are silent".
  • Modded audio is WAV only. No .ogg or .mp3, because decoding those at runtime means an async path and dialogue cannot wait on a decode. Modders pay in file size.
  • Position is coarse. A portrait is left or right; there is no offset, scale or depth. Finer placement would be new modifier syntax and a new field.
  • No hub NPC path. BossArenaSequence is the only DialogueSet consumer in a shipped scene (DialoguePreviewDriver consumes one too, but it is editor-spawned into WHATEVER SCENE IS OPEN — not a throwaway one — and never placed in a build. That distinction matters when previewing: a scene that loads another one out from under it (0.Bootstrapper, whose splash goes to 1.Title) takes the preview with it while the console still reports that it previewed). ForgeSite and RunModifierSite use the panel but build their lines inline, and 2.Hub lacks the panel prefab entirely.
  • Overrides load once, at boot. Editing a mod file mid-session changes nothing until a restart; there is no hot reload.
  • The DialogueController class comment still names BossIntro as its first consumer — that component was superseded by BossArenaSequence. Comment only; the code is current.
