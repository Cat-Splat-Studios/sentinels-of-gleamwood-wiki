UI & the HUD

Every screen in Gleamwood is UI Toolkit — a PanelRenderer per panel, a .uxml for the structure and a .uss for the look. This page covers the two that run during play: the player HUD and the combat read. The menus (title, settings, shop, save slots) are built on the menu framework instead.

Per-enemy markup is built in CODE, not in UXML. EnemyUI.uxml declares only two things: an empty root the tags are added to, and the boss bar. Everything per-enemy is constructed by EnemyUIController.BuildVisuals, because the number of enemies is not known until they spawn. Look there, not in the UXML, when a tag renders wrong.

02The one rule: the tree is rebuilt behind your back

A PanelRenderer hands its visual tree to a controller through RegisterUIReloadCallback, and it can fire more than once — a window resize is enough. Every element reference a controller holds is stale after a reload.

So both HUD controllers follow the same shape, and anything new must too:

  • Re-query every element in the reload callback. Never cache across it.
  • Re-parent code-built elements into the fresh tree (EnsureBowRing is the template: construct once, root.Add every reload).
  • Subscribe to the model exactly once, behind a latch. The tree is rebuilt; the model is not.
  • Re-read remembered state. The boss bar is the worked example — see §04.
In a test, yield twice. The reload callback fires on the frame after enable. A single yield return null reads a tree the controller has not populated, and it fails as "the element is null", which reads like a missing element rather than a timing bug.

Why some are polled and some are events. An event is right when the publisher already raises one and the value changes rarely. Gleam moves on every kill, the modifier set at a reward and the seed once a run — three different publishers, none of which raised anything, and adding three events to serve one view is more machinery than the view is worth. Each poll is a single comparison; the modifier strip compares RunModifiers.Revision rather than diffing the list, so the allocating rebuild only runs when the set actually changed.
Never poll RunDirector.CurrencyBalance. It calls SaveSystem.Load — a disk read — on every get. The in-run number the HUD wants is RunCurrency; the banked total is read once on entering the hub.

Two bars that hide themselves

The enemy health bar appears on the first point of damage and the execution meter on the first point of EP. A room of eight untouched enemies each wearing a full bar is noise that makes the one you have actually hurt harder to find.

The execution meter exists because the EXECUTE flash is binary. The points underneath it are continuous and they decay, so before the meter "am I getting there" had no answer at all — the state was fully visible in a test and invisible in play.

04The boss bar, and remembered signals

A boss is not a property of a creature — the same prefab rolled from a spawn table is an ordinary enemy. Only BossArenaSequence knows which one came through the boss door, so the bar is driven by a signal:

GameSignals.RaiseBossEngaged(boss, displayName);   // step 4, "fight on"
GameSignals.RaiseBossDisengaged();               // the gate opened, or the arena was destroyed

It goes up when the fight is armed, not when the boss spawns: the boss stands dormant through its entrance and the whole dialogue exchange, and a health bar over something that cannot yet be hit — held there for the length of a conversation — reads as a bug and steps on the one beat that is deliberately not a fight.

The signal REMEMBERS its value, and that is load-bearing. GameSignals.CurrentBoss is set before the listener check, exactly as CurrentObjective is. A panel rebuilt mid-fight — a window resize is enough — was not subscribed when the signal fired, so a bar driven only by the live event would vanish and never return. The reload callback re-reads CurrentBoss instead. The same property is why BossArenaSequence.OnDestroy must clear it: a stale value survives into the next scene and raises a bar over the hub.

Name it with BossDefinition.displayName, which falls back to the enemy definition's asset name. It lives on the boss definition rather than on the enemy so a campaign can name its boss in the player's language.

05The dev stamp

Bottom-right of the HUD, in the editor and in development builds only: version · commit · seed.

The seed is the point. A playtest report is worth far more with the number that reproduces the level in it, and it is the one value that is neither in the build nor in any log a player would think to send. Version and commit ride along because "which build was that" is the other question every report needs answered.

It is gated by #if UNITY_EDITOR || DEVELOPMENT_BUILD and, outside that, the text is cleared rather than merely hidden — a populated-but-invisible label is one stylesheet edit away from shipping.

BuildInfo must live in a Resources/ folder. Two runtime readers resolve it with Resources.Load<BuildInfo>("BuildInfo") — this stamp and the debug panel's Troubleshoot tab — and that call returns null for anything outside Resources/ in a build as well as in the editor. It sits at Assets/Resources/BuildInfo.asset; its GUID is referenced by three scenes, so it must be moved, never re-created.

06Testing a screen

Two fixtures show the pattern: DialogueRenderTests and RunHudTests. Both do the same three things.

  1. Instantiate the shipped prefab from Assets/Prefabs/UI/. Not a fixture built by hand — the prefab is what the game loads, and the difference between the two is where UI bugs hide.
  2. Yield twice, for enable then the first UI reload.
  3. Read the controller's own cached element by reflection, rather than querying the panel tree. The root is handed to the controller through a callback and is not reachable from outside — and reading the cache asserts something stronger, that the controller found the element, which is the half that breaks when a UXML name is renamed.

Pixels are out of reach headlessly. Colour, layout and the shake kick are what the preview tools are for; a screen test asserts the wiring and the numbers, which is where the bugs actually are.
