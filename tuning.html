Live Tuning & the INI

Two INI files, one JSON, and an F1 panel that builds itself from attributes. This page is the contract: where every number lives, which edits persist and which die with the session, and the key-by-key reference for GameContent.ini.

01The four homes of a number

Before you tune anything, know where the value you're touching actually lives. There are exactly four homes, and they never overlap.

Rule of thumb: asset/Workbench edits = permanent authored defaults. F1 edits = this session only. The one exception is a control that asks to persist, and no gameplay control is allowed to — the eighteen keys in the tracked DebugSettings.json today are all Camera.* CameraFollow rows, each equal to what every playable scene authors — TunableParityTests pins that parity, boots the panel against a file that says otherwise and requires the PixelPerfectCamera to keep the scene's reference resolution (one row persisted Camera.ResolutionSettingsX = 720 against the scenes' 640 from 2025-06 to 2026-09, which halved the pixel-perfect zoom at 720p), and fails the suite if a Movement/Jump/Dash/Wall Slide key ever joins them. §5 has the reasoning; it cost a real bug.

The dev-build row is not a typo for "release build": the whole F1 panel is compiled out of a release player (§3).

02[Tunable] — declare, don't wire

One attribute on a field (or property) puts a live control on the F1 panel — no panel code, no tab registration, and a new tab name creates the tab on demand.

Defined in Assets/_Framework/DebugUI/TunableAttribute.cs, built into UI by TunableTabs.Build (Assets/_Framework/DebugUI/TunableTabs.cs). Both declarations below are the real shipped ones, copied from PlayerContext.cs — including their Save = false, which is not an oversight but the rule (§5):

// Declare on any float/int/bool field — the tab appears on demand:
[Tunable("Movement", 0f, 20f, Save = false, Tooltip = "Base movement speed of the player")]
public float MoveSpeed = 5f;   // a GAMEPLAY value: the asset owns it, the panel only borrows it

[Tunable("Jump", 0f, 5f, Section = "Jump Settings", Save = false,
         OnChanged = nameof(ApplyJumpGravity))]
public float MaxJumpHeight = 2f;   // side effects via OnChanged, still declaration-local

What it accepts

  • Types: bool → Toggle; float and int → Slider (int values are Mathf.RoundToInt on set). Anything else logs [Tunable] {Type}.{Field}: unsupported type {T} (float/int/bool only). and is skipped.
  • Fields AND properties: reflection covers Public | NonPublic | Instance; properties need both CanRead and CanWrite. KinematicMover2D uses properties deliberately — its setters clamp and trigger recalculation (e.g. SkinWidth clamps ≥ 0.001 and calls CalculateRaySpacing()).
  • Tab merging: PlayerContext and KinematicMover2D both declare on "Movement" — one tab, two source objects, sections keeping them readable.

03The F1 panel today — every control on it

Only the Camera tab's CameraFollow rows persist. Its three Pixel Perfect Camera rows do not — the reference resolution and PPU are the display-scaling contract, not a taste — and every other control on the panel is session-only by design, so a slider you drag here is a question, never an edit — and TunableParityTests is what keeps it that way.

Press F1 in play mode (title: Debug Settings; the toggle key is stamped on the Player prefab's PlayerDebugUI). Movement, Dash, Jump, Wall Slide and Hitboxes come entirely from [Tunable] declarations on PlayerContext (Assets/_Game/Player/Code/PlayerContext.cs), KinematicMover2D (Assets/_Game/Systems/Movement/KinematicMover2D.cs) and CombatHitboxViewer (Assets/_Game/Combat/Code/CombatHitboxViewer.cs) — the three explicit AddTabsFrom targets. The panel is a dev tool, and the whole panel is gated. PlayerDebugUI.Start() opens with #if !UNITY_EDITOR && !DEVELOPMENT_BUILD, which disables the child UIDocument GameObject, sets enabled = false and returns before base.Start(). A release player therefore has no F1 panel at all — not a panel with the cheats removed. Hisham's call was to gate the panel, not the tab: the alternative shipped an F1 panel that retunes the player's movement and prints the save path. The document has to go with the script, because a UIDocument builds its visual tree on its own and would otherwise render debug markup with nothing driving it.
Inside the editor or a dev build, F1 works wherever the Player prefab does. uiDocument, its PanelSettings and its source asset are wired on Assets/Prefabs/Player.prefab itself, so no scene needs an override and none carries one. If the wiring is ever lost, Gleamwood ▸ Dev ▸ Run ▸ Wire Debug Panel rebuilds it — including pointing the document at Assets/UI Toolkit/DebugPanelSettings.asset, its own PanelSettings, so the panel sorts above the HUD rather than merging into it.
Tune jumps on the Jump tab, never mover gravity. Gravity is derived: Gravity = -(2·MaxJumpHeight) / TimeToJumpApex². ApplyJumpGravity() pushes it to both consumers — Mover.Gravity and Physics2D.gravity (dynamic rigidbodies inherit it). The mover's serialized gravity (−25) is overwritten at startup by PlayerStateMachine.
A saved control overrides the scene, silently. Every control marked to save writes into DebugSettings/DebugSettings.json, and that file is re-applied at boot, over whatever the scene or asset authored — nothing logs that it happened. A value you tuned months ago keeps winning. It cost a real bug: a stale Camera.UseBounds clamped the hub camera into a rect the player spawns outside of, so it parked in a corner and never followed. Two rules follow. Host-owned runtime state must not be saved — anything a host writes per room entry (camera bounds and their rect) is saveValue = false, live-toggleable but not persisted. And to retire a stale value, bump the control's key (OffsetY → OffsetYV2) rather than editing the JSON, which is usually someone's working file; a renamed key makes the old entry inert. Precedents in PlayerDebugUI: OffsetYV2, LookAheadDistanceV2, LookAheadTriggerSpeedV2, VerticalDeadzoneV2. That rule governs values the panel still owns — which today means the Camera tab and nothing else.

Not tunable on purpose (inspector/Workbench only): TurnAccelerationMultiplier, MaxHealth, ComboResetTime, dashCurve, MinJumpFraction, JumpCutMultiplier, ApexSpeedThreshold, the weapon references and EnemyLayers.

04Getting your object in front of the panel

Declaring [Tunable] is half the job — the panel also has to know your object exists. There are exactly two doors in, both in DebugUI.cs / TunableTabs.cs.

Door 1 — AddTabsFrom (the wired path)

PlayerDebugUI.ConfigureTabs() (Assets/_Game/Player/Code/PlayerDebugUI.cs) is the override point. Today it does, in essence:

AddTabsFrom(playerContext, playerContext.Mover, hitboxViewer);
// ^ Movement / Dash / Jump / Wall Slide / Hitboxes — all from [Tunable], three targets;
//   PLUS everything in TunableRegistry.Targets — today the three Impact hosts (door 2, below)

if (cameraFollow != null) AddTab(ConfigureCameraTab()); // hand-built: binds scene components + lambdas

#if UNITY_EDITOR || DEVELOPMENT_BUILD
AddTab(ConfigureTroubleshootTab());   // reports state — first, so it is what a report opens on
AddTab(ConfigureRunCheatsTab());      // changes state — kept deliberately apart from the above
#endif
AddTab(ConfigureDebugInfoTab());

If your object is reachable from here (a player-side SO or component), append it to the AddTabsFrom call and you're done.

Door 2 — TunableRegistry (the zero-wiring path)

For anything the player panel shouldn't know about — mechanic SOs, spawned systems — there's an opt-in registry (TunableTabs.cs): TunableRegistry.Register(object) / Unregister(object), null-safe and deduping. AddTabsFrom always builds from its explicit targets plus everything registered.

void OnEnable()  { RuntimeDebugUI.TunableRegistry.Register(this); }
void OnDisable() { RuntimeDebugUI.TunableRegistry.Unregister(this); }
// Register in Awake/OnEnable — the panel SNAPSHOTS the registry when its Start() configures tabs.
// Register late and your tab simply doesn't appear this session.
Status today: three game-code registrants, all on one tab. CombatTimeManager (Assets/_Game/Combat/Code/CombatTimeManager.cs), ShakeComponent (Assets/_Game/Systems/Mechanics/ShakeComponent.cs) and PlayerHurtReact (Assets/_Game/Player/Code/PlayerHurtReact.cs) each Register(this) in Awake and together declare twenty [Tunable]s on "Impact" — hitstop, the perfect-release freeze and shake, enemy hit flash, camera shake, the player's hurt flash and shake (§03). Until 2026-08-15 the grep for TunableRegistry.Register outside _Framework returned nothing; ImpactTuningTests now asserts each host reaches TunableRegistry.Targets and that every declaration becomes a control. Two lessons the first users paid for and the code comments spell out: register in Awake, not OnEnable, because DebugUI.Start snapshots the registry once and never rebuilds; and unregister in OnDestroy, not OnDisable, because the registry is static and outlives the scene.

Recipe: a whole new tab for a new system

  1. Declare [Tunable("MyMechanic", min, max, ...)] on float/int/bool fields or read-write properties of any class. A new tab name creates the tab — no registration of tab names anywhere.
  2. Pick a door: add the object to AddTabsFrom(...) in PlayerDebugUI.ConfigureTabs, or call TunableRegistry.Register(this) in Awake/OnEnable (and Unregister on the way out).
  3. Optional polish: Section groups controls under headers, and OnChanged = nameof(Method) handles side effects. Leave Save at its default unless the control is a genuine panel preference rather than a value the game owns — see §5 before you reach for it.
  4. Nothing else. DebugUI and PlayerDebugUI need no edits — this is the M6 "declare, don't wire" rule.

05Save keys and what actually persists

Twenty-one keys are in the tracked JSON today and every one of them is Camera.*. Nothing else on the panel persists, and that is enforced, not merely true.

Only controls with Save = true (or, on a hand-built control, saveValue = true) are written. The save key grammar is {tabName}.{memberName} — tab name with spaces stripped, member name as written in C#. Live examples, all real: Camera.OffsetX, Camera.OffsetYV2, Camera.VerticalDeadzoneV2. Saved controls show a trailing * on their label and an (Auto-saved) tooltip suffix.

Why the gameplay keys are gone rather than merely inert. Movement, Jump, Dash and WallSlide keys sat in the tracked JSON long after their Save flags were flipped to false, kept harmless by exactly one line — if (!control.saveValue) continue; in DebugUI.LoadValues' apply loop, which runs before the key lookup. (LoadFromFile is not where to look: it only deserialises the file into debugData and never sees a control. The hazard lives in the loop that walks the tabs afterwards.) Reorder those two statements and twenty-one dead numbers come back to life over the assets, silently, and every retune in the project starts lying again. They were byte-identical to the assets, which is precisely why nobody would have caught it: shadowing only becomes visible the first time someone changes an asset and sees nothing happen. So TunableParityTests.TheTrackedSettingsFile_PersistsNoGameplayValue reads the committed file and fails on any gameplay-prefixed key.
MechanismBehavior in this project
Auto-save modeDebounced (the default): the JSON is written 2 s after the last change. Other modes exist (Immediate, Interval 30 s, Manual). Also saves on focus loss and on destroy.
FileDebugSettings\DebugSettings.json — in the editor that's <project root>\DebugSettings\; in a Windows build, next to the .exe; fallback Application.persistentDataPath. Footer buttonsSave Settings (reads Save Settings * when dirty), Clear Saved, Open Folder (desktop). A status label flashes Saving… / Saved.

Reset ≠ authored defaults. "Originals" are captured after the JSON load, so the Reset button restores the start-of-session (saved) values — not the asset's authored values. To truly go back to the asset, press Clear Saved and restart play mode.
Renames auto-invalidate saves. Because the key embeds the member name, renaming a [Tunable] field orphans its stale persisted value for free. Hand-built controls must bump their name manually — the Camera tab's LookAheadTriggerSpeedV2 and VerticalDeadzoneV2 are the precedent: both were renamed precisely so a stale persisted value could not silently disarm look-ahead or break the calm-follow guarantee.

06Authored source vs live copy

The authored source of player feel is one asset — and the panel never touches it, because the panel is bound to a per-session clone.

That asset is Assets/_Game/Player/Resources/PlayerSettings.asset (a PlayerContext SO). At boot, PlayerStateMachine.Awake loads it and clones it:

PlayerContext initalState = Resources.Load<PlayerContext>("PlayerSettings");
context = Instantiate(initalState);   // a fresh clone per session — the asset is never touched at runtime

The F1 panel binds to this clone (AddTabsFrom(playerContext, ...)), so slider edits die with the play session. The mechanism that could survive them is still there — a Save = true control writes the JSON, which is re-applied over the clone at every startup — but no control on the clone declares it any more: every PlayerContext and KinematicMover2D tunable is Save = false, so that escape hatch is closed on the player. The live shadowing surface is the hand-built Camera tab, whose 22 controls bind scene components rather than the clone.

The advice survives the fix, because it is still how the hub-camera bug happened: if a tuned value "won't change", check DebugSettings\DebugSettings.json first. A saved value overrides what the scene authored every session until Clear Saved.

To change the authored defaults, edit the asset — the Workbench's Player category (Gleamwood ▸ Content Workbench) is the curated front door, complete with derived-gravity effective labels so you see the jump math while you type.

The mover is different: KinematicMover2D tunables bind to the scene/prefab component itself — no clone. In a build nothing persists except via the DebugUI JSON; in the editor, play-mode changes revert on exiting play as usual.

Diff noise you can ignore: the asset's [ReadOnly] runtime fields (e.g. LastTimeGrounded) leak in from editor play sessions. ResetProperties() zeroes them at Awake — harmless, just noisy in git.

07GameSettings & config.ini — player-facing persistence

Everything the player touches in the settings menu goes through GameSettings → ConfigStore (Assets/_Game/Systems/Settings/), and every typed Set persists immediately.

On desktop and in the editor that's a human-editable INI at Application.persistentDataPath/config.ini — on Windows, %USERPROFILE%\AppData\LocalLow\Cat Splat Studios\sentinels-of-gleamwood\config.ini (the two path segments are companyName and productName from ProjectSettings.asset, so they are not the Unity defaults and carry no -unity suffix). On other platforms the same keys land in PlayerPrefs as cfg.<section>.<key>. Invariant culture throughout.

Adding a persisted setting (one-liner pattern)

  1. Add the key + section to GameSettings.Sections and a default to GameSettings.Defaults (GameSettings.cs).
  2. Add one row in SettingsMenuController.BuildModel() (Assets/_Game/UI/Code/Screens/SettingsMenuController.cs) using the row factories — Header, Option, Slider (0–100), Action:
Option("Screen Shake", new[]{ "Full", "Reduced", "Off" },
    () => GameSettings.GetInt("screenShake", 0),
    i  => GameSettings.SetInt("screenShake", i))

For a live-apply setting, add a typed accessor on GameSettings that applies in its setter (the WindowMode/MasterVolume pattern). Non-settings systems can persist here too — ConfigStore's own comment: "Other systems can store their own data here too - just pick a section."

08GameContent.ini — the content authoring INI

The other INI is nothing like config.ini. Assets/_Game/Content/GameContent.ini is the authoring source for the entire run — biomes, bosses, enemy vitals, rests, the player's feel, and the node web — imported by ContentIniImporter (Assets/_Game/Editor/ContentIniImporter.cs).

Strictly one-way, editor-only. The INI is the authoring source; the SO assets stay the runtime truth. The game never reads INI at runtime, and there is no INI export. RunContentValidator (Gleamwood ▸ Validate Run Content) auto-runs after every import — and the same validator is the build gate, so broken content refuses to compile.

Grammar

RuleDetail

An accepted key that nothing sets is a feature the game does not have. topology, latticeTier and the whole Branching generator existed, were tested, and could be selected by a campaign INI — while no biome the game shipped could ask for any of them, so every shipped level was a chain. The importer comment says it plainly: a generator no shipped content can reach is a generator that does not exist as far as a player is concerned. That is also why this page's key tables are the contract (§9): a key missing from them is a key nobody will author.

The import loop

  1. Edit Assets/_Game/Content/GameContent.ini in any text editor.
  2. Run Gleamwood ▸ Import Content INI. The importer resolves every key into the SO assets, creating missing Biome/Boss definitions as it goes.
  3. The validator auto-runs. Read the Console: warnings are advisory, errors mean a field was left untouched — fix the INI and re-import. (You can re-run it any time with Gleamwood ▸ Validate Run Content.)
  4. Commit the .ini and the touched .asset files together — the import is the edit; the assets are its output.
Drift is watched from both sides now. The INI and the assets can disagree — a Workbench edit the INI doesn't know about, or an INI edit nobody imported. Gleamwood ▸ Check Content INI Sync reports every section's verdict on demand; the Workbench shows an in sync / DIVERGED row on biome forms, boss staging and enemy vitals (the fields the INI co-owns); Gleamwood ▸ Validate Run Content warns per diverged section; and Import Content INI logs which units it is about to overwrite before it does. The compare mirrors the importer key-for-key (same parser, same resolvers — ContentIni.cs / GameContentSync.cs), and the ContentIniSyncTests flagship test keeps the committed INI and assets in agreement forever. One deliberate nuance: [Node:] sections rebuild the web wholesale, so an absent key there counts as a reset, not "untouched" — the compare knows.
Re-globbing changes old seeds. The resolved roomPool order feeds the seeded generator, so adding a room that matches an existing glob can change layouts for old seeds. Resumed runs re-generate from the current pool — acceptable by design, but know it's happening.
nodeIds are SAVE data. They're written into suspended-run files; never rename shipped ones — the INI's own header says so. A biomeId is save data too — a suspended run resolves its biome by id and the run-web fingerprint hashes it, and the field's own tooltip says never rename once players have saves — so renaming one breaks existing saves as well as the [Node] biome = references at import time.

09Where the INI is headed

Today's split is deliberate: config.ini belongs to the player, GameContent.ini belongs to the designer, and the runtime reads only assets. That shape is also the growth plan.

More keys, same file

The Workbench already defers deep wiring to the INI on purpose — its Levels UI states "Rooms/pool + layout wiring stay in the raw inspector and GameContent.ini". As fields prove stable, they graduate into the key tables above. The table on this page is the contract: a new key isn't shipped until it's listed here.

Content packs

Because the importer creates missing Biome and Boss definitions and the run web is pure data, a new block of INI is a new chapter: nodes, biomes, a boss, a rest — no scene edits, no Build Settings. The intended future: additional authoring INIs imported the same one-way route, validated by the same gate.

Mod-friendly by construction

One-way import + the validator-as-build-gate means text edits can never silently break a build — a typo errors and leaves wiring untouched. Pair that with a human-editable config.ini and a TunableRegistry that the Impact tab has now used exactly as designed (§04), and the tuning surface is already shaped for hands that aren't ours.

None of the future items above exist yet beyond what §8 documents — treat this section as direction, not reference. When any of it lands, it moves up into the tables and this box shrinks. The order in which the open items on this page are meant to land — displayName in [Boss:] and the Deck hardware walk — is sequenced in Documentation/DESIGNER-HANDOFF-PLAN.md; the rows themselves live only in Documentation/OUTSTANDING.md. Extension seams in code live on Extending.

10The Steam Deck — a display you don't own

The Deck is a primary platform, and it has no build of its own: it runs the Windows player through Proton, under gamescope. Every number this page teaches you to tune therefore has a second audience — a 1280×800 panel seven inches wide, held at arm's length, pad in both hands — and it works on Windows is not the same claim as it works on the Deck.

The display is decided before the game exists

On a Deck the resolution is chosen before launch, from Steam/Proton settings, and the game defers on both halves: the Display tab's Window Mode and Resolution rows are dimmed to Set in Steam, and the boot-time apply of a saved resW/resH/windowMode returns before touching Screen — the keys are ignored, never erased, so the same config.ini still drives a desktop. The mechanics live in §07; what this section adds is the rule behind them: never author anything that assumes the game can set its own resolution or window mode, and before any change that touches display, windowing, fullscreen or UI scaling, ask what does Proton do with it? Under gamescope every window mode composites into the same host-owned surface — Fullscreen and Borderless are the same picture, and a floating window is hostile to a handheld — so a feature whose value depends on owning the display has no value on this platform.

Interruptions are platform behaviour too. FocusGuard pauses a live run when the window loses focus, when a pad disconnects, and when the Steam overlay opens — and on a Deck the Steam button does that mid-fight, routinely. Author nothing that cannot tolerate the pause menu opening on any frame. Details: ui.html §05.

Text has a physical floor

The shared Assets/UI Toolkit/PanelSettings.asset scales the whole interface from a 1200×800 reference, half by width and half by height, so the factor a screen actually receives depends on its aspect:

DisplayPanel scaleA 12 px USS rule renders at
Steam Deck — 1280×800, 16:10, 7-inch panel≈ ×1.03≈ 12 physical px
1920×1080 monitor≈ ×1.47≈ 18 px
2560×1440 monitor≈ ×1.96≈ 24 px

At ×1.03 a USS pixel is, near enough, a physical pixel on a screen seven inches across. Hence the floor: keep information-bearing text at 12 px or more. Enemy status stacks, HUD run-modifier names, run-map node names and the pause-menu seed are all information, and several of them ship below that today — the open half of Documentation/OUTSTANDING.md, the row "Deck legibility: 10–13 px text and a Text Size row read by nothing", and closing it is USS-only, designer-doable work. The player's Text Size row (Small ×0.9 / Medium ×1 / Large ×1.15, GameSettings.TextSizeScale) multiplies the whole panel's scale; it is the player's accessibility dial, not your size budget — Large does not make a 10 px rule readable on a handheld, and Small makes it smaller still. Author for Medium and keep your floor clear of both ends.

The reference aspect is an open decision. 1200×800 is 3:2 — an aspect the game ships on nowhere — which is why the factor swings by aspect at all. The fix starts with a decision only Hisham can make and is tracked on OUTSTANDING "The UI is not consistent across resolutions". Until it lands, walk any screen you author at 16:9 and 16:10 before calling it done.

A shake number is a haptics number

The Deck has motors, and Rumble drives them from ShakeComponent.Shake — every impact that shakes the camera also buzzes the pad, at a strength derived from the same amplitude you author: full motor at 0.35, and most shipped shakes run 0.1–0.3, so a heavy hit reads strong without every tap saturating — the one outlier is the bow execution's authored 0.5, which pegs the motor at full. Retune a HitShake on a swing (combat §02) and you have retuned the player's hands as well as their eyes. Deliberately, the rumble sits above the Screen Shake gate and reads its own Vibration key: stilling the camera and silencing the pad are two different accessibility answers, and RumbleTests pins them apart — don't tidy them into one condition.

Sanity-checking without the hardware

  1. Walk your screens at the Deck's shape. Add a 1280×800 entry to the Game view's resolution dropdown and re-check every screen you touched at 16:10 — the aspect and the panel scale are the Deck's even though the editor's DPI is not. Read the smallest text from further back than feels fair.
  2. Check Text Size in a development build, not in play mode. The panel write is deliberately compiled out of the editor — PanelSettings is a tracked asset and a play-mode write to one survives exiting play mode — so flipping the row under the editor changes nothing, by design. In a build, Settings ▸ Accessibility ▸ Text Size: your layout must survive ×0.9 and ×1.15 without clipping a row.
  3. Run the suite. DeckDisplayPolicyTests (the display deference, pinned in both directions with a desktop control), InterfaceScaleTests (the Text Size apply), RumbleTests (shake→motor, and the gate separation) and PauseGuardTests (the pause-on-interruption rules) all run on every machine, because each drives the platform answer through an injection seam.
The editor can prove the policy, never the platform. Nothing on a dev machine is a Steam Deck — detection is SteamUtils.IsSteamRunningOnSteamDeck(), and every non-injected path answers not a Deck — so a green suite here is exactly as good as the injection seam and no better. The proof is a hardware walk at the next checkpoint build, scripted step by step in publishing §09; until somebody walks it, the whole policy stays on OUTSTANDING "The Steam Deck display fix is in, but unproven on hardware".
